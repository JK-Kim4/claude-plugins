# Document Generator

좋은 문서는 템플릿이 아니라 **"누가, 왜 읽는가"에 맞춘 정보 선택**에서 나온다. 이 스킬은 항상 같은 순서로 움직인다: 목적 판단 → (모호하면) 짧게 질문 → 형식 선택 → 실제 내용 수집 → 작성. 상세 규칙은 `references/`에 있고, 아래 표가 어느 파일을 언제 읽는지 정한다.

## 1단계: 목적과 유형 판단

프롬프트에서 먼저 읽어낸다.

- **독자** — 나중의 나 / 팀원 / 리뷰어 / 처음 보는 사람. 독자가 아는 것이 적을수록 배경을 더 담는다.
- **읽는 목적** — 무슨 일이 됐는지 / 다음에 뭘 할지 / 왜 이렇게 설계했는지 / 어떻게 쓰는지.
- **출력 형식** — 사용자가 명시한 것을 따른다. 명시가 없으면 **Markdown 파일**.
- **언어** — 기본 한국어(코드·식별자·명령어·고유명사는 원문 유지).
- **문체** — **산문형**(3~6문장 문단, 리스트는 진짜 열거에만)과 **개조식**(불릿 압축) 중 하나. 명시가 없으면 유형 관례를 따르되(진행/추적·회의록은 개조식, 기술 아티클·긴 설계는 산문형) 문체가 결과를 크게 좌우하는 문서는 2단계에서 확인한다. 산문형의 리스트 항목은 "굵은 주장 문장 + 뒷받침 문장"으로 완결되게 쓴다.

유형을 하나로 매핑하고 **해당 템플릿 파일을 읽고 그 구조와 권고를 따른다.** 각 파일 하단의 출처는 권고의 근거이지 문서에 인용할 대상이 아니다.

| 유형 | 언제 | 핵심 질문 | 템플릿 |
|------|------|-----------|--------|
| **작업 보고서** | "정리해줘", "리포트", "PR 설명", "변경 요약" | 무엇을, 왜 했고, 결과가 무엇인가 | `references/work-report.md` |
| **진행/추적** | "체크리스트", "TODO", "진행 현황", "마일스톤" | 무엇이 끝났고 무엇이 남았나 | `references/progress-tracking.md` |
| **기술 설계/분석** | "설계 문서", "ADR", "기술 분석", "트러블슈팅 정리" | 왜 이 결정을 했고 대안은 무엇이었나 | `references/technical-design.md` |
| **온보딩/가이드** | "README", "가이드", "셋업 안내", "사용법" | 독자가 따라서 성공할 수 있나 | `references/onboarding-guide.md` |
| **회의록** | "회의록", "미팅 정리" | 무엇이 결정됐고 누가 무엇을 하나 | `references/meeting-notes.md` |
| **장애 보고서** | "포스트모템", "장애 보고서", "인시던트 회고" | 왜 일어났고 재발을 어떻게 막나 | `references/postmortem.md` |
| **기술 아티클/해설** | "블로그 글", "기술 해설", "설계 스토리" | 왜 바꿨고 무엇을 배웠나 (서사) | `references/tech-article.md` |

유형이 둘 이상에 걸치면 **주된 목적 하나**를 뼈대로 삼고 필요한 섹션만 빌려온다.

## 2단계: 모호하면 짧게 질문

목적·독자·범위가 잡히지 않으면 추측하지 말고 **1~2개**만 묻는다. 답에 따라 문서 구조가 실제로 달라질 때만 묻는다(팀 공유용인가 본인 기록용인가 / 설계 문서인가 작업 보고인가 / 새로 만들까 이어 쓸까). 답이 명확하면 가정을 한 줄로 밝히고 진행한다.

## 3단계: 실제 내용 수집

빈칸을 추측으로 메우지 않는다. 방금 한 작업이면 대화 기록에서, 코드 변경이면 `git diff`·`git log`·변경 파일에서 사실을 확인한다. 확인되지 않은 결과(테스트 통과 여부 등)는 "미확인"으로 표시하거나 확인한다.

## 4단계: 작성

- **요약을 맨 위에.** 첫 문단/표만 보고도 핵심을 알 수 있어야 한다.
- **추측과 사실을 구분한다.** 검증된 것·추정·미확인을 섞지 않는다.
- **빈 섹션은 넣지 않는다.** 해당 내용이 없으면 뺀다.
- **섹션 제목은 라벨이 아니라 주장·질문으로.** "배경", "내용", "기타" 대신 "왜 재설계가 필요했나"처럼 제목만 훑어도 논리가 보이게(템플릿의 관례 섹션명은 예외).
- **파일로 저장한다.** 위치 미지정이면 프로젝트 루트나 `docs/`에 `kebab-case.md`로 저장하고 경로를 알린다.
- 분량은 목적에 맞게(추적은 짧게, 설계는 맥락 충분히). 개별 문장은 아래 규칙대로 짧게.

**문장 규칙**: 본문을 쓰기 전에 `references/sentence-style.md`를 읽고 따른다(번역체 제거·능동형·한 문장 하나의 생각·수치·용어 일관). 저장 전에 그 파일 하단의 점검 목록으로 훑는다.

**출력 형식·시각화 분기** — 해당하는 경우에만 그 파일을 읽는다.

| 상황 | 읽을 파일 |
|---|---|
| HTML(스타일 문서·PDF) 요청 | `references/html-output.md` — 자기완결 단일 HTML, 종류별 컴포넌트, 한글 레이아웃 규칙, 저장 전 `check-layout.py` |
| Notion 요청("노션에 정리해줘") | `references/notion-output.md` — 블록 매핑, mermaid 코드블록, 편집 사고 방지 |
| HTML에 아키텍처·시퀀스·상태·ER 그림 | `references/mermaid-render.md` — Mermaid를 생성 시점에 정적 SVG로 렌더(CDN 금지) |
| HTML에 데이터 차트·Before/After 쌍 | `references/diagrams.md` — 손으로 그리는 인라인 SVG, 좌표·한글 폭 규칙 |

다이어그램은 채널에 맞춘다: HTML은 인라인 SVG, Notion은 mermaid 코드블록, Markdown은 표. ASCII 아트는 쓰지 않는다. **모든 그림 바로 아래에 그림이 보여주는 것을 완결 문장 한 줄(캡션)로 적는다.** 수치 비교·추이는 구조 그림이 아니라 데이터 차트(HTML) 또는 표(Markdown·Notion)로.

작성 후, 어떤 유형으로 판단했고 어디에 저장했는지 한 줄로 알린다.

## 갱신 모드: 기존 문서 업데이트

사용자가 기존 문서를 지목하거나 같은 주제의 문서가 이미 있으면 새로 만들지 않고 갱신한다. 존재가 의심되면 짧게 검색하고, 이어 쓸지 새로 만들지 모호하면 묻는다.

- **기존 문서를 끝까지 읽고 그 구조·표기 관례를 따른다.** 템플릿과 달라도 기존 구조가 우선이다. 재구성은 제안만 하고 승인 전에는 손대지 않는다.
- **유형별 갱신 규칙**
  - *진행/추적*: 완료 항목은 지우지 말고 체크로 남긴다. 최종 갱신일과 RAG 상태를 현실에 맞게 재평가하고, 해소된 blocker는 해소됐다고 남긴다.
  - *작업 보고서/분석*: 기존 서술과 상충하면 조용히 덮어쓰지 말고 무엇이 달라졌는지 드러낸다.
  - *기술 설계(ADR)*: 수락된 ADR은 불변. 새 ADR을 만들고 기존 상태를 `Superseded by ADR-NNNN`으로 바꾼다.
  - *회의록(정례)*: 이전 액션 아이템의 완료 여부를 이어서 추적한다.
- **삭제는 보수적으로.** 낡아서 틀린 정보(잘못된 상태, 지난 일정)에 한정하고, 판단이 서지 않으면 남기고 표시한다.
- HTML 문서 갱신 시 `<style>`은 현재 `document.css`로 교체하고 감싸이지 않은 표를 `.table-wrap`으로 감싼다(`html-output.md`).
