# HTML 출력 가이드

사용자가 문서를 **HTML 형태**로 요청했을 때(또는 스타일·디자인이 입혀진 문서를 원할 때) 따른다. 핵심은 두 가지다: **내용·구조는 문서 종류의 템플릿을 그대로 따르고, 형식만 HTML로 입힌다.** 그리고 **문서 종류에 맞는 시각적 컴포넌트**를 적용해 목적이 한눈에 드러나게 한다.

## 1. 먼저 종류별 템플릿을 읽는다

HTML은 표현 형식일 뿐이다. *무엇을 담을지*는 여전히 해당 문서 종류의 템플릿(`work-report.md` / `progress-tracking.md` / `technical-design.md` / `onboarding-guide.md`)이 정한다. 그 파일을 먼저 읽고 섹션 구조·원칙·안티패턴을 따른 뒤, 아래 규칙으로 HTML을 입힌다.

## 2. 자기완결 단일 HTML 파일로 출력한다

공유·열람 시 파일 하나만 열면 바로 보이도록, **외부 의존성이 없는 단일 `.html` 파일**로 만든다.

- `assets/document.css`의 **내용을 읽어 `<head>`의 `<style>` 태그 안에 그대로 임베드**한다. 외부 CSS 링크나 CDN(폰트·JS 라이브러리 포함)은 쓰지 않는다 — 오프라인에서도 깨지지 않아야 한다.
- `<html lang="ko">`, `<meta charset="utf-8">`, `<meta name="viewport" ...>`를 포함한다.
- JavaScript는 기본적으로 넣지 않는다. 꼭 필요하면(예: 목차 토글) 외부 의존 없는 짧은 인라인 스크립트만.
- 기본 골격:

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>[문서 제목]</title>
  <style>
  /* assets/document.css 내용을 여기에 그대로 붙여넣는다 */
  </style>
</head>
<body>
  <!-- 문서 본문 -->
</body>
</html>
```

## 2-1. 한글 레이아웃 규칙 (필수)

한글은 글자당 폭이 영문의 약 1.7배다. 영문 기준으로 짜인 표·박스·다이어그램에 한글을 넣으면 칸을 넘겨 **표가 본문을 밀어내거나 글자가 잘린다.** `document.css`가 절반을 막아주지만(한글은 어절 중간에서 끊지 않되, 어절·경로가 칸보다 길면 강제로 끊는다), 나머지는 본문을 쓸 때 지켜야 한다.

- **표는 예외 없이 `<div class="table-wrap">`으로 감싼다.** 이 래퍼가 없으면 넓은 표가 페이지 전체를 가로로 밀어낸다(좁은 창·모바일에서 즉시 드러난다). CSS 클래스만으로는 적용되지 않는다 — 매번 감싸야 한다.

  ```html
  <div class="table-wrap">
    <table>…</table>
  </div>
  ```

- **표는 4열 이하로.** 한글 표는 열이 늘어날수록 각 칸이 글자 두세 개 폭으로 쪼그라든다. 5열이 필요하다고 느껴지면 열이 아니라 정보 구조가 잘못됐다 — 긴 서술 열은 빼서 표 아래 불릿으로 옮긴다.
- **긴 경로·URL·브랜치명을 표 칸에 그대로 넣지 않는다.** `docs/research/2026-07-21-member-lifecycle-delta-mockup.html` 같은 값은 칸을 독차지한다. 파일명만 쓰거나(`…delta-mockup.html`) 표 밖 본문에서 한 번 밝힌다.
- **다이어그램 텍스트는 `references/diagrams.md`의 글자수 예산을 따른다.** SVG 안의 글자는 줄바꿈되지 않고 잘려 사라진다.
- **인쇄(PDF)에서는 가로 스크롤이 없다.** `.table-wrap`은 화면용 안전망일 뿐이고, 인쇄 시에는 `@media print`가 스크롤 영역을 펼치므로 애초에 폭을 넘기지 않게 써야 한다.
- **기존 HTML 문서를 갱신할 때는 `<style>` 블록을 현재 `document.css` 내용으로 교체하고, 감싸이지 않은 표를 `.table-wrap`으로 감싼다.** 갱신 모드의 "기존 구조·표기 관례를 보존한다" 규칙은 **본문**에 적용되고 스타일시트에는 적용되지 않는다 — 낡은 CSS를 그대로 두면 고쳐진 넘침이 그 문서에서만 되살아난다.

## 3. 문서 종류별 컴포넌트 적용

`document.css`가 제공하는 클래스를 종류에 맞게 쓴다. 모든 요소를 다 쓰려 하지 말고, 해당 문서에 실제로 필요한 것만.

### 작업 보고서
- 제목 아래 `<p class="doc-meta">`에 날짜·작성자.
- 요약은 `<div class="summary">`로 상단 강조.
- **Breaking Change는 `<div class="callout callout-warning">`**(빨강)으로 눈에 띄게. 주의사항은 `callout-caution`(노랑).
- 검증 결과의 통과/미확인은 `<span class="badge badge-green">통과</span>` / `badge-neutral`로.

### 진행/추적
- 문서 상단에 **RAG 헬스 헤더**를 크게:
  ```html
  <div class="health health-amber"><span class="dot">🟡</span> At Risk — PG사 API 키 발급 대기로 결제 연동 지연</div>
  ```
  (green/amber/red 중 현실에 맞게. `health-green`/`health-amber`/`health-red`)
- 체크리스트는 `<ul class="checklist">` + `<li class="done|todo|blocked">`.
- 상태 표를 쓸 때 상태 셀에 `badge-green`/`badge-amber`/`badge-red` 배지.
- Blocker는 `<div class="callout callout-caution">`로 강조하고 담당·기한을 함께.

### 기술 설계 / ADR
- 제목 아래 `doc-meta`에 상태 배지: `<span class="badge badge-amber">Proposed</span>` (Accepted=green, Rejected/Superseded=red/neutral).
- **고려한 대안의 장단점, Consequences의 긍정/부정은 `<div class="proscons">`**(좌 `.pros` 초록 / 우 `.cons` 빨강)로 시각 대비.
- 결정(Decision)은 `summary` 박스로 도드라지게 해도 좋다.
- 분석·트러블슈팅 문서의 **권장 조치가 여럿이면 확신도를 배지로 구분**한다: `badge-green` 강력 권장(근거 확인됨) / `badge-amber` 검토 권장(트레이드오프 있음) / `badge-neutral` 추정(미검증). 근거가 약한 제안을 강한 제안과 같은 무게로 늘어놓으면 독자가 우선순위를 못 잡는다.
- 구조를 바꾸는 결정은 Before/After 다이어그램(`diagrams.md` 6번)으로 결정의 효과를 보인다.

### 온보딩 / 가이드
- 섹션이 많으면 상단에 `<nav class="toc">` 목차(앵커 링크).
- 단계는 `<ol>`로, 각 단계의 기대 결과는 `<div class="expected">이게 보이면 성공</div>`.
- 명령어는 `<pre><code>` 코드 블록. 언어가 분명하면 그대로 텍스트로 두되 가독성 위해 들여쓰기 유지.

## 4. 다이어그램 / 시각화

구조·흐름·상태·데이터 관계를 그림으로 보여줄 때는 **ASCII 아트(monospace 박스·화살표)를 쓰지 않는다.** 대신 `references/diagrams.md`를 읽고 그 규칙을 따른다 — **인라인 SVG를 `<figure class="diagram">`에 임베드**한다(외부 의존 없음, 자기완결 유지). SVG를 얻는 경로는 둘이다: 아키텍처·시퀀스·상태·ER처럼 관계가 graph 형태면 **Mermaid로 기술해 생성 시점에 정적 SVG로 렌더**하고(`references/mermaid-render.md` — 자동 레이아웃이라 좌표가 어긋나지 않는다), 데이터 차트와 Before/After 쌍은 **손으로 작성**한다. 어느 쪽이든 완성된 문서에는 SVG만 남는다 — **Mermaid CDN 스크립트를 문서에 넣지 않는다.** 그리드 좌표 규칙과 보일러플레이트를 따르면 박스·화살표가 어긋나지 않는다. 아키텍처/컴포넌트, 시퀀스/흐름, 상태 전이, ER, 데이터 차트(막대/선), Before/After 비교 6종 패턴이 있다. 특히 **기술 설계/ADR 문서**는 아키텍처 구조와 핵심 흐름을 다이어그램으로, **작업 보고서·진행 문서**는 수치 비교·추이를 데이터 차트로 보강할 때 직관성이 크게 오른다. **구조를 바꾼 작업(리팩토링·마이그레이션·아키텍처 전환)은 결과만 그리지 말고 Before/After를 나란히** 두면 무엇이 나아졌는지가 한눈에 잡힌다.

## 5. 편집 원칙 — 절제와 밀도

HTML은 색·박스·배지를 얼마든지 쓸 수 있어서, 그냥 두면 **대시보드처럼 보이지만 읽히지는 않는 문서**가 되기 쉽다. 목표는 화려함이 아니라 밀도다. 사내 대시보드가 아니라 잘 조판된 인쇄물에 가깝게 만든다.

**색과 강조는 의미를 전달할 때만 쓴다.**

- 강조색은 **하나**(`--accent`)로 고정한다. 나머지 색은 의미가 정해진 것만: 초록=성공/완료, 노랑=주의/지연, 빨강=실패/breaking. 항목마다 다른 색을 칠하지 않는다.
- 배지·callout·health 헤더를 한 화면에 겹겹이 쌓지 않는다. **모든 것이 강조되면 아무것도 강조되지 않는다.**
- 진행/추적의 RAG는 보기 좋으라고 green을 주지 않는다 — 현실을 반영한다.
- 여백을 아끼지 않는다. 섹션이 서로 붙어 있으면 구조가 보이지 않는다.

**산문을 줄이고 구조로 말한다.**

- 불릿이 될 수 있는 문장은 불릿으로 쓴다. 불릿을 지워도 뜻이 남으면 지운다.
- 군더더기 도입부("먼저 살펴보자면", "~라는 점도 주목할 만하다")와 얼버무리는 표현("~인 것 같다", "어느 정도")을 쓰지 않는다. 불확실하면 **"미확인"으로 명시**한다 — 얼버무리는 것과 다르다.
- 표·배지·체크리스트로 이미 표현된 내용을 본문에서 다시 서술하지 않는다.
- 요약 박스는 문서 전체를 압축한 것이지, 도입부 인사말이 아니다.

**용어를 문서 안에서 일관되게 쓴다.** 같은 대상을 문단마다 다른 이름으로 부르지 않는다(모듈/컴포넌트/서비스를 섞어 쓰지 않는다). 문서 종류의 템플릿이 정한 용어 — ADR의 배경/결정/결과, 포스트모템의 근본 원인/기여 요인 — 를 그대로 쓰고 임의로 바꾸지 않는다.

## 6. 저장 전 레이아웃 점검

파일을 쓴 뒤 반드시 실행한다. 한글 넘침은 코드를 눈으로 읽어서는 보이지 않는다 — 좌표를 계산해야 드러난다.

```bash
python3 <스킬경로>/assets/check-layout.py report.html
```

SVG 텍스트가 박스·viewBox를 벗어나는지, 표가 `.table-wrap`으로 감싸였는지, 표 열이 너무 많은지를 잡아낸다. **발견 0건이 될 때까지 고친다.** 지적된 텍스트는 짧게 줄이거나 문장을 SVG 밖으로 옮기고, 박스 폭을 늘렸으면 `viewBox`도 함께 늘린다.

## 7. 공통 원칙 유지

- Markdown 기본 출력과 마찬가지로 빈 섹션은 넣지 않고, 요약을 위에 두고, 추측과 사실을 구분한다.
- 파일은 의미 있는 이름(`kebab-case.html`)으로 저장하고 경로를 알려준다.

## 8. 다른 형식 요청 시

- **PDF**: 먼저 위 방식으로 자기완결 HTML을 만든 뒤, 사용자에게 "브라우저에서 인쇄→PDF 저장" 또는 변환 도구 사용을 안내한다. CSS에 `@media print`가 포함돼 인쇄 시에도 레이아웃이 유지된다. 변환 도구(예: wkhtmltopdf 등) 사용은 환경에 설치돼 있는지 확인 후에만.
- 그 외 형식은 사용자의 명시를 따르되, 불확실하면 짧게 확인한다.
