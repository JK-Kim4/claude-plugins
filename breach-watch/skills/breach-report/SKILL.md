# breach-report — 쉬운 점검 보고서 HTML

breach-audit 보고서(`docs/security/breach-audit/YYYY-MM-DD.md`)는 다음 점검이 읽는 원본이라 길고 촘촘하다. 이 스킬은 그것을 **사람이 3분 안에 읽는** HTML로 옮긴다.

## 독자

- 기본 독자는 **개발을 모르는 사람**이다. 대표, 기획, 운영, 그리고 중학생이 읽어도 알아들어야 한다.
- 개발자가 볼 것(파일:줄, 함수 이름, 설정 키)은 카드마다 접힌 `개발자용 근거` 칸에만 둔다. 이 칸을 다 접어도 문서가 이해돼야 한다.

## 파일

| 파일 | 쓰는 때 |
|---|---|
| `templates/report.html` | 출발점. 복사해서 `{…}`를 채운다. 신호등·숫자 칸·서비스 지도·지적 카드·흐름 그림·질문·용어 풀이 부품이 들어 있다 |
| `reference/plain-words.md` | 용어를 바꿀 때. 원래 말 → 본문에 쓸 말 → 풀이 한 줄 |
| `check/check.py` | 넘기기 전 점검. 0건이어야 한다 |

## 글 규칙

- **서술하지 않는다. 한 줄 bullet로 쓴다.** 한 줄에 사실 하나. 길이 상한: 결론 50자, 카드 bullet 60자, 질문 90자, 흐름 단계 26자, 카드 제목 34자.
- **결과를 먼저 말한다.** ❌ "카카오 이메일 검증 플래그 미확인" ✅ "남이 관리자 열쇠를 가져갈 수 있어요"
- **쉬운 말 표를 따른다.** IDOR → "남의 것 열어보기", JWT 서명키 → "출입증 도장", MFA → "2단계 확인". 원래 용어가 꼭 필요하면 `<span class="term">쉬운 말 <small>(용어)</small></span>`로 한 번 붙이고 '낯선 말 풀이'에 넣는다.
- **해요체.** "~해요", "~예요". 명사로 끝내도 된다.
- **숫자와 조건은 원본 그대로.** "14일", "5회 실패하면 30분". 조건이 있는 지적은 조건을 떼지 않는다("관리자 이메일로 된 일반 가입 계정이 없으면").
- **실제 사고를 한 줄 붙인다.** "쿠팡(2025)도 출입증 도장이 새서 뚫렸어요." 독자가 "남 일이 아니구나"를 느끼는 줄이다.
- **잘 된 점도 쓴다.** 고칠 것만 있으면 독자가 전부 엉망이라고 오해한다.

## 그림 규칙

그림이 설명의 중심이다. 글로 길게 풀어야 할 것은 그림으로 바꾼다.

| 무엇을 보여 주나 | 부품 |
|---|---|
| 우리 서비스가 어떻게 생겼고 구멍이 어디 있나 | **서비스 지도** `.map` — 사용자 → 화면 서버 → API 서버 → DB 줄과 바깥 서비스(카카오, AI 등). 상자 색은 그 상자에 걸린 가장 위험한 카드 색(`.m-weak` 빨강·`.m-warn` 주황·`.m-note` 노랑), 번호 배지 `.m-hit`(`.o`·`.y`)는 카드로 링크. 한 상자에 카드가 여럿이면 가장 위험한 번호를 달고 나머지는 범례 줄에 적는다 |
| 한 지적이 어떻게 피해로 이어지나 | **공격 흐름** `.flow` — `누가` → `구멍` → `피해` 3~4단계. 막는 법을 보여 줄 때는 `.n-block` 단계와 `.arrow.x` |
| 전체 상태 | **신호등** `.signal`(결론 3~4줄) + **숫자 칸** `.stats`(판정별 수) |

- 서비스 지도는 원본 보고서의 스택 태그와 코드에서 확인한 구성으로 그린다. 확인 못 한 상자는 그리지 않는다.
- 빨간 카드는 반드시 지도에 번호로 표시한다(점검 스크립트가 본다).
- 흐름 단계 글자는 짧게. 단계에 설명이 더 필요하면 카드 bullet로 옮긴다.
- 그림 색은 뜻이 하나씩이다. 지도·카드: 빨강=아주 위험, 주황=위험, 노랑=주의. 숫자 칸·알약: 빨강=열려 있음, 주황=반쯤 막힘, 남색=확인 필요, 초록=잘 돼 있음, 회색=해당 없음. 흐름 그림: 남색=누가, 빨강=구멍, 주황=피해, 초록=막음.

## 절차

1. **원본 읽기.** breach-audit 보고서 .md 전체를 읽는다. 메타 주석(catalog_version, audited_at)과 요약 수를 그대로 옮긴다.
2. **고를 것.** 카드는 FAIL·PARTIAL 지적 전부. 순서는 원본의 심각도 순. 비슷한 지적은 한 카드로 묶지 않는다(다음 점검이 항목 단위로 본다). 단, 원본에 없는 지적을 만들지 않는다.
3. **지도 그리기.** 구성 요소를 정하고 각 카드가 지도 어디에 해당하는지 번호를 단다.
4. **쓰기.** 틀을 출력 파일로 복사해 채운다. 출력 위치는 원본 옆 같은 이름의 `.html`(`docs/security/breach-audit/YYYY-MM-DD.html`).
5. **점검.** `python3 -I <이 스킬 폴더>/check/check.py <출력.html>`이 0건이 될 때까지 고친다.
6. **사람 눈으로 보기.** 아래 '사람이 볼 것'을 확인한다. 가능하면 헤드리스 브라우저로 밝은·어두운·좁은 화면을 찍어 본다(ezpz 스킬의 '렌더' 절과 같은 방법).
7. **넘기기.** 파일 경로를 알려 주고, 이 문서가 공격 경로를 담고 있으니 공개 저장소에 커밋하거나 공개 링크로 올리지 말라고 한 줄 덧붙인다. 공유 링크가 필요하면 사용자에게 묻고 비공개로만 게시한다.

## 사람이 볼 것 (점검 스크립트가 못 잡는 것)

- 숫자 칸·카드 수가 원본 요약과 같은가
- 조건부 지적의 조건이 빠지지 않았는가
- 개발자용 칸을 전부 접고 읽어도 각 카드가 이해되는가
- 지도의 상자가 실제 구성과 맞는가(없는 서버를 그리지 않았는가)
- 비밀값이 한 글자도 들어가지 않았는가
