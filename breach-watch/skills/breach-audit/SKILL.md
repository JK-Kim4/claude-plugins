# breach-audit — 사고 기반 취약점 점검

공격자가 AI로 정찰·취약점 탐색 비용을 낮추면서, **이미 알려진 약점이 더 빨리, 더 많이** 털린다. 이 스킬은 "최근 실제로 뚫린 경로"를 점검 항목으로 바꾼 카탈로그를 들고 현재 프로젝트를 훑는다.

## 안전 규칙 (먼저 읽는다)

- **읽기 전용.** 파일을 읽고, 로컬에서 읽기 전용 명령만 돌린다. 운영·스테이징 시스템에 요청을 보내 취약점을 확인하지 않는다(포트 스캔, 퍼징, 익스플로잇, 로그인 시도 모두 금지). 확인이 필요하면 보고서에 "운영 확인 필요"로 남긴다.
- **비밀값을 옮기지 않는다.** 하드코딩된 키·토큰을 찾으면 `파일:줄`과 앞 6자만 적는다. 보고서·대화·커밋 어디에도 전체 값을 쓰지 않는다. `scan`은 줄 내용을 자동으로 가린다.
- **외부로 데이터를 보내는 도구는 묻고 돌린다.** `npm audit`·`pip-audit`·`osv-scanner`는 의존성 목록을 외부 DB에 보낸다. 설치돼 있으면 쓰겠다고 한 줄 묻는다. `gitleaks`처럼 로컬에서만 도는 도구는 설치돼 있으면 바로 쓴다. 도구를 새로 설치하지 않는다.
- **신호 없음 ≠ 안전.** 패턴이 안 걸린 항목도 `how_to_check`대로 직접 보고 판정한다.

## 파일

| 파일 | 쓰는 때 |
|---|---|
| `scripts/catalog.py` | 카탈로그 위치·버전 확인, 스택 추정, 항목 선택, 신호 스캔. `python3 <이 스킬 경로>/scripts/catalog.py <명령>`으로 프로젝트 루트에서 실행 |
| `catalog/checks.json` | 점검 항목(정본). 항목마다 근거 사건, 확인 방법, 통과 기준, 조치 |
| `catalog/incidents.json` | 근거 사건. 날짜·조직·공격 경로·근본 원인·AI 관여 수준·출처 |
| `catalog/CHECKLIST.md` | 사람이 읽는 목록(생성물). 사용자에게 전체 목록을 보여 줄 때 |
| `catalog/CHANGELOG.md` | 버전별로 무엇이 들어왔는지 |
| `references/report-template.md` | 보고서 형식 |

카탈로그는 `catalog.py where`가 가리키는 곳을 쓴다. 사용자 카탈로그(`~/.claude/breach-watch/catalog`)가 있으면 그것이, 없으면 플러그인 번들이 쓰인다.

## 절차

### 1. 카탈로그와 이전 점검 확인

```bash
python3 <skill>/scripts/catalog.py where
ls docs/security/breach-audit/ 2>/dev/null
```

- `researched_through`가 오늘보다 **60일 넘게** 지났으면 사용자에게 한 줄 알린다: "카탈로그가 YYYY-MM-DD까지 조사됐다. 먼저 breach-update로 갱신할까?" 사용자가 그냥 진행하라면 진행하고 보고서에 기준일을 적는다.
- 이전 보고서가 있으면 맨 위 메타의 `catalog_version`과 '열린 지적' 목록을 읽는다. 모드를 정한다.
  - **증분 점검**(기본, 이전 보고서가 있고 사용자가 전체를 원하지 않을 때): `--since <이전 catalog_version>` 항목 + 이전 보고서의 FAIL·PARTIAL 재확인.
  - **전체 점검**: 이전 보고서가 없거나, 카탈로그 major 버전이 바뀌었거나, 사용자가 원할 때.

### 2. 대상 스택 추정

```bash
python3 <skill>/scripts/catalog.py profile
```

태그(node, python, github-actions, aws, firebase, supabase, llm-app, mcp, ai-agent-config …)를 보여 주고 바로 진행한다. 빠진 스택을 사용자가 말하면 `--tags`에 더한다. 모노레포면 하위 앱마다 `--root`를 바꿔 돌린다.

### 3. 항목 뽑기와 신호 스캔

```bash
python3 <skill>/scripts/catalog.py list-checks --tags auto [--since X.Y.Z]
python3 <skill>/scripts/catalog.py scan --tags auto [--since X.Y.Z]
```

`list-checks`는 심각도 순 항목과 확인 방법을, `scan`은 항목별로 "여기를 읽어라" 후보(파일·패턴 매치)를 준다.

### 4. 항목별 판정

항목마다 `how_to_check`를 따라 실제 파일을 읽고 아래 다섯 중 하나로 판정한다. **근거 없는 판정은 쓰지 않는다.**

| 판정 | 뜻 | 근거 |
|---|---|---|
| `FAIL` | 사고와 같은 경로가 열려 있다 | `파일:줄` 인용 필수 |
| `PARTIAL` | 일부만 막혀 있다(예: 키 로테이션은 있으나 퇴사자 폐기 절차 없음) | 막힌 곳·열린 곳 각각 인용 |
| `PASS` | `pass_criteria`를 만족한다 | 만족을 보여 주는 `파일:줄` |
| `MANUAL` | 저장소만으로 판단 불가(조직 절차, 운영 설정, 클라우드 콘솔) | 사용자·조직에 물을 질문 한 줄 |
| `N/A` | 이 시스템에 해당 구성요소가 없다 | 없다는 근거(예: 매니페스트에 SDK 없음) |

- `method: process` 항목은 대개 `MANUAL`이다. 질문을 구체적으로 쓴다. ❌ "헬프데스크 보안 확인" ✅ "전화로 MFA 재설정을 요청받으면 본인 확인을 어떤 수단으로 하나? 콜백 번호는 사내 디렉터리에서 가져오나?"
- 심각도는 카탈로그 값을 출발점으로, 이 시스템의 노출 정도로 한 단계 올리거나 내릴 수 있다. 바꾸면 이유를 한 줄 적는다.
- 항목이 30개 넘거나 저장소가 크면 카테고리별로 서브에이전트에 나눠 맡긴다. 각 서브에이전트에는 해당 항목의 JSON(`list-checks --category X --format json`), 이 '판정' 표, 안전 규칙을 그대로 넘기고, 판정·근거 인용·질문만 돌려받는다.

### 5. 보고서

`references/report-template.md` 형식으로 `docs/security/breach-audit/YYYY-MM-DD.md`에 쓴다. 맨 위 메타에 **catalog_version, 모드, 스택 태그, 기준일**을 반드시 넣는다. 다음 증분 점검이 이 값을 읽는다.

- 저장소에 쓰기만 하고 커밋하지 않는다. 공개 저장소면 보고서가 공격 지도가 될 수 있으니 커밋 전에 사용자에게 확인을 받으라고 알린다.
- 대화 답변은 FAIL 중 critical·high 상위 3개와 보고서 경로만. 나머지는 보고서에 있다고 말한다.
- 사람이 읽을 문서(HTML)가 필요하면 breach-report 스킬로 같은 이름의 `.html`을 만든다. .md는 다음 점검이 읽는 원본이라 그대로 둔다.

## 판정할 때 흔한 실수

- **설정 파일만 보고 PASS.** 예: `firestore.rules`가 있어도 `allow read, write: if true`면 FAIL이다. 규칙 본문까지 읽는다.
- **lockfile 없음을 놓침.** 의존성 핀이 없으면 공급망 항목 대부분이 PARTIAL 이하다.
- **AI 에이전트 설정을 코드가 아니라고 건너뜀.** `.mcp.json`, `.claude/settings.json`, `.cursor/`, `AGENTS.md`도 점검 대상이다. 최근 공급망 사고는 이 파일들을 노렸다.
- **도구 기본값을 버전 확인 없이 가정함.** 예: pnpm 10+는 install 스크립트를 기본 차단하지만 pnpm 8·9와 npm은 실행한다. 패키지 관리자·런타임 버전(`pnpm -v`, lockfileVersion, Dockerfile FROM)을 먼저 본다.
- **권한을 무엇으로 판정하는지 안 봄.** 관리자 여부가 이메일·닉네임처럼 바뀌거나 외부 제공자가 넣어 주는 값으로 정해지면, 그 값이 들어오는 모든 경로(소셜 로그인, 이메일 변경)를 따라간다.
- **조건부 결함을 PASS나 FAIL로 뭉갬.** "운영 DB에 X가 없으면 열린다"처럼 저장소로 확정 못 하면 PARTIAL로 두고 조건을 적고, 확인 질문을 MANUAL에 넣는다.
- **scan 잡음에 끌려감.** lockfile과 테스트 경로는 기본으로 패턴 스캔에서 빠진다(`--include-tests`로 포함). 서드파티 스킬·벤더 스크립트에서 나온 매치는 판정 대상 코드가 아니면 넘긴다.
- **카탈로그에 없는 문제를 지어냄.** 점검 중 카탈로그 밖의 위험을 발견하면 보고서 '카탈로그 밖 관찰'에 따로 적고, breach-update 때 항목 후보로 쓰라고 남긴다. FAIL 목록에 섞지 않는다.
