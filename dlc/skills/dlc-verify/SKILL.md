# dlc-verify — 검증

생명주기의 마지막 스테이지다. 구현이 요구사항을 만족하는지 네 가지로 확인한다 — 전체 테스트, 커버리지 기준, 추적성, 코드 리뷰 — 그리고 판정을 적는다. 질문 파일이 없는 스테이지다. 리뷰 중에는 코드를 고치지 않는다. 고칠 것이 나오면 먼저 판정에 적고, 고치는 것은 반려 뒤 사용자 결정으로만 한다.

공통 절차는 [../dlc/references/protocol.md](../dlc/references/protocol.md), 출처 규칙과 ID 형식은 [../dlc/references/grounding.md](../dlc/references/grounding.md)에 있다. 스크립트 위치 `${CLAUDE_PLUGIN_ROOT}/skills/dlc/scripts/dlc.py`의 뜻은 protocol.md의 "스크립트 위치" 절을 따른다. protocol.md의 4~7단계(질문·답변·요약 확인)는 이 단계에 없다. 아래는 이 단계에서만 다른 것이다.

## 읽을 것

- `requirements.md`. FR마다 있는 `수용 기준` 줄이 통과·실패의 기준이다.
- `plan.md`의 `## 완료 정의`·`## Seam과 테스트 예산`. 실행 명령과 예산은 여기서 가져온다.
- `units.md`와 `build/*.md` 전부. 변경 파일 목록이 리뷰 범위, 추적성 표가 추적성 검사의 입력이다.
- `design.md`·`decisions.md`(full). 구현이 컴포넌트 경계·엔티티 소유권·ADR을 지켰는지 본다.
- `docs/dlc/practices.md`의 `## 테스트`(커버리지 목표, 실행 명령)·`## 코드 스타일`(린터, 크기 제한, 금지 패턴). 리뷰의 `[practice]` 기준이다. express·bugfix에는 없을 수 있다. 그때는 plan.md의 실행 명령과 저장소의 린터 설정을 쓴다.

## 순서

1. **전체 테스트.** practices.md 또는 plan.md의 실행 명령으로 전체 스위트를 한 번 돌린다. 명령과 결과(통과·실패·건너뜀 수, 실패한 테스트 이름)를 그대로 기록한다. 실패가 있어도 여기서 고치지 않는다.
2. **커버리지 기준.** practices.md에 커버리지 목표가 있으면 프로젝트의 커버리지 도구로 측정해 비교한다. **기준을 통과시키려고 목표를 낮추거나 파일을 제외하지 않는다.** 도구가 없으면 측정하지 않았다고 적고 가정 절에 남긴다. 목표가 없으면 "기준 없음 [practice]"로 적는다.
3. **추적성.** `dlc.py check build`를 다시 돌려 모든 최상위 FR/NFR이 어느 유닛의 추적성에든 있는지 확인한다. 그 다음 FR마다 수용 기준 한 줄과 그것을 확인하는 테스트 이름(또는 수동 확인 결과)을 표로 잇는다. 수용 기준 열은 requirements.md의 문장을 그대로 옮긴다. 다시 쓰지 않는다. 테스트가 수용 기준의 예시값과 다른 픽스처를 썼으면 확인 열에 그 사실을 적고, 기준의 판정 조건(형식·종료 코드 등)을 여전히 검증하는지 본다. 검증하지 않으면 미확인이다. 테스트가 아니라 `[assumption]`으로만 대응된 요구사항도 "미확인"으로 적는다.
4. **리뷰.** `build/*.md`의 변경 파일을 전부 읽는다. 지적마다 파일과 줄, 근거(코드 인용 또는 practices.md·design.md의 규칙)를 단다. 인용할 수 없는 지적은 내지 않는다. 심각도는 아래 표. 리뷰 관점: (a) 수용 기준과 다른 동작, (b) 계약(units.md)과 다른 시그니처·경로·페이로드, (c) 엔티티 소유권·ADR 위반(full), (d) 테스트가 구현 세부에 결합됐거나 기대값을 재계산하는 경우, (e) practices.md의 코드 스타일 위반, (f) 보안·데이터 손상 가능성.
5. **판정.** 아래 규칙으로 하나를 고른다. 판정이 `반려`면 승인 게이트로 가지 않는다.
6. **승인 게이트.** protocol.md 10단계. 요약에는 테스트 결과 한 줄, 커버리지 한 줄, 추적성 미확인 수, 리뷰 발견의 심각도별 수, 판정을 넣는다.

| 심각도 | 뜻 | 예 |
|---|---|---|
| P1 | 꼭 반영해야 한다 | 수용 기준 불일치, 데이터 손상·크래시 유발 로직, 명확한 보안 취약점 |
| P2 | 적극적으로 고려해야 한다 | 계약 불일치, 동시성 문제, 소유권·ADR 위반, 팀이 강제하는 관행 위반 |
| P3 | 웬만하면 반영한다 | 가독성·유지보수에 실질 영향이 있는 개선, 구현 세부에 결합된 테스트 |
| P4 | 반영해도 좋고 넘어가도 좋다 | 경미한 스타일 |
| P5 | 사소한 의견 | 취향 |

**판정 규칙**

| 판정 | 조건 |
|---|---|
| 승인 | 전체 테스트 GREEN, 커버리지 기준 충족(또는 기준 없음), 추적성 미확인 0, P1 0건 |
| 조건부 승인 | 위와 같되 P2가 있거나, 추적성 미확인이 있거나, 커버리지 목표는 있는데 도구가 없어 측정하지 못했고, 사용자가 그것을 알고 받아들였다. 받아들인 항목을 판정 절에 나열한다 |
| 반려 | 테스트 실패, 커버리지 기준 미달, P1 1건 이상 중 하나라도 |

반려면 사용자에게 무엇이 걸렸는지 보이고 결정을 받는다. (a) 이 세션에서 고친다 — dlc-build의 "유닛 하나의 순서" 2~5단계(seam에서 red 확인 → green → 린터·전체 실행)로 고치고, 고친 유닛의 `build/<unit>.md`를 갱신하고 `dlc.py note verify "<무엇을 고쳤는가>"`로 남긴 뒤 1부터 다시 한다. (b) 멈춘다 — verify는 `active`로 남는다. 다음 세션에서는 `dlc.py start verify`를 다시 실행하지 않고 `dlc.py note verify "재개"`로 기록한 뒤 1부터 다시 한다. 어느 쪽이든 verify.md는 마지막 실행 결과로 덮어쓴다. 이전 실행에서 찾아 고친 발견은 리뷰 발견 표에서 빼고, 판정 절에 note 시각으로만 언급한다. 표의 심각도별 수와 판정의 수가 같아야 한다.

**PR을 올렸다면.** 저장소가 GitHub이고 사용자가 이 작업의 PR을 이미 만들었으면, `pr-reviewer` 스킬(설치돼 있으면)로 같은 발견을 PR 코멘트로 남길 수 있다고 한 번 안내한다. 이 스킬이 대신 부르지 않고, PR을 만들지도 않는다.

## 산출물 골격

### verify.md

```markdown
# 검증

## 테스트 결과
- 실행: `python3 -m pytest -q` → 12 passed, 0 failed. [code:tests/]
- 린터: `ruff check .` → 이상 없음. [practice]
- 커버리지: 새 코드 91% (기준 80%, `pytest --cov`). [practice]
- 실제 인프라 테스트: 0건 (예산 0). [practice]

## 추적성
`dlc.py check build`: OK.

| 요구사항 | 수용 기준 | 확인 | 결과 | 출처 |
|---|---|---|---|---|
| FR1 | 존재하는 SKU는 200과 수량, 없으면 404 | `test_returns_total_for_existing_sku`, `test_unknown_sku_is_404` | 통과 | [code:tests/inventory/test_stock_query.py] |
| FR2 | 조회 1건마다 이력 1행 | `test_logs_one_row_per_query` | 통과 | [code:tests/audit/test_log.py] |
| NFR1 | p95 300ms (100 rps) | 수동 측정 없음 | 미확인 | [assumption] |

## 리뷰 발견
| 번호 | 심각도 | 파일:줄 | 지적 | 근거 | 권장 |
|---|---|---|---|---|---|
| 1 | P2 | `src/inventory/stock_query.py:41` | 404 응답 본문이 계약의 `{error}` 형식이 아니다 | units.md 계약 표 "재고 조회" 행 / 코드 `return None` | 계약대로 `{"error": "not found"}` 반환 |
| 2 | P4 | `tests/inventory/test_stock_query.py:12` | 픽스처 이름이 practices.md 네이밍(snake_case)과 다르다 | practices.md 코드 스타일 표 "네이밍" 행 | 이름 변경 |

## 판정
조건부 승인. P2 1건(404 본문 형식)은 사용자가 후속 작업으로 미루기로 했다(log.md note 2026-09-13T03:10:22Z). NFR1은 미확인으로 남긴다.

## 가정과 열린 질문
- NFR1 부하 측정은 staging 배포 뒤 별도 작업으로 한다. [assumption]
```

- `## 리뷰 발견`에 지적이 없으면 표 대신 "없음. 검토 범위: <파일 수>개 파일, 관점 (a)~(f)."라고 적는다. 빈 표를 두지 않는다.
- `## 판정` 첫 단어는 `승인`, `조건부 승인`, `반려` 중 하나다. `dlc.py check verify`가 이 첫 단어를 보며 `반려`면 실패로 처리한다. 조건부 승인이면 받아들인 항목을 나열한다.
- `## 판정`의 근거는 위 세 절이므로 출처 태그를 달지 않는다. 사용자가 채팅으로 내린 결정(조건부 승인 수락 등)은 `dlc.py note verify`로 log.md에 남기고 판정 절에서 그 note의 시각을 적는다.

## 완료 기준

- `dlc.py check verify`가 OK: 필수 절 다섯, requirements.md에 없는 ID 참조 없음, 판정 첫 단어가 `승인` 또는 `조건부 승인`, 가정 절.
- 판정이 `승인` 또는 `조건부 승인`이다. `반려`는 승인 게이트로 가지 않는다.
- 사용자가 승인 게이트에서 승인했다(protocol.md 10단계). 승인 뒤 `dlc.py approve verify`. approve 출력이 `다음: done`이면 작업이 끝났다고 알린다.

## 출력 언어

사용자 대면 출력과 산출물은 한국어. 코드, 식별자, 경로, 명령, 테스트 이름은 원문 유지.
