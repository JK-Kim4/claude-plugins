# dlc-requirements — 요구사항 분석

뒤 단계(설계·계획·구현·검증)가 가리킬 요구사항 ID를 확정한다. 산출물 `requirements.md`의 `FR<n>`·`NFR<n>`은 이후 이름을 바꾸거나 다시 번호를 매기지 않는다.

공통 절차는 [../dlc/references/protocol.md](../dlc/references/protocol.md), 출처 규칙과 ID 형식은 [../dlc/references/grounding.md](../dlc/references/grounding.md)에 있다. 스크립트 위치 `${CLAUDE_PLUGIN_ROOT}/skills/dlc/scripts/dlc.py`의 뜻은 protocol.md의 "스크립트 위치" 절을 따른다. 아래는 이 단계에서만 다른 것이다.

## 읽을 것

- `state.md`의 `description`(`[desc]` 출처)과 `profile`·`depth`.
- `intent.md`(full 프로파일). 문제·대상·범위 밖은 여기서 가져오고 다시 묻지 않는다.
- `docs/dlc/practices.md`·`docs/dlc/codebase.md`(있으면). 기술 제약과 테스트 기준의 `[practice]` 출처다.

## 질문 주제 — 여섯 차원

depth minimal(express·bugfix)은 2~4개, standard(full)는 5~8개. 앞 산출물에서 답이 나오는 차원은 묻지 않는다.

| 차원 | 묻는 것 | minimal 우선순위 |
|---|---|---|
| 기능 | 무엇을 하는가. 주 흐름과 예외 흐름. 입력·출력 | 1 |
| 시나리오 | 대표 사용자 여정 하나. 실패·경계 상황에서 어떻게 되어야 하는가 | 2 |
| 기술 | 붙는 지점(기존 API·DB·외부 시스템), 다루는 데이터 | 3 |
| 품질 | 무엇이 되면 완료인가(수용 기준). 어떤 테스트가 있어야 하는가 | 4 |
| 비기능 | 성능·보안·가용성·호환 중 이번에 중요한 것과 그 수치 | standard |
| 비즈니스 | 우선순위(빠져도 되는 것), 성공 조건, 일정·정책 제약 | standard |

minimal이면 우선순위 1~4 차원에서 빈 것만 묻는다. standard면 여섯 차원에 각 1개 이상을 두되 앞 산출물이 답한 것은 뺀다.

**bugfix 프로파일**이면 차원 대신 다음 주제로 바꾼다. 순서대로 빈 것만 묻는다.

| 순위 | 주제 |
|---|---|
| 1 | 재현 조건: 환경, 입력, 순서, 빈도(항상·간헐) |
| 2 | 기대 동작과 실제 동작의 차이 |
| 3 | 영향 범위: 누가·어느 기능이 영향받는가, 데이터 손상 여부 |
| 4 | 회귀 테스트: 어느 수준(단위·통합)에 어떤 테스트가 이 결함을 잡아야 하는가 |
| 5 | 근본 원인 가설(있으면). 없으면 묻지 않는다 |

질문 파일은 작업 폴더의 `requirements-questions.md`. 형식과 답변 검사는 protocol.md.

## 답변 검사에서 이 단계가 더 보는 것

protocol.md 6단계(모호어·모순·한 단어 답변)에 더해:

- **과신.** "항상", "절대", "모든 경우"처럼 단정하는 답에 근거가 없으면 "예외가 있을 수 있는 상황은 무엇인가요?"를 후속 질문으로 묻는다.
- **수치 없는 비기능.** "빨라야 한다", "안전해야 한다"는 목표값과 측정 방법을 받는다.
- **범위 충돌.** 답이 `intent.md`의 `### 밖`에 있는 항목을 요구하면 사용자에게 알리고 어느 쪽을 따를지 확인한다. 조용히 한쪽을 고르지 않는다.

## 산출물 골격

### requirements.md

```markdown
# 요구사항

## 의도 요약
무엇을 왜 만드는지 2~3문장. full이면 intent.md 요약, 아니면 description 기반. [desc]

## 기능 요구사항

### FR1. SKU 단위 재고 조회 [Q1]
- FR1.1 SKU 하나의 현재 수량을 돌려준다.
- FR1.2 창고별 수량을 분리해 돌려준다. [Q2]
- 수용 기준: 존재하는 SKU를 조회하면 200과 수량, 없으면 404.

### FR2. 조회 이력 기록 [Q3]
- FR2.1 조회 시각과 호출 주체를 남긴다.
- 수용 기준: 조회 1건마다 이력 1행.

## 비기능 요구사항

### NFR1. 응답 시간 [Q4]
- 조회 API p95 300ms 이하. 측정: 부하 테스트 100 rps.

## 제약
| 항목 | 내용 | 출처 |
|---|---|---|
| 데이터베이스 | 기존 PostgreSQL 인스턴스를 공유한다 | [practice] |
| 인증 | 사내 SSO 토큰만 받는다 | [Q1] |

## 범위 밖
- 입출고 등록. ERP가 담당한다. [desc]

## 가정과 열린 질문
- 창고는 최대 20개로 가정한다. [assumption]
```

- `FR<n>`·`NFR<n>`은 1부터 연속, 하위는 `FR<n>.<m>`. 정의는 `## 기능 요구사항`·`## 비기능 요구사항` 절 안에서만 한다(grounding.md). `## 범위 밖`에서 번호를 새로 쓰지 않는다.
- FR마다 `수용 기준` 한 줄 이상. 검증 단계가 이 줄로 통과·실패를 판정한다.
- 비기능 요구사항이 정말 없으면 절은 두고 본문에 `해당 없음. [Q<n>]`처럼 근거를 단다.
- **bugfix**는 같은 골격에 내용만 달라진다. `## 의도 요약`에 재현 조건과 실제 동작을 적고, FR1은 기대 동작, FR2는 회귀 테스트가 잡아야 하는 것, NFR은 영향 범위에서 나온 것(데이터 정합성 등)으로 쓴다.

## 완료 기준

- `dlc.py check requirements`가 OK: 필수 절 여섯 개, FR/NFR 번호 연속, 질문 파일의 모든 답변과 `Looks correct`, 가정 절.
- 모든 FR에 수용 기준이 있고, 모든 실질 문단·표 행에 출처 태그가 있다.
- 사용자가 승인 게이트에서 승인했다(protocol.md 10단계). 승인 뒤 `dlc.py approve requirements`.

## 출력 언어

사용자 대면 출력과 산출물은 한국어. 코드, 식별자, 경로, 명령은 원문 유지.
