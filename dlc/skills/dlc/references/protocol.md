# 스테이지 공통 절차

모든 `dlc-*` 스테이지 스킬이 따르는 한 벌의 절차다. 스테이지 스킬은 자기 단계의 질문 주제와 산출물 골격만 갖고, 순서와 게이트는 여기서 가져온다.

## 스크립트 위치

상태 전이와 검사는 `<skills>/dlc/scripts/dlc.py`가 맡는다. `<skills>`는 스킬이 로드될 때 보인 스킬 디렉터리의 부모다(Claude Code 플러그인이면 `<plugin>/skills`, `npx skills add`면 `.agents/skills`). 스킬 디렉터리가 형제로 설치되므로 스테이지 스킬 안에서는 `../dlc/scripts/dlc.py`와 같은 파일이다. 항상 프로젝트 루트에서 실행한다.

```bash
python3 <skills>/dlc/scripts/dlc.py next
```

python3는 3.9 이상이어야 한다. 스크립트가 없거나 python3가 없으면 이 문서 끝의 **수동 체크리스트**로 같은 규율을 지킨다.

## 한 스테이지의 순서

1. **위치 확인.** `dlc.py next`를 실행한다. 출력의 첫 단어가 지금 스테이지와 다르면 멈추고 사용자에게 알린다. 앞 단계 산출물이 없는 채로 진행하지 않는다. 예외 하나: 사용자가 `dlc-analyze`를 명시 호출했는데 `next`가 지문 일치로 analyze를 건너뛴 경우, 2단계에서 `dlc.py start analyze --force`를 쓴다.
2. **시작 기록.** `dlc.py start <stage>`.
3. **문맥 읽기.** `state.md`의 depth와 workspace, 앞 단계 산출물, 그리고 프로젝트 공유 산출물(`docs/dlc/codebase.md`, `docs/dlc/practices.md`)이 있으면 읽는다. 앞 단계에서 이미 답한 것은 다시 묻지 않는다.
4. **질문 파일.** 빈 곳을 찾아 `<stage>-questions.md`를 쓴다(형식은 아래). depth가 minimal이면 2~4개, standard면 5~8개가 기준이다. 답이 앞 단계에서 유추되면 묻지 않는다. 질문이 하나도 필요 없으면 파일을 만들지 않는다.
5. **답변 수집.** 사용자가 고르게 한다. (a) 채팅으로 하나씩, 한 번에 최대 4개씩 묻는다. (b) 사용자가 파일을 직접 고치고 "done"이라고 한다. 어느 쪽이든 답은 파일에 기록한다. 파일이 진실이다.
6. **답변 검사.** 모호어("아마", "상황에 따라", "적당히", "알아서"), 답변 간 모순(범위 대 단순성, 위험 대 민감 데이터, 기술 충돌), 한 단어 답변을 찾는다. 걸리면 후속 질문 `Q<n+1>`을 파일에 추가하고 5로 돌아간다. "알아서 해주세요"에는 "어떤 결과가 가장 중요한가요?"로 되묻는다.
7. **요약 확인.** 답을 불릿으로 요약해 파일 끝의 `## Consolidated Summary Confirmation`에 쓰고, 사용자에게 "이대로 맞습니까?"를 묻는다. 답이 정확히 `Looks correct`가 될 때까지 산출물을 쓰지 않는다. `Request changes`면 "무엇을 바꿀까요?"를 묻고 5로 돌아간다.
8. **산출물 작성.** 스테이지 스킬의 골격대로 쓴다. 출처 태그 규칙은 `grounding.md`.
9. **검사.** `dlc.py check <stage>`. 실패 항목을 고치고 다시 검사한다. 통과할 때까지 게이트로 가지 않는다.
10. **승인 게이트.** 사용자에게 (a) 산출물 경로, (b) 3~6줄 요약, (c) 검사 결과, (d) 남은 가정 목록을 보이고 "승인 / 수정 요청" 중 고르게 한다. 승인이면 `dlc.py approve <stage> --note "<사용자 말 그대로>"`. 수정 요청이면 내용을 `dlc.py note <stage> "<요청>"`으로 기록하고 8로 돌아간다.
11. **다음 안내.** approve 출력의 "다음:" 줄을 사용자에게 그대로 전한다. 다음 스킬을 스스로 실행하지 않는다. 라우터가 `--all`로 돌고 있을 때만 이어간다.

## 질문 파일 형식

```markdown
## Q1. 재고 API를 호출하는 주체는 누구입니까?
사용 주체에 따라 인증 방식과 권한 모델이 달라집니다.
A. 사내 관리 화면만
B. 외부 파트너 시스템
C. 최종 고객 앱
X. Other (please specify)

[Answer]:

## Consolidated Summary Confirmation
- (답변 요약 불릿)

- Looks correct
- Request changes

[Answer]:
```

- 제목은 `## Q<n>.`으로 시작하고 번호는 1부터 연속이다. 질문마다 `[Answer]:` 행이 하나 있어야 하며 `dlc.py check`가 행의 존재·답변 값·번호 연속을 본다.
- 질문은 스스로 설명해야 한다. "FR3이 맞나요?"처럼 식별자만 던지지 않는다. 이유가 자명하지 않으면 한 줄 맥락을 붙인다.
- 선택지는 A~E, 마지막은 항상 `X. Other (please specify)`. 답은 `[Answer]: B` 또는 `[Answer]: X - <자유 서술>`.
- 요약 확인 항목만 글자 접두 없이 `Looks correct` / `Request changes`를 쓴다. `[Answer]: Looks correct`가 정확한 문자열이어야 한다.

## 승인 게이트에서 하지 않는 것

- 침묵을 승인으로 치지 않는다.
- 승인 전에 다음 스테이지 산출물을 미리 쓰지 않는다.
- `state.md`를 편집기로 고치지 않는다. 전이는 `dlc.py`만 한다.
- 한 스테이지에서 받은 "알아서 진행해"를 다음 스테이지로 가져가지 않는다. 자율 허가는 그 스테이지 한 번에만 유효하다.

## 수동 체크리스트 (스크립트가 없을 때)

- `docs/dlc/active`의 작업 폴더에서 `state.md`를 읽어 done/skipped가 아닌 첫 스테이지가 지금 스테이지인지 확인한다.
- 산출물의 필수 절(스테이지 스킬에 적힌 H2 목록)이 모두 있고 `## 가정과 열린 질문`이 비어 있지 않은지 본다.
- 질문 파일의 모든 `[Answer]:`가 채워졌고 요약 확인이 `Looks correct`인지 본다.
- 요구사항 ID가 1부터 연속인지, 설계·계획이 존재하지 않는 ID를 참조하지 않는지 본다.
- 승인 뒤 `state.md`의 해당 행을 `done`으로, `log.md`에 한 줄을 추가한다. 이 경우에만 손으로 고친다.
