# 인터뷰 — 질문과 판단 기준

조사(1단계) 결과를 손에 쥐고 물어야 한다. 실측값 없이 던지는 질문은 답이 안 나온다.
한 번에 하나씩, 추천을 붙여서.

---

## Q1. 어떤 저장소를 통합하는가

조사에서 찾은 후보를 규모와 함께 보여주고 고르게 한다.

**주의할 것 하나 — 소유권이 다른 문서가 섞이는 경우.** 회사 업무 문서와 개인 프로젝트
문서를 한 저장소에 합치면 나중에 원격 저장소를 어디에 둘지가 곤란해진다. 조사 단계에서
`git remote -v`로 출처가 갈리는지 확인하고, 갈리면 이 질문에서 명시적으로 짚는다.
사용자가 알고 합치는 것과 모르고 합치는 것은 다르다.

**소유권이 갈리는데도 통합을 택했다면** — 원격 전략은 이 자리에서 정하지 않는다.
로컬 `git init` 후 원격은 언제든 붙일 수 있어 미루는 비용이 0이다. 결정 목록을
불필요하게 늘리지 않는다.

## Q2. 루트를 어디에 둘 것인가

**추천: 홈 아래 짧고 도구 중립적인 이름** — `~/knowledge`, `~/wiki`.

근거:
- 스크립트와 스킬에 절대 경로가 박히므로 짧을수록 좋다
- `~/obsidian/` 아래에 두면 특정 앱이 소유하는 것처럼 읽힌다. 마크다운은 어느 도구로든 열린다
- 코드 저장소 계층(`~/dev`, `~/workspaces`) 아래는 부적절하다 — 지식베이스는 코드 저장소가 아니다

**기존 저장소 하나를 승격시키는 것은 비추천.** 이름이 "여럿 중 하나"를 암시하고,
그 저장소의 기존 구조가 통합 루트의 구조를 왜곡한다.

## Q3. 링크 문법을 통일할 것인가

조사에서 나온 wikilink / 마크다운 링크 파일 수를 붙여서 묻는다.

**추천: 마크다운 경로 링크로 통일.**

근거 — 취향이 아니라 정확성 문제다:
- `[[이름]]`은 **트리 전체에서 파일명으로** 해석된다. 여러 저장소를 합치면 같은 이름의
  파일(`00-INDEX.md`, `README.md`)이 여러 개 생겨 해석이 모호해진다
- 마크다운 경로 링크는 어디서나 동작하고, 링크 그래프를 추출할 때 경로가 확정적이다
- "Obsidian 때문에 wikilink"라는 논거는 확인이 필요하다. `.obsidian/`이 실제로 어느
  저장소에 있는지 보라 — Obsidian으로 여는 vault가 오히려 마크다운 링크를 쓰고 있을 수 있다

**"혼용 허용"도 진짜 선택지다.** 비용은 백링크를 찾을 때 패턴 두 개를 봐야 하는 것뿐이고,
이관 중에 파일 내용을 건드리지 않는다는 이점이 있다. 변환 대상이 수백 개라면 진지하게 고려한다.

## Q4. 지식 층을 몇 개로 시작할 것인가

**추천: 확정 지식 한 층(`knowledge/`)으로 시작하고 나머지는 필요할 때 만든다.**

근거:
- 3계층을 미리 깔면 대개 빈 폴더로 남는다. 실제 사례에서 몇 주 뒤 `articles/` 0개,
  `research/` 1개였다
- 폴더는 나중에 추가해도 비용이 0이다. 미리 만드는 건 요청하지 않은 구조를 짓는 것이다
- "아직 확정 아님"은 디렉터리가 아니라 `status: provisional` 프론트매터가 나른다

**이미 내용이 있으면 그 폴더는 만든다.** 외부 원문 6개가 있는데 `sources/`를 안 만들
이유는 없다. 규칙은 "미리 만들지 않는다"이지 "만들지 않는다"가 아니다.

## Q5. 프론트매터를 어디까지 강제할 것인가

조사에서 나온 보유율을 붙여서 묻는다.

**추천: 신규 문서만 — 템플릿으로 자연히 갖추게 한다.**

근거:
- 프론트매터의 값어치는 필터링(`status:`, `tags:`)인데, 초기에 필요한 건 검색이고
  그건 본문으로 충분하다
- 백필은 LLM이 문서마다 본문을 읽고 제목·요약을 생성해야 해서 비용이 실질적이다
- 필터가 실제로 아쉬워졌을 때 하면 된다. 그때는 무엇이 필요한지도 더 명확해진다

**사용자가 전면 백필을 택하면** 규모를 정직하게 알린다. 수백 건이면 한 세션에 안 끝나므로
청크로 나누고 진행 상태를 파일로 남기는 방식이 필요하다.

## Q6. 세션 기록을 원료로 쓸 것인가

`~/.claude/projects/`나 `~/.codex/sessions/`에 대화 로그가 있으면 묻는다.

**쓴다면 반드시 짚을 것 — 보존 정책.** Claude Code는 기본 30일이 지나면 세션을 지운다.
`raw/`로 확보하지 않으면 원료가 조용히 사라진다. 이미 가공된 문서가 있고 그 문서가
원본 경로를 기록하고 있다면, **이관 전에 원본이 아직 살아 있는지 확인하고 확보한다.**

수집 스크립트가 이미 있다면 **범위를 확인한다.** 한 프로젝트만 수집하도록 필터가 걸려
있는 경우가 흔한데, 프로젝트를 가로지르는 지식베이스에서는 그게 곧 누락이다.

## Q7. 대용량 원본의 git 처리

세션 JSONL 같은 대용량 원본이 이미 git 이력에 들어가 있으면 묻는다.

**추천: 새 저장소로 fresh init.** 원격이 없다면 지금이 가장 싼 시점이다. 원격에 올라간
뒤에는 강제 푸시와 협업자 동기화 문제가 붙는다.

보존할 커밋이 많다면 `git filter-repo`가 대안이지만, 커밋이 몇 개뿐이라면 이력 가치보다
저장소 크기 비용이 크다.

**어느 쪽이든 `.gitignore`를 먼저 쓰고 `git init`을 한다.** 순서가 바뀌면 첫 커밋에
대용량이 들어간다.
