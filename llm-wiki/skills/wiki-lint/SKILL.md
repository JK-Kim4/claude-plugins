# wiki-lint

Karpathy 원문의 세 연산 Ingest · Query · Lint 중 **Lint**. 지식베이스는 쓸수록 링크가
끊기고, 아무도 안 읽는 문서가 쌓이고, 한때 맞았던 서술이 조용히 틀려진다. 이 스킬은
그걸 찾는다.

**낡음 판정이 여기 있는 이유** — 원문도 Lint 를 "새 소스가 밀어낸 낡은 서술
(stale claims)"을 찾는 자리로 둔다. 조회(`wiki-recall`)는 위키 안에서 끝내고 판정을
이쪽으로 넘긴다. 아래 3번이 문서에 덧붙이는 `→ YYYY-MM-DD 확인:` 주석이 그다음
조회의 근거가 된다 — 검증 비용은 여기서 한 번만 치른다.

**핵심 원칙: 스크립트는 좁히고, 판정은 LLM 이 한다.** 수백~수천 건 규모에서 전량을
LLM 이 읽는 방식은 성립하지 않는다. 기계로 후보를 줄인 다음, 줄어든 것만 읽는다.

**경계** — 문서를 새로 쓰거나 세션을 가공하지 않는다. 그건 `wiki-digest` 다.
링크 파싱·해석도 여기서 구현하지 않는다. `wiki-bootstrap` 의 `survey.py`·
`wikilink_convert.py` 를 그대로 가져다 쓴다. 두 벌이 되면 어느 숫자가 맞는지 알 수 없다.

판정 기준은 `references/judgment.md` 를 읽는다.

## 한 번에 보기 — 어느 디렉터리에서 실행해도 된다

```bash
python3 <skill>/scripts/lint.py                 # 루트는 설정에서
python3 <skill>/scripts/lint.py <위키루트>       # 직접 지정
```

**위키 루트는 인자가 없으면 설정(`~/.config/llm-wiki/config.json` 의 `root`)에서
얻는다.** 없으면 알려주고 멈춘다.

점검 4종의 요약이 나온다. 각 항목은 `--check <이름>` 으로 상세를 본다
(`links` · `orphans` · `pending` · `stale`). `--json out.json` 은 판정용 원자료다.

## 1. 깨진 링크 — 세는 것과 고칠 수 있는 것은 다르다

`survey.py` 는 이미 깨진 링크를 센다. 여기서 더하는 건 **복구 가능성 분류**다.

| 분류 | 뜻 | 처리 |
|---|---|---|
| 복구 가능 | 대상이 하나로 특정됨 | `--apply` 로 일괄 수정 |
| 모호 | 같은 이름 후보가 여럿 | 사람이 고른다 |
| 대상 없음 | 트리에 없음 | **고치지 않는다** |
| 불변 영역 | 아카이브·`sources/`·`raw/` 출발 | **손대지 않는다** |

```bash
python3 <skill>/scripts/lint.py <루트> --check links           # 건식 — 무엇을 바꿀지
python3 <skill>/scripts/lint.py <루트> --check links --apply   # 적용
```

**"대상 없음"은 결함이 아니라 정보다.** 없는 문서를 가리키는 링크는 "여기에 문서가
있어야 한다"는 표시고, 지우면 그 정보까지 지운다. 대개는 위키 밖 코드 저장소를
가리키는 것이라 애초에 고칠 대상이 아니다. **0 을 목표로 삼지 않는다.**

**불변 영역은 절대 자동 수정하지 않는다.** 이유가 둘 다 실측으로 확인됐다 —
아카이브 스냅샷의 내부 링크를 현행 문서로 갈아끼우면 스냅샷이 옛 상태의 기록이
아니게 되고, `sources/` 의 원문은 링크가 **원본 저장소 기준**으로 쓰여 있어 위키
안에서 같은 이름을 찾아 이으면 엉뚱한 프로젝트 문서로 연결된다.

적용 후 `survey.py` 로 깨진 링크가 실제로 그만큼 줄었는지 대조한다.

## 2. 고아 문서 — 발견은 목록이 아니라 디렉터리다

피참조 0건인 문서를 찾되, **링크로 도달하지 않는 게 정상인 것은 뺀다.**

- 세션 문서·템플릿 — 날짜와 검색으로 도달한다. 링크 대상이 아니다.
- 아카이브(`_archive/`·`archive/`) — 안 걸리는 게 목적이다.
- 진입점 파일(`00-INDEX.md`·`README.md`·`00-STATUS.md`) — 링크의 출발지다.

이걸 안 빼면 고아 목록이 전체의 40% 가 되고, 그러면 아무도 안 본다.

**개별 파일을 나열하기 전에 디렉터리별 집계를 본다.** 한 디렉터리의 문서 80건이
통째로 안 걸린다면 그건 결함 80개가 아니라 **그 디렉터리에 색인이 없다는 사실 하나**다.
고칠 것도 링크 80개가 아니라 색인 문서 1개다.

## 3. 미결 마커 — 문서가 스스로 적어둔 낡음 후보

`wiki-digest` 규격의 세션 문서는 "어디로 이어지나"에 남은 일을 적는다.
`미착수` · `미검증` · `미확인` · `미결` · `미병합` · `미push` · `착수 전` · `남았다` 같은
좁은 어휘를 쓰는데, **그 하나하나가 지금은 참이거나 거짓인 주장**이다.

이게 "낡은 주장" 점검의 후보 좁히기다. 문서 수백 건이 아니라 그 지점 수백 개만 본다.

판정은 위키 안에서 안 된다. **원본 저장소·코드·이슈 트래커에서 실측한다** —
커밋이 실제로 병합됐는지, 이슈가 닫혔는지, 미착수라던 작업이 끝났는지.
확인 방법과 결과 반영은 `references/judgment.md` 에 있다.

## 4. 오래 손 안 댄 문서 — 신호가 없으면 없다고 말한다

git 이력에서 파일별 최종 수정일을 얻는다. **이력 전체가 30일보다 짧으면 "신호 없음"으로
보고하고 아무것도 내지 않는다.**

이관 직후에는 반드시 이 상태가 된다. `cp -R` 이 mtime 을 전부 리셋하고 첫 커밋이
모든 파일을 같은 날로 만들기 때문이다. **없는 신호를 있는 척 내놓으면 안 된다** —
전량이 "오늘 수정됨"인 목록은 정보가 0이다. 몇 달 지나면 같은 코드가 진짜 신호를 낸다.

## 무엇을 점검하지 않나 — 모순 서술

**서로 모순되는 서술은 이 스킬이 다루지 않는다.** 후보를 좁히는 기계적 신호를
찾지 못했다. 같은 식별자(커밋 해시·PR 번호)를 언급하는 문서 쌍으로 좁혀봐도
수백 쌍이 남고, 애초에 두 문서가 같은 커밋을 언급하는 건 모순이 아니라 정상 패턴이라
거의 전부 거짓 양성이다.

모순은 **미결 마커를 판정하는 과정에서 드러나는 것**으로 둔다. 실제로 관측된 모순도
그렇게 나왔다. 없는 기둥을 세우는 것보다 되는 것으로 시작하는 편이 낫다.

## 테스트

```bash
python3 -m unittest discover -s <skill>/tests
```

외부 의존 없이 stdlib 만 쓴다. **스크립트를 고치면 여기부터 돌린다** — 이 스위트의
상당수가 실사용에서 터진 버그의 회귀 방지라, 통과하지 않으면 같은 사고가 재발한다.

## 마무리

무엇을 고쳤고 무엇을 판정 대기로 남겼는지 보고한다. **자동 수정한 것과 사람이 결정할
것을 반드시 구분한다.** 위키 루트에 `log.md` 가 있으면 이번 턴 항목을 하나 추가한다 —
파일당이 아니라 턴당 하나다.
