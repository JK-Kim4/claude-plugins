# wiki-lint

`${CLAUDE_SKILL_DIR}`는 Claude Code가 스킬을 로드할 때 이 스킬 디렉터리의 절대 경로로 치환한다. 치환되지 않는 환경(`npx skills add`로 설치한 Codex·Gemini)에서는 이 SKILL.md가 있는 디렉터리를 뜻한다.

Karpathy 원문의 세 연산(Ingest · Query · Lint) 중 **Lint**. 지식베이스는 쓸수록 링크가 끊기고, 아무도 안 읽는 문서가 쌓이고, 한때 맞았던 서술이 조용히 틀려진다. 이 스킬은 그것을 찾는다.

**핵심 원칙: 스크립트는 좁히고, 판정은 LLM이 한다.** 수백~수천 건을 전량 읽는 방식은 성립하지 않는다.

**경계** — 문서를 새로 쓰거나 세션을 가공하지 않는다(그건 `wiki-digest`). 링크 파싱·해석은 `wiki-bootstrap`의 `survey.py`·`wikilink_convert.py`를 그대로 쓴다. 낡음 판정은 조회(`wiki-recall`)가 아니라 여기서 한 번만 치른다 — 3번이 남기는 `→ YYYY-MM-DD 확인:` 주석이 이후 조회의 근거가 된다.

- 후보를 놓고 무엇을 근거로 결정하는가 → `references/judgment.md`
- 점검 항목을 이렇게 나눈 이유와 실측 → `references/rationale.md`

## 한 번에 보기

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/lint.py                 # 루트는 설정에서
python3 ${CLAUDE_SKILL_DIR}/scripts/lint.py <위키루트>       # 직접 지정
```

위키 루트는 인자가 없으면 `~/.config/llm-wiki/config.json`의 `root`에서 얻는다. 없으면 알려주고 멈춘다. 점검 4종의 요약이 나오고, `--check <이름>`(`links` · `orphans` · `pending` · `stale`)으로 상세를, `--json out.json`으로 판정용 원자료를 본다.

## 1. 깨진 링크 — 세는 것과 고칠 수 있는 것은 다르다

`survey.py`가 세고, 여기서 **복구 가능성**을 분류한다.

| 분류 | 뜻 | 처리 |
|---|---|---|
| 복구 가능 | 대상이 하나로 특정됨 | `--apply`로 일괄 수정 (적용 전 건식 결과 확인, judgment.md) |
| 모호 | 같은 이름 후보가 여럿 | 사람이 고른다 |
| 대상 없음 | 트리에 없음 | **고치지 않는다** — "여기에 문서가 있어야 한다"는 정보다 |
| 불변 영역 | 아카이브·`sources/`·`raw/` 출발 | **손대지 않는다** |
| 외부(위키 밖) | 위키 루트 밖을 가리키는데 이 머신에 그 파일이 없음 | **자동 수정하지 않는다** — 경로 오탈자인지 머신 레이아웃 차이인지 사람이 가른다 |

외부 대상이 **실존**하는 링크는 애초에 깨진 것으로 세지 않는다(파일시스템 실존 기준). 이런 링크는 머신 레이아웃에 종속되므로 다른 머신에서는 전부 "외부"로 떨어진다.

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/lint.py <루트> --check links           # 건식
python3 ${CLAUDE_SKILL_DIR}/scripts/lint.py <루트> --check links --apply   # 적용
```

**0을 목표로 삼지 않는다.** 적용 후 `survey.py`로 깨진 링크가 실제로 그만큼 줄었는지 대조한다.

## 2. 고아 문서 — 발견은 목록이 아니라 디렉터리다

피참조 0건인 문서를 찾되, 링크로 도달하지 않는 것이 정상인 것은 뺀다: 세션 문서·템플릿(날짜와 검색으로 도달), 아카이브(안 걸리는 것이 목적), 진입점 파일(`00-INDEX.md`·`README.md`·`00-STATUS.md`).

**개별 파일을 나열하기 전에 디렉터리별 집계를 본다.** 한 디렉터리 80건이 통째로 안 걸린다면 결함 80개가 아니라 **색인이 없다는 사실 하나**이고, 고칠 것도 색인 문서 1개다.

## 3. 미결 마커 — 문서가 스스로 적어둔 낡음 후보

세션 문서의 "어디로 이어지나"에 적힌 `미착수` · `미검증` · `미확인` · `미결` · `미병합` · `미push` · `착수 전` · `남았다` 같은 어휘는 **지금은 참이거나 거짓인 주장**이다. 이것이 낡은 주장 점검의 후보 좁히기다.

판정은 위키 안에서 안 된다. **원본 저장소·코드·이슈 트래커에서 실측한다.** 확인 방법, 어휘별 오탐률, 결과를 문서에 덧붙이는 형식은 `references/judgment.md`.

## 4. 오래 손 안 댄 문서 — 신호가 없으면 없다고 말한다

git 이력에서 파일별 최종 수정일을 얻는다. **이력 전체가 30일보다 짧으면 "신호 없음"으로 보고하고 아무것도 내지 않는다.** 이관 직후에는 반드시 이 상태다(`cp -R`과 첫 커밋이 전부 같은 날로 만든다). 없는 신호를 있는 척 내놓지 않는다.

## 점검하지 않는 것 — 모순 서술

서로 모순되는 서술은 후보를 좁히는 기계적 신호를 찾지 못해 다루지 않는다(rationale.md). 모순은 **미결 마커를 판정하는 과정에서 드러나는 부산물**로 둔다.
