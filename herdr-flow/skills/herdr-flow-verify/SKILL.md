# 하위 세션 보고 받아 대조하기

`<skills>`는 이 스킬 디렉터리의 부모다(로컬 설치면 `~/.claude/skills`, 플러그인 설치면 `<plugin>/skills`). `herdr-flow/`는 공용 규칙·스크립트만 담은 형제 디렉터리다.

먼저 읽을 것: `<skills>/herdr-flow/shared/rules.md` 4~7절. 스크립트: `<skills>/herdr-flow/scripts/`.

## 1. 감시는 한 번만 건다

하위 세션이 실제로 일하는 동안만 건다. 이미 걸려 있으면 다시 걸지 않는다.

```
Monitor(
  description: "<작업> INBOX 새 보고 줄",
  command: "<skills>/herdr-flow/scripts/inbox-watch.sh <작업 폴더>/reports/INBOX.md",
  timeout_ms: 1800000
)
```

- Monitor는 최대 30분이면 끝난다. 만료 알림이 오면 하위 세션이 아직 일하는 중일 때만 같은 명령으로 다시 건다. 다시 걸기 전에 `tail -5 INBOX.md`로 그 사이 놓친 줄이 없는지 본다(`tail -n 0`이라 만료 사이 줄은 안 나온다).
- Monitor 안에서는 herdr를 부르지 않으므로 샌드박스 안에서 돌아간다.

- 모든 하위 세션이 `[대기]`(사용자 결정 대기)거나 끝났으면 감시를 멈춘다(TaskStop).
- 정해진 시각에 직접 대조할 회차(배포 뒤 첫 실발송 등)가 있으면 따로 깨운다: `Bash(run_in_background) <skills>/herdr-flow/scripts/wake-at.sh "<YYYY-MM-DD HH:MM>" "<할 일>"`. 대조할 데이터가 쌓이도록 회차 2~3분 뒤로 잡는다. 체크리스트에는 미리 `start`를 쓰지 않는다.
- 트래픽 없는 dev에는 시간 감시를 걸지 않는다. 시험 결과 확인으로 끝.
- 쓰지 않는 방식: 화면 끝 grep, `agent list` idle 폴링, 10분짜리 `until` 루프를 반복해서 다시 걸기.

## 2. 새 줄 분류

| 줄 | 할 일 |
|---|---|
| `… 끝` / `준비 끝` | 3절 대조 → 4절 기록 → 5절 보고 |
| `[대기]` | 하위 세션이 낸 사실을 대조한 뒤, 사용자에게 **결정 하나만** 묻는다(`rules.md` 7절). 하위 세션의 선택지 문장을 그대로 옮기지 않는다 |
| `[인계 필요]` | 진행 중 단계가 끝났는지 확인 → 같은 일을 새 세션에 맡긴다(`herdr-flow-brief`, 지시서는 그대로 + 「앞 세션 결과 파일부터 읽기」). 옛 세션은 작업 트리 확인 후 닫는다 |
| 되돌림 실행(herdr 직접 보고 포함) | 즉시 사용자에게 알린다: 무엇이 기준을 벗어났고, 무엇을 되돌렸고, 지금 상태. 그다음 대조 |
| 회차 보고 | 판정에 쓰이는 회차면 3절 대조. 단순 진행이면 기록만 |

여러 줄이 한꺼번에 오면 사용자 결정이 필요한 것(`[대기]`, 되돌림)부터.

## 3. 직접 대조 — 같은 폭으로

하위 세션 보고는 주장이다. 사용자에게 사실로 올리거나 다음 결정에 쓰기 전에 직접 본다. 결과 파일을 열고, 보고의 값마다 원천을 하나씩 다시 읽는다.

| 보고에 이런 게 있으면 | 오케스트레이터가 직접 볼 것 |
|---|---|
| 커밋·PR·머지 | `git log`·`gh pr view --json state,mergeCommit,headRefOid`, diff가 지시서 범위 안인지 |
| 배포 | 실제 태그·이미지(`kubectl get … -o jsonpath`), 파드 Ready·재시작, ArgoCD Synced, 배포 전후 오류 로그·5xx·요청량 비교 |
| 설정 변경 | 배포된 값(운영 렌더 결과·live 리소스), 바뀐 줄이 의도한 것뿐인지 |
| 건수·대상 수 | 읽기 전용 DB(replica)·로그로 같은 구간을 다시 센다. 센 기준(회차 ±N분, 템플릿, DISTINCT)을 붙인다 |
| 「A와 B가 같다」 | 양쪽을 다 읽는다(이전·이후, 옛 구현·새 구현, 부르는 쪽·받는 쪽). 직전 회차까지 |
| 「동작한다/안 한다」 | 연결이 살아 있는지(클라이언트 초기화, 환경변수, 플래그), 서버가 스스로 도는 예약 작업(cron)까지 |
| 「경로 없음」「불가」「권한 없음」 | 그대로 믿지 않는다. 메모리·인계 문서 「작업 요령」에 적힌 다른 경로를 직접 시도 |
| `미확인` 항목 | 보고하기 전에 오케스트레이터가 해소할 수 있으면 해소한다 |

- 운영 DB는 읽기 전용 replica만. primary가 필요하면 사용자 규칙의 승인 절차로 묻는다.
- 개인정보 칸(회원 이름·연락처·메시지 본문)은 출력하지 않는다. count만.
- 비용이 드는 조회(넓은 기간 로그 검색·BigQuery 등)는 먼저 크기를 재고 사용자 규칙의 비용 승인 절차를 따른다.
- 대조가 길어지면(조회 10회 이상 예상) 대조 자체를 하위 에이전트·세션에 맡기지 않는다. 오케스트레이터가 할 일이다. 대신 조회 묶음을 스크립트로 만들어 한 번에 돌린다.

## 4. 기록 (같은 턴에)

1. 체크리스트 `log`: 하위 세션이 `done`을 썼는지 query로 확인. 안 썼으면 오케스트레이터가 `done`(by=오케스트레이터, note에 「<세션> 보고 대조 끝」). 대조에서 다른 값이 나왔으면 `issues`에 행.
2. 단계 추가·범위 변경이 생겼으면 `checklist.json` 수정 → 재생성 → 재게시 → `history` 행.
3. 하위 세션 표(인계 문서): 상태·컨텍스트 갱신. 일이 끝났으면 `scripts/close.sh <이름> <작업 트리>`로 닫고 표에서 「닫음」.

## 5. 사용자에게 보고

한 보고에 한 주제. 형식:

```
<단계 내용>(<단계 ID>) <끝/통과/다름>. <핵심 값 1~2개, 센 기준 포함>.
확인 범위: <직접 본 것> / 하위 세션 보고만: <있으면> / 미확인: <있으면, 확인 방법>
<다음: 오케스트레이터가 할 일 한 줄, 또는 결정 질문 하나>
```

- 하위 세션 보고와 다른 값이 나왔으면 다르다고 먼저 쓴다(어느 쪽이 맞는지와 근거).
- 승인 질문은 맨 끝, 하나만. 다른 대기 항목을 옆에 늘어놓지 않는다.
- 사용자가 「어디까지 됐어」라고 물으면: 체크리스트 `log` query → 진행 중·대기·끝 단계 표, 하위 세션 표(컨텍스트 %), 다음 시각이 정해진 일.
