# 계획 세우기

`<skills>`는 이 스킬 디렉터리의 부모다(플러그인 설치면 `<plugin>/skills`). 공용 규칙·양식은 `<skills>/herdr-flow/`에 있다.

먼저 읽을 것: `<skills>/herdr-flow/shared/rules.md` 2절(페르소나)·7절(결정과 승인)·8절(지시서), `shared/templates/plan.md`, `shared/templates/decisions.md`. 작업 폴더가 없으면 진입점(`herdr-flow`) 2절로 먼저 만든다.

이 스킬은 계획만 한다. 구현·조사 지시서를 쓰거나 하위 세션을 띄우는 것은 계획 승인 뒤(`herdr-flow-brief`).

## 1. 이미 정해진 것 모으기

- 사용자가 이 작업을 지시한 원문, 티켓 본문, 회의 기록, 앞 세션 인계 문서의 결정 표. **이미 합의된 요구는 다시 묻지 않는다.** 원문을 `decisions.md`에 옮기고 출처를 붙인다.
- 저장소 관례: 고칠 저장소의 `AGENTS.md`·`CLAUDE.md`·컨벤션 문서(브랜치·배포 방식·테스트 방식). 관례에 없는 것을 계획에 넣으면 「새로 들이는 것」으로 표시한다.

## 2. 전제 확인 — 묻기 전에

질문에 들어갈 전제(누가 무엇을 읽고 쓰나, 어느 표·어느 경로, 지금 동작)는 **묻기 전에 원천에서 확인한다**: 코드 `파일:줄`, 배포된 설정, 읽기 전용 데이터, 로그. 확인한 시각과 함께 `plan.md` 「배경과 외부 제약」에 근거로 적는다.

- 확인 못 한 전제는 `미확인`과 확인 방법으로 적고, 질문에 사실처럼 넣지 않는다.
- 상황이 실제로 가능한지(그 경로로 들어오는 요청이 있나, 그 데이터가 있나) 한 줄 근거를 못 채우면 묻지 말고 먼저 조사한다. 조사가 크면 `investigator` 서브에이전트에 맡기고 결과를 직접 대조한다.
- 사용자가 전제를 부정하면 다시 설명하지 말고 원천으로 간다.

## 3. 인터뷰 — 한 번에 한 질문

갈림길마다 하나씩 묻는다(AskUserQuestion 또는 채팅).

- 질문에는 맥락을 붙인다: 왜 정해야 하나, 지금은 어떻게 되어 있나, 선택지별로 무엇을 얻고 잃나, 추천과 이유 한 줄. 사용자가 다른 창을 열지 않고 답할 수 있게.
- 낱말은 원천의 말만 쓴다(사용자 말, 회의 기록, 화면 문구, 코드 이름). 새 이름을 지어 질문에 넣지 않는다. 필요하면 「제안」으로 표시해 먼저 승인받는다.
- **묻지 않는 것**: 지금 동작을 그대로 유지하는 선택(같은 입력에 같은 결과) — 계획에 넣고 보고만 한다. 이미 합의된 요구. 구현 세부(사용자 결정이 아닌 것).
- **반드시 묻는 것**: 동작이 바뀌는 선택, 합의 밖의 새 의존(저장소·캐시·테이블·외부 서비스), 범위를 넓히거나 줄이는 것, 운영에 닿는 순서.
- 답을 받으면 같은 턴에 `decisions.md`에 한 건 쌓는다(문제·옵션·선택·근거·사용자 원문·시각). AI가 정한 것은 출처 `AI`.

## 4. plan.md 채우기

`templates/plan.md`의 절을 채운다. 지금 참인 것만 쓴다.

| 절 | 채우는 법 |
|---|---|
| 의도와 완료 기준 | 완료 기준은 관찰할 수 있는 조건(「운영 replica에서 N이 0」, 「테스트 n개 통과」, 「사용자가 검수 승인」) |
| 배경과 외부 제약 | 2절에서 확인한 사실, 근거와 시각 |
| 범위 | **다루지 않을 것을 구체적으로.** 하위 세션이 임의로 넓히지 못하게 하는 칸이다. 조사 중 나온 범위 밖 발견은 여기 넣지 말고 사용자에게 따로 보고(티켓 제안) |
| 단계와 진행 | 5절 |
| 검증 방법 | 단계마다 무엇을 어떻게 확인하나(명령·조회·기대값) |

## 5. 묶음과 단계 나누기

- **묶음 하나 = 지시서 한 장 = 하위 세션 하나.** 같은 파일을 건드리지 않고 순서가 없는 묶음은 동시에 돌린다. 검증이 끝난 뒤 하나씩 천천히 옮기지 않는다.
- **묶음마다 페르소나를 정한다**(`rules.md` 2절 표). 구현 `implementer`, 조사 `investigator`, 운영 실행 `operator`, 문서 `writer`, 기계적 작업 `clerk`, 운영 감시 회차 `watcher`, 외부 리뷰 `reviewer`. 설계 갈림길은 `herdr-flow-debate`로 따로 둔다. 사용자가 모델을 지정한 묶음은 그 모델을 적는다.
- **검증 위치를 붙인다**: `[로컬]`·`[dev]`·`[운영]`. 운영 동작이 바뀌는 변경은 운영 단계 앞에 dev 배포·확인 단계를 둔다.
- **승인 단계**: 되돌리기 어렵거나 남이 보는 일(운영 쓰기, 머지, 배포, 실발송, 삭제, 공유 문서 게시, 비용이 드는 작업) 앞에 승인 단계를 하나씩 둔다(`herdr-flow-gate`). 지시서에서는 준비/실행으로 나뉜다.
- 단계마다 멈춤 조건과 되돌리기(쓰기가 있는 단계)를 한 줄씩. 날짜·「다음 주」 같은 일정은 사용자가 정하지 않았으면 넣지 않는다.
- 기계적 작업(재게시, 대기, 행 수 대조)은 별도 단계로 두지 않아도 된다. 오케스트레이터가 `clerk` 서브에이전트에 넘긴다.

## 6. 체크리스트 (사용자가 원할 때)

사용자가 진척을 볼 화면을 원하면 체크리스트 스킬(예: `work-checklist`)로 만든다. 단계 ID·페르소나·승인 단계는 `plan.md` 단계 표와 같게 맞춘다. 체크리스트 기록은 오케스트레이터만 한다(`rules.md` 5절).

## 7. 계획 승인

사용자에게 한 화면으로 보인다: 의도·완료 기준, 다루지 않을 것, 단계 표(페르소나·검증 위치·승인 단계), 남은 미확인. 그리고 **계획 승인 하나만** 묻는다.

- 계획 승인은 실행 승인이 아니다. 운영 쓰기·머지·배포는 그 단계에서 따로 묻는다(`herdr-flow-gate`). `decisions.md`에 둘을 나눠 적는다.
- 승인을 받으면 `plan.md` 상태를 「구현」으로 바꾸고 첫 단계로 `herdr-flow-brief`를 부른다.
- 나중에 계획을 바꿀 때는 `plan.md`를 조용히 고치지 않는다. 바뀌는 이유를 `decisions.md`에 쌓고(번복이면 옛 결정에 「대체됨 → D-n」), 사용자에게 보고한 뒤 고친다.
