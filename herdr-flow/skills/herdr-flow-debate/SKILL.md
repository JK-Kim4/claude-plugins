# 설계 토론

`<skills>`는 이 스킬 디렉터리의 부모다(플러그인 설치면 `<plugin>/skills`). 공용 규칙·스크립트는 `<skills>/herdr-flow/`에 있다.

먼저 읽을 것: `<skills>/herdr-flow/shared/rules.md`(전부), `shared/folder-layout.md`의 `design-review/` 줄. 세션 기동·지시 전송은 `herdr-flow-brief` 4~5절과 같은 스크립트를 쓴다.

파일은 모두 작업 폴더 `design-review/`에 둔다. 토론 세션의 보고는 `design-review/INBOX.md`(덧붙이기만)로 받는다.

| 역할 | 누가 | 페르소나 |
|---|---|---|
| 토론 한쪽 | 오케스트레이터 자신 | (이 세션) |
| 토론 상대 | `<약어>-fable` 세션 | `debater` (Fable) |
| 정본 반영 | `<약어>-edit` 세션 | `writer` (Opus) |
| 외부 리뷰 | `<약어>-codex` 세션 | `reviewer` (Codex 최신 astra) |

## 1. 토론 지시서 `design-review/BRIEF.md`

쓰기 전에 전제를 원천에서 확인한다(코드 `파일:줄`, 읽기 전용 데이터, 배포된 설정). 절:

1. **할 일 한 줄** — 무엇을 하나로 모으나.
2. **사용자 질문(원문 그대로)** — 시각과 함께. 자기 말로 바꾸지 않는다.
3. **배경** — 지금 합의된 설계(정본 파일 경로와 줄 범위), 오늘 생긴 일(리뷰어 의견 원문 등), **오케스트레이터가 확인한 사실**(조회 방법·시각). 추정은 「추정, 확인할 것」.
4. **후보** — 아는 후보를 적되 「이것만으로 좁히지 말 것」.
5. **판단 기준** — 사용자 말을 평가 기준으로 풀어 적고(예: 「우아함」 = 이름 그대로 읽힘, 불변식이 적음, 지금 쓰는 경우를 무리 없이 표현, 앞으로 올 요청을 구조 변경 없이 받음, 구현·이관 비용), **그 풀이가 맞는지도 의견을 내라**고 적는다.
6. **라운드 규칙** — 1라운드는 상대 안을 읽지 않고 독립 작성. 라운드마다 결과 파일 하나(`<상대>-rN.md`), 끝나면 `design-review/INBOX.md`에 한 줄. 최대 3라운드.
7. **금지** — 코드·정본 문서·설정 수정 금지(읽기 전용), 운영 쓰기 금지, 사용자에게 직접 묻기 금지(질문은 결과 파일 「사용자에게 물을 것」 절에).

## 2. 토론 상대 띄우기

```bash
<skills>/herdr-flow/scripts/spawn.sh <약어>-fable debater
<skills>/herdr-flow/scripts/send.sh <약어>-fable <<'EOF'
당신은 <작업 이름> 설계 토론 상대 <약어>-fable입니다. <BRIEF 절대 경로> 를 끝까지 읽고 1라운드 결과를 <design-review 절대 경로>/fable-r1.md 에 쓰세요. 1라운드에서는 orch-r1.md를 읽지 마세요. 끝나면 <design-review 절대 경로>/INBOX.md 에 한 줄을 덧붙이세요. 답과 결과는 한국어로 씁니다.
EOF
```

- 사용자가 Fable 대신 다른 모델을 지정하면 그 모델로(`spawn.sh <이름> claude` 등).
- `design-review/INBOX.md` 감시를 건다(`herdr-flow-verify` 1절, 경로만 바꿔서).

## 3. 라운드

1. **1라운드(독립)**: 오케스트레이터는 `fable-r1.md`를 읽기 전에 `orch-r1.md`를 쓴다. 각자 결론, 근거(확인한 사실과 출처), 기각한 후보와 이유, 사용자에게 물을 것.
2. **2라운드(교차)**: 서로의 r1을 읽고 동의·반박·수정을 `orch-r2.md`·`fable-r2.md`에. 상대 주장에 동의할 때도 근거를 직접 확인한 뒤 동의한다. 상대가 낸 사실은 오케스트레이터가 원천으로 다시 본다.
3. **3라운드(선택)**: 남은 이견이 있을 때만. 수렴하면 멈춘다.

라운드 지시는 한 줄로: `[<오케스트레이터> HH:MM] r2: orch-r1.md를 읽고 fable-r2.md에 동의·반박·수정을 쓰세요.`

## 4. 합의안 `design-review/consensus.md`

```
# 합의: <질문> (<YYYY-MM-DD HH:MM>)
## 결론            — 한두 문장 + 모양(표·구조)
## 오케스트레이터가 직접 다시 확인한 것 — 결론이 기대는 사실마다 원천·시각
## 남은 이견        — 있으면 양쪽 주장과 근거
## 사용자 결정 필요  — 질문마다 선택지별 결과, 추천
```

- 합의안이 나중 라운드로 바뀌면 지우지 않고 아래에 「N라운드 갱신(시각) — 위 결론 n을 대체」 절을 붙인다.
- 사용자에게는 결론과 직접 확인한 것을 보고하고, **결정은 한 번에 하나씩** 묻는다(`rules.md` 7절). 답은 `decisions.md`에 원문으로.

## 5. 정본 반영 — 문서 담당 세션

결정이 나면 `design-review/BRIEF-edit.md`(반영할 결정 원문·바꿀 파일과 절·점검 명령·금지)를 쓰고 `writer` 세션에 맡긴다.

```bash
<skills>/herdr-flow/scripts/spawn.sh <약어>-edit writer
```

- 결과는 `edit-report.md`(바꾼 파일·절, 점검 결과, 주의). 두 번째 반영부터 `BRIEF-edit2.md`·`edit-report-2.md`.
- 지시서에 없는 구체화(새 조건·새 이름)를 하위 세션이 넣었으면 결과의 「주의」에 적게 하고, 오케스트레이터가 사용자 결정 거리인지 판단한다.
- 사용자가 Fable로 문서를 쓰라고 지정했을 때만 `spawn.sh <약어>-edit fable`.

## 6. 외부 리뷰 — Codex

반영이 끝나면 독립된 눈으로 리뷰를 받는다. `design-review/BRIEF-codex.md`:

- 사용자 지시 원문, **무엇을 리뷰하나**(두 Claude 세션이 합의해 반영한 설계, 「두 세션의 결론에 끌려가지 말 것」), 읽을 것(정본·논의 경과 파일·코드 경로, 읽기 전용), 사용자 쟁점 원문.
- **리뷰 관점**마다 판정을 요구한다: 문제 있음 / 없음 / 판단 보류, 근거 `파일:줄`. 관점 예: 도메인 모델, 지금 동작 보존(옮겼을 때 결과가 같은가, 다른 경우를 조건과 함께), 경계·권한, 되돌리기·이관 순서, 문서와 사실의 일치.
- 결과는 `codex-review.md` 하나만 쓰고 다른 파일은 고치지 말 것. Codex에는 지시를 영어로 쓰고 결과 언어를 한국어로 정해 주면 안정적이다.

```bash
<skills>/herdr-flow/scripts/spawn.sh <약어>-codex reviewer     # 출력의 model= 을 기록
```

## 7. 리뷰 반영

- 지적마다 오케스트레이터가 원천으로 직접 대조해 **받아들임 / 받아들이지 않음(이유) / 사용자 결정 필요**로 나눈다. 리뷰 문장을 그대로 사용자에게 옮기지 않는다.
- 동작이 바뀌는 지적, 합의 밖 새 의존은 사용자에게 하나씩 묻는다. 지금 동작을 유지하는 보완은 묻지 않고 반영 목록에 넣는다.
- 받아들인 것만 5절로 다시 반영(`BRIEF-edit<n>.md`). 「막음」 수준 지적이 있었으면 반영 뒤 재리뷰(`BRIEF-codex2.md` → `codex-review-2.md`).

## 8. 끝내기

- 토론·반영·리뷰 세션을 닫는다(`scripts/close.sh <이름>`). 정본을 고친 세션은 작업 트리를 넘겨 확인한다.
- `plan.md` 「관련 문서」에 `design-review/consensus.md`와 최종 정본 경로를 링크하고, 결론은 `decisions.md`에 이미 쌓였는지 확인한다.
- 사용자에게: 결론 한 줄, 반영한 파일, 리뷰에서 받아들인 것·받아들이지 않은 것 수와 이유, 남은 결정.
