# DLC 1라운드 결과물 리뷰

판정: **보완 필요(FAIL)**. 2·3라운드가 의존할 공유 스크립트와 산출물 계약에 수정할 문제가 있다.

대상: `f0852a6a8f14115b1b4b89e1c3a22d2d1f091d67`의 1라운드 변경 12개 파일. 직전 커밋 대비 검토했다. 별도 작업 트리 `/tmp/dlc-round1-review-f0852a6`에서 읽기·실행 검증했으며 제품 코드는 수정하지 않았다. 아직 없는 스테이지 스킬은 설계상 R2·R3 범위이므로 누락 결함으로 세지 않았다.

심각도: P1은 잘못된 대상 수정 또는 지원 프로파일 진행을 막는 문제, P2는 특정 입력·환경의 오류 및 검사 누락이다. 번호는 처리 순서를 위한 것이며 독립 수정 가능한 결함을 구분한다.

## 우선 수정할 결함

### 1. [P1] 전역 --root가 무시되어 다른 폴더를 수정한다

- 위치: `dlc/skills/dlc/scripts/dlc.py:474-479`.
- 입력: 별도 cwd에서 `dlc.py --root <target> init --profile express --slug demo`.
- 실제: 종료 코드 0이지만 target에는 docs가 없고 cwd에 작업이 생성된다. 루트가 직접 재현했다. `init --root <target>` 순서는 정상이다.
- 원인: 공통 인자 파서를 최상위와 서브파서에 모두 달면서 서브파서의 기본값 `.`가 이미 받은 값을 덮어쓴다.
- 영향: init뿐 아니라 상태 변경 명령에서 사용자가 지정하지 않은 작업을 수정할 수 있다.
- 수정 방향: 기본값 중복 덮어쓰기를 제거하고 인자 위치 양쪽을 실제 CLI 테스트로 보호한다.

### 2. [P1] express·bugfix의 유닛 산출물 생성 책임이 비어 있다

- 위치: `dlc/skills/dlc/scripts/dlc.py:316-321`, 프로파일 정의 33-36행.
- 계약: 두 프로파일은 design을 건너뛰고 requirements → plan → build로 진행한다. 설계 문서는 units.md를 design 산출물로만 정의한다.
- 실제: build 검사에서는 프로파일에 관계없이 units.md가 없으면 실패한다. plan의 산출물 계약은 plan.md뿐이다.
- 영향: 지금 계약대로 R2·R3 스킬을 구현하면 express·bugfix는 build 승인을 통과할 수 없다. 스테이지 파일 미구현이 아니라 공유 계약의 충돌이다.
- 수정 방향: design을 생략하는 프로파일에서 plan이 최소 units.md를 만들도록 명시하거나, 유닛 정보를 공급하는 대안을 정해 검사와 문서를 일치시킨다.

### 3. [P2] 소스 내용 변경을 분석 캐시가 감지하지 않는다

- 위치: `dlc/skills/dlc/scripts/dlc.py:106-111`, 189-203행.
- 실제: app.py 내용을 `print(1)`에서 `class NewService: pass`로 바꿔도 지문은 `76ea484890c7`로 같다. 경로를 바꾸면 `6f9f3d8c7678`로 달라진다.
- 영향: 파일명이 유지된 코드 변경 이후 새 작업에서 낡은 codebase.md를 재사용하고 analyze를 건너뛴다.
- 수정 방향: 분석에 영향을 주는 소스 내용·빌드 설정 변경이 캐시를 무효화하도록 지문 기준을 정하고 검증한다.

### 4. [P2] 문서의 python3 명령이 기본 Python 3.9에서 시작하지 못한다

- 위치: `dlc/skills/dlc/scripts/dlc.py:123`.
- 실제: 이 환경의 기본 Python 3.9.6에서 `str | None` 평가가 TypeError를 내어 --help와 테스트 import부터 실패한다. Python 3.12 및 3.14에서 기존 36개 테스트는 통과했다.
- 계약: README와 프로토콜은 최소 버전 없이 python3만 요구한다.
- 수정 방향: 지원 버전을 명시하고 실행 방법·오류 안내를 맞추거나, Python 3.9에서도 annotation을 평가하지 않도록 호환 처리한다.

### 5. [P2] README의 스킬 이름 와일드카드로 설치되지 않는다

- 위치: `dlc/README.md:47`.
- 실제: 로컬 검토 소스를 대상으로 같은 `--skill 'dlc*'` 선택자를 사용하면 `No matching skills found`로 실패한다.
- 영향: 문서대로 따라가는 Codex·Gemini·Cursor 사용자의 설치 경로가 막힌다.
- 수정 방향: 설치 도구에서 지원하는 정확한 스킬 이름을 사용한다. R1은 `--skill dlc`, 후속 라운드는 라우터와 단계 스킬을 모두 명시하는 설치 안내를 실제 검증한다.

### 6. [P2] 선행 단계가 끝나지 않아도 후행 단계를 승인한다

- 위치: `dlc/skills/dlc/scripts/dlc.py:437-443`.
- 실제: requirements가 pending일 때 `start plan`은 거부되지만, 필수 절이 있는 plan.md를 만든 후 `approve plan`은 종료 코드 0으로 plan을 done으로 바꾼다.
- 영향: 이후 requirements를 확정해도 이미 승인된 plan을 다시 확인하지 않고 build로 진행한다.
- 수정 방향: 승인에서도 현재 진행 가능한 단계인지 검사하고 공통 프로토콜의 start→check→approve 순서를 일치시킨다.

### 7. [P2] 존재하지 않는 요구사항 참조가 통과한다

- 위치: `dlc/skills/dlc/scripts/dlc.py:288-297`, 316-322행.
- 실제: plan의 `FR999.1`은 최상위 ID 추출에서 제외되어 검사되지 않는다. build/u1-api.md의 추적성에 `FR999`를 넣어도 `check build: OK`다.
- 계약: grounding.md는 설계·계획·빌드에서 존재하지 않는 요구사항 참조를 check가 검출한다고 명시한다.
- 수정 방향: 실제 정의된 하위 ID를 포함해 검증하고, 빌드 산출물에도 참조 검사를 적용한다. 같은 근본 목적의 검사 누락 두 경로를 함께 기록했다.

### 8. [P2] 질문에 답변 필드가 없으면 미답변을 검출하지 않는다

- 위치: `dlc/skills/dlc/scripts/dlc.py:249-258`.
- 실제: Q1과 선택지만 쓰고 Q1의 [Answer] 행을 생략한 뒤 요약 확인에만 `Looks correct`를 쓰면 `check requirements: OK`다.
- 원인: 비어 있는 태그만 찾고 각 질문의 답변 존재 여부는 검사하지 않는다.
- 수정 방향: 질문 절마다 답변 필드와 값을 요구하고 요약 확인 답변은 별개로 검사한다.

### 9. [P2] 여러 줄 설명이 상태 메타데이터로 해석된다

- 위치: `dlc/skills/dlc/scripts/dlc.py:148-150`, 165-166행.
- 실제: description에 `첫 줄\n- profile: unknown`을 전달하면 init은 성공하지만 다음 next에서 `KeyError: 'unknown'`이 발생한다. 일반 다중행 설명도 재독해 과정에서 첫 줄만 남는다.
- 영향: 사용자 설명 유실 및 상태 오염. 로컬 입력의 직렬화 결함이며 원격 공격으로 주장하지 않는다.
- 수정 방향: 자유 텍스트의 줄바꿈을 안전하게 저장·복원하고 메타데이터와 구분한다.

### 10. [P2] 활성 작업 경로·심볼릭 링크를 통해 프로젝트 밖에 쓴다

- 위치: `dlc/skills/dlc/scripts/dlc.py:134-142`, 366-369행.
- 전제: 로컬 active 파일이 절대경로나 잘못된 링크를 담고 있는 경우다.
- 실제: A 프로젝트의 active에 B 작업 절대경로를 넣으면 A에서 start가 B의 state/log를 변경한다. active를 외부 일반 파일의 심볼릭 링크로 만들면 init이 링크 대상 내용을 작업 이름으로 덮어쓴다. 모두 리뷰어가 만든 /tmp 파일로만 재현했다.
- 영향: 기존 사용자 파일 권한 범위의 데이터 손실. 원격 실행·권한 상승은 확인되지 않았다.
- 수정 방향: 단일 작업 폴더 이름과 실제 경로의 포함 관계를 검증하고, 상태·커서 쓰기 경로의 심볼릭 링크 정책을 정한다.

## 최종 검증 요약

| 검토 영역 | 판정 | 주요 근거 |
|---|---|---|
| 요구사항·공유 계약 | FAIL | express/bugfix 산출물 계약 충돌 |
| 코드 품질·정확성 | FAIL | --root 대상 오류, 승인 순서 및 검사 누락 |
| 실행 QA | FAIL | 43회 CLI 실행, 설치 선택자 및 경계 조건 실패 |
| 보안·경로 경계 | FAIL | 로컬 경로 오설정에서 외부 파일 쓰기 재현 |
| 관련 맥락 | PASS | R1 범위 및 등록 구조 확인, 문서 경로 오기만 발견 |

- Python 3.12·3.14에서 기존 unittest 36개 통과.
- `claude plugin validate ./dlc` 통과.
- skills CLI 1.5.26에서 정확한 이름 `--skill dlc`의 격리된 프로젝트 설치와 복사된 7개 리소스 바이트 일치 확인.
- 실제 두 스킬 사이 상대 경로 호출 및 전체 생명주기 실행은 R2·R3 스킬 부재로 미검증이다. 디렉터리 복사 성공을 전체 스킬 실행 성공으로 간주하지 않았다.
- `git diff HEAD~1 HEAD --check` 통과(고정 리뷰 작업 트리).
- QA에서 `skip --reason ''`가 빈 사유로 성공하는 추가 경계 문제도 확인했다. 사유 필수 계약에 맞게 공백 입력을 거부해야 한다. `skip requirements --reason ""` 실행 시 종료 코드 0과 `requirements: skipped ()`가 관찰됐다.

리뷰 중 원 브랜치에 별도 리뷰 문서 커밋 `fc0511e`가 추가됐다. 제품 구현 변경은 없었으며 이 보고서는 고정한 R1 구현 SHA를 대상으로 한다. 기존 문서는 건드리지 않았다.
