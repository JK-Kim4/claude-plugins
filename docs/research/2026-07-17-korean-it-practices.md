## 1. 요구사항·계획

### 이슈 관리 도구: Jira + Confluence 조합이 대기업 표준

- **Jira의 지배력(글로벌 수치)**: Stack Overflow Survey 2024에서 Jira는 전문 개발자 비동기 협업 도구 1위(57.5%), Confluence 35.3%, Notion 18.1%, Linear 3.2%. (출처: [Stack Overflow Survey 2024](https://survey.stackoverflow.co/2024/technology), 1차, 확신도 높음 — 단 글로벌 통계이며 한국 세그먼트 분리 수치 아님)
- **한국 대기업의 실제 사용(1차 자료 합산)**: LINE 광고 서버팀은 기획안을 Confluence로 쓰고 요구사항이 명확해지면 Jira 이슈로 쪼개 6개 상태로 추적 ([LINE 광고 서버 DevOps 문화](https://engineering.linecorp.com/ko/blog/line-ads-devops-culture), 1차, 2021). 우아한형제들 기획자는 Wiki+Jira로 문서화하고 Jira를 배포 단위로 관리 ([기획자 협업문화 인터뷰](https://techblog.woowahan.com/4122/), 1차, 2021). 컬리 입고팀은 "하나의 Jira 티켓은 한 개의 스토리만 포함" 원칙으로 에픽-스토리 구조 운영 ([입고팀 스크럼 1부](https://helloworld.kurly.com/blog/inbound-squad-sprint-1/), 1차, 2022). 카카오도 JIRA·Confluence·GitHub Enterprise 운영 (tech.kakao.com 계열, 1차이나 스니펫만 확인, 확신도 중간).
- **한국 한정 Jira 점유율 정량 수치는 확인 불가** — 프로그래머스 설문에는 협업 도구 문항 자체가 없고, 오픈서베이는 수치가 다운로드 전용 리포트에만 있음. "국내에서도 Jira가 지배적"이라는 명제는 기업별 1차 자료의 정성적 합산으로만 뒷받침된다.

### 기획서·화면설계서 문화와 PRD로의 이동

- 한국에는 "서비스 기획자" 직군이 존재하며, 화면설계서(스토리보드, SB)를 파워포인트로 만드는 관행이 SI·에이전시권을 중심으로 이어져 왔고 최근 Figma 전환 흐름이 있다. (출처: [이랜서 블로그](https://www.elancer.co.kr/blog/detail/66), [플러스엑스 brunch](https://brunch.co.kr/@plusx/108) — **2차 자료**, 확신도 중간)
- 자사 서비스 기업은 위키 기반 기획 문서로 이동: 우아한형제들 기획자는 "사소한 것까지 Wiki나 Jira에 기록" ([1차](https://techblog.woowahan.com/4122/), 2021).
- **당근의 문서 타임라인(가장 구체적인 1차 사례)**: 아이디어 회의록 → PRD → 실험 문서 → 테크 스펙 → QA 문서 → 회고록 순의 문서 체계. PRD는 "어떤 문제를 해결하는지, 어떤 구현을 해야 하는지"를 담는 문서로 정의. (출처: [당근 개발자·디자이너·PM 협업](https://careers.daangn.com/blog/post/당근마켓-it-개발-협업-pm-개발자-디자이너/), 1차, 2023, 확신도 높음)
- "파워포인트 화면설계서 → PRD 전환"을 명시적으로 서술한 기업 공식 문서는 미발견. 이 전환 서사는 두 사실(화면설계서 관행 존재 + IT 기업의 PRD 채택)의 병치로만 추론 가능하다.

### 기획-개발 협업 방식

- **우아한형제들**: 과제 시작 시 담당자 전원 킥오프 미팅(정책 협의·리스크 검토) → 사용자 스토리 상세기획 → 기획서 스펙 리뷰 → 주간 스프린트(금요일 우선순위 결정, 월요일 플래닝) + 데일리 스크럼 + Slack 과제 채널. ([1차](https://techblog.woowahan.com/4122/), 2021, 확신도 높음)
- **컬리 입고팀**: 2주 스프린트 스크럼. 주 1회 스토리 리뷰(1.5h, 피보나치 스토리 포인트), 플래닝 30분, 데일리 스탠드업 15분, 회고 30분, 주 1회 정기 배포. 팀 working agreement로 티켓 작성법·회의 방식을 사전 합의. ([1차](https://helloworld.kurly.com/blog/inbound-squad-sprint-1/), 2022, 확신도 높음)
- **토스**: 전통적 스크럼 대신 사일로(PO+디자이너+개발자+데이터 애널리스트 목적 조직)가 자율 운영·독립 배포. PO는 "0→1", PM은 "1→100" 구분. ([토스피드 넥스트 애자일](https://toss.im/tossfeed/article/next-agile-with-pm), 1차, 2022, 확신도 높음 — 단 "스크럼을 안 한다"는 명시 문장은 미확인) 토스플레이스 사일로는 스펙 리뷰 → QnA 세션 → 변경사항 정리 흐름 운영. ([1차](https://toss.tech/article/tossplace-qa-manager), 2025)
- **당근**: 아이디어 회의 → 기획·디자인·개발 → 1차/2차 QA → 배포. "QA 이후 개발 기간을 과소평가하지 않는다"는 원칙. 개발자 포함 누구나 기획 제안 가능. ([1차](https://careers.daangn.com/blog/post/당근마켓-it-개발-협업-pm-개발자-디자이너/), 2023)

### 확인 불가

- 한국 한정 이슈 트래커 점유율 정량 수치 (프로그래머스·오픈서베이·JetBrains 공개분 모두 없음)
- 카카오 본체의 애자일·기획 관행 본문 (tech.kakao.com SPA 렌더링으로 열람 실패)
- 네이버(d2.naver.com)의 요구사항·계획 단계 1차 자료
- 당근 PRD 템플릿의 구성 항목 상세

### 스킬 반영 후보

1. **to-prd 한국화**: PRD 단독 산출이 아니라 당근식 문서 타임라인(회의록 → PRD → 테크 스펙 → QA 문서 → 회고)의 앞 단계로 위치시키고, "기획서/화면설계서" 개념(정책·화면 흐름·엣지 케이스 정의)을 PRD 섹션으로 흡수하는 옵션을 둔다.
2. **to-issues 한국화**: 컬리의 "1 티켓 = 1 스토리" 원칙과 에픽-스토리 계층, 우아한형제들의 "Jira를 배포 단위로 관리"를 이슈 분해 규칙으로 반영. tracer-bullet 분해 시 "배포 단위" 경계를 묻는 질문 추가.
3. **grilling 확장**: 토스플레이스의 "스펙 리뷰 → QnA 세션 → 변경사항 정리" 흐름을 미러 — 질문 공세 후 확정된 변경사항을 별도 스레드(변경 로그)로 정리해 남기는 마무리 절차.

## 2. 설계·도메인 모델링

### 설계 문서: "테크 스펙"이 사실상의 표준 용어

- **뱅크샐러드 테크 스펙(한국에서 가장 많이 인용되는 공식 사례)**: 구현 착수 전 요약 / 배경 / 목표·비목표(Goals·Non-goals) / 계획(다이어그램·API 명세 포함) / 마일스톤 5개 섹션의 테크 스펙을 Google Docs로 작성, 전사 개발 구성원이 리뷰. 도입 목적은 커뮤니케이션 복잡도 감소. (출처: [뱅크샐러드의 특별한 스펙, '테크 스펙'](https://blog.banksalad.com/tech/we-work-by-tech-spec/), 1차, 2020, 확신도 높음)
- **당근**: 기능 개발 전 테크 스펙을 작성해 설계·기술 선택을 동료와 사전 논의. (출처: [당근 백엔드 성장기](https://medium.com/daangn/입사-2개월차-백엔드-개발자의-우당탕탕-개발-성장기-048b1e2403da), 1차이나 스니펫만 확인, 확신도 중간)
- **LINE**: "규모가 크거나 장기적인 계획이 필요한 구현은 미리 설계 문서를 작성해서 논의"하는 관행. ([LINE 클라이언트 코드 리뷰 문화](https://techblog.lycorp.co.jp/ko/code-review-culture-of-line-client-developers), 1차, 2024, 확신도 높음)
- **토스페이먼츠**: 새 API 설계 시 "API 리뷰"를 거치고, 테크니컬 라이터가 설계 단계부터 참여해 "설명하기 어려운 스펙은 코드 스멜"로 간주. ([그 많은 개발 문서는 누가 다 만들었을까](https://toss.tech/article/tech-writer-1), 1차, 2024, 확신도 높음)

### ADR: 국내 대형 기업의 공개 채택 사례 미발견 (부정적 발견)

- 주요 기업 블로그 도메인 13개 한정 검색을 포함한 5회 이상의 검색에서 "우리 팀이 ADR을 운영한다"는 국내 대기업 공식 글은 0건. 한국어 ADR 자료는 개념 소개·번역(CNCF 한국 커뮤니티, 벤더, AWS 문서 한국어판)과 개인 적용기 수준이다. (확신도 중간 — 부재의 증거는 원리상 단정 불가. 사내 비공개 위키에서의 사용 여부는 판정 불가능)
- 시사점: 한국 현업에서 "설계 의사결정 기록"은 ADR이라는 형식보다 테크 스펙 문서와 위키에 녹아 있는 것으로 보인다(이 문장은 위 두 발견의 병치에 기반한 추론임을 명시).

### DDD: 전략적 설계 도구의 부분 채택이 주류

- **컬리**: "Database Driven Development에서 진짜 DDD로" — 데이터 모델링 중심 설계에서 벗어나 이벤트 스토밍으로 유비쿼터스 언어를 만들고 몹 프로그래밍·TDD로 구현. ([road-to-ddd](https://helloworld.kurly.com/blog/road-to-ddd/), 1차, 2020, 확신도 높음)
- **카카오페이**: 여신(대출)시스템 내재화에 DDD 채택 — 바운디드 컨텍스트/애그리거트 정의, 유비쿼터스 언어, PlantUML 가시화. "학습 곡선은 가팔랐으나 유지보수성 향상"과 한계(배치용 JPA Entity 중복)까지 공개. ([여신코어 DDD](https://tech.kakaopay.com/post/backend-domain-driven-design/), 1차, 2025, 확신도 높음)
- **우아한형제들**: 회원시스템 이벤트 기반 아키텍처에 이벤트스토밍·도메인 모델링 활용. "DDD를 위해서가 아니더라도 이벤트스토밍은 문제 영역 식별에 좋은 도구"라는 실용주의 입장. ([1차](https://techblog.woowahan.com/7835/), 2022, 확신도 높음) 세일즈서비스팀은 이벤트 스토밍을 일상 협업의 지식 공유 도구로 사용. ([1차](https://techblog.woowahan.com/14671/), 2023)
- 우아콘 2024에 "DDD 그거 그렇게 하는 거 아닌데" 세션 존재([우아한테크 YouTube](https://www.youtube.com/watch?v=sLG5n_pXWK0), 1차, 스니펫만, 확신도 중간). 스포카(2021)·타다(2022)도 도입기 공개(1차, 스니펫만).
- **종합 평가**: 전술적 패턴(애그리거트, 레포지토리 등) 전면 도입보다 이벤트스토밍·유비쿼터스 언어 등 전략적 설계 도구의 부분 채택이 두드러진다. 이는 사례들의 패턴에서 도출한 정성 판단이며 설문 근거는 없다. (확신도 중간)

### 확인 불가

- 네이버·카카오 본체·토스 코어의 설계 문서 제도 1차 자료
- 국내 대기업의 ADR 공개 채택 사례 (사내 비공개 사용 여부 판정 불가)
- 설계 문서/DDD 관행에 대한 정량 설문 데이터
- Confluence를 설계 문서와 명시적으로 연계 운영한다는 공개 기업 사례 (뱅크샐러드=Google Docs, 당근=Notion만 확인)

### 스킬 반영 후보

1. **테크 스펙 템플릿 스킬**: 뱅크샐러드 5섹션(요약/배경/목표·비목표/계획/마일스톤)을 설계 문서 기본 템플릿으로 채택. 특히 "Non-goals(목표 아님)" 섹션은 스코프 확정에 효과적이며 grilling 결과물의 착지점으로 적합.
2. **domain-modeling 스킬의 ADR 항목 현지화**: ADR이라는 용어·형식을 강제하지 말고 "테크 스펙 내 의사결정 기록" 또는 위키 페이지 형식을 기본값으로, ADR은 옵션으로 제공.
3. **도메인 모델링은 유비쿼터스 언어 우선**: DDD 전술 패턴 적용보다 용어 사전(한글 도메인 용어 ↔ 코드 식별자 매핑) 구축을 1순위 산출물로 — 한국 현업의 부분 채택 패턴과 일치.

## 3. 구현

### 코딩 컨벤션: 네이버 캠퍼스 핵데이 Java 컨벤션이 사실상 표준

- **문서 실체(1차 확인)**: [캠퍼스 핵데이 Java 코딩 컨벤션](https://naver.github.io/hackday-conventions-java/)은 v1.2.0(2020-07), 최종 수정 2022-03 기준 8개 섹션(파일 공통 요건/이름/선언/들여쓰기/중괄호/줄바꿈/빈 줄/공백). 구체 규칙: 하드탭 들여쓰기(탭=스페이스 4), 최대 줄 너비 120자, UTF-8+LF, 클래스 대문자 카멜·메서드/변수 소문자 카멜·상수 대문자+언더스코어. [GitHub 저장소](https://github.com/naver/hackday-conventions-java)는 checkstyle 규칙·EditorConfig·IDE 포매터 설정을 함께 배포하고, 각 규칙에 `indentation-tab` 같은 식별자를 부여. (1차, 확신도 높음)
- **확산 경로**: 우아한테크코스 프리코스가 이 컨벤션을 권고하고, 개인 적용기가 다수 존재 — 교육·취준 층을 통해 de facto 표준화. (2차 자료 다수의 일관된 교차 확인, 확신도 중간. 기업 참조율 정량 데이터는 없음)
- **토스**: 프론트엔드 코드 지침 [Frontend Fundamentals](https://github.com/toss/frontend-fundamentals)를 오픈소스 공개 — "변경하기 쉬운 코드"를 좋은 코드로 정의, 가독성·예측 가능성·응집도·결합도 4기준. (1차, 확신도 높음)
- 카카오는 공개 코딩 컨벤션 문서가 확인되지 않음 (확인 불가 항목).

### TDD: "도입 희망은 상위, 실제 도입은 최하위" — 정확한 채택률 수치는 확보 불가

- 프로그래머스 2022 설문(5,362명): "팀에 도입된 개발 문화" 중 코드 리뷰 1위, TDD 최하위권. 단 공식 페이지는 차트만 제공해 정확한 %는 확인 불가이며, "TDD 최하위" 해석은 [2차 자료](https://veluxer62.github.io/discussions/for-better-test-culture/) 경유. (설문 자체는 1차, 확신도 중간)
- 프로그래머스 2021 설문(5,595명): "팀에 가장 도입하고 싶은 것" 1위 테스트 자동화(34.2%). (1차, 원문 확인, 확신도 높음)
- JetBrains DevEco 2022(글로벌): TDD 직접 문항 없음. 79%가 "테스트가 개발에 필수적", BDD 사용 17%. ([1차](https://www.jetbrains.com/lp/devecosystem-2022/testing/), 확신도 높음) — 즉 어떤 대규모 설문으로도 한국 TDD 채택률 정량화 불가.
- **장애물의 1차 기록**: 우아한형제들 배민선물하기팀은 (1) 테스트 개념의 팀 내 합의 부재, (2) @SpringBootTest의 느린 피드백, (3) 테스트 대역의 리팩토링 내성 저하, (4) 격리 경계 설정의 어려움을 자인하고, 협동/단독 테스트 격리 기준·GWT 패턴·DB 초기화 프로시저(실행시간 30~40% 단축)로 개선. ([서버사이드 테스트 파랑새를 찾아서](https://techblog.woowahan.com/14874/), 1차, 2023, 확신도 높음)
- **토스 서버**: TDD·커버리지 수치를 명시적으로 지향하지 않음 — "가치 있는 20%의 테스트로 80% 이상의 신뢰성", 커버리지 목적 테스트 거부, 고전파(Classicist) 접근으로 실제 객체 우선·외부 서비스만 Fake. ([가치있는 테스트를 위한 전략과 구현](https://toss.tech/article/test-strategy-server), 1차, 2024, 확신도 높음) 반면 토스뱅크에는 "커버리지 100%를 1년 6개월 유지" 사례(SLASH 21)도 있어 팀별 철학이 갈린다. (1차, 스니펫만, 확신도 중간)

### 커밋 메시지 컨벤션: 기업 공식 가이드 부재, 커뮤니티 관행으로 유지

- Conventional Commits는 [공식 한국어 번역](https://www.conventionalcommits.org/ko/v1.0.0/)이 존재할 만큼 확산됐고, Udacity 스타일(type: subject / body / footer, 제목 50자)이 커뮤니티에서 가장 널리 인용된다. 다만 확산의 증거는 velog·개인 블로그 정리글 다수라는 간접 증거다. (1차+2차 혼합, 확신도 중간)
- 네이버·카카오·라인·우아한형제들의 공식 커밋 컨벤션 공개 문서는 미발견. (부정적 발견, 확신도 중간)
- 한글 커밋 문화: "영어 prefix + 한글 본문" / "전부 한글" / "전부 영어"가 혼재하며 "팀 합의 우선, 히스토리 내 언어 일관성"이 통설. 한글 제목은 약 30자(영문 50자 환산) 요령. (출처: [OKKY 논의](https://okky.kr/articles/838664) 등 — **2차 자료**, 확신도 중간, 정량 데이터 없음)

### git 브랜치 전략: git-flow(develop 중심)가 출발점, 2022년 이후 이탈 사례 등장

- **우아한형제들 "우린 Git-flow를 사용하고 있어요"(한국에서 가장 많이 인용되는 브랜치 전략 1차 자료)**: 2016년 GitHub-flow로 시작 → 팀이 5명으로 커지며 2017년 git-flow 전환. master/develop/feature/release/hotfix 5종, feature에서 rebase+squash, PR 코드 리뷰 필수, release 브랜치에서 QA 후 master·develop 양쪽 머지+태그. ([1차](https://techblog.woowahan.com/2553/), 2017, 확신도 높음)
- "develop 중심 git-flow가 국내 지배적"이라는 직접 정량 데이터는 없으나, 위 글의 광범위한 인용과 커뮤니티 정리글 대부분이 git-flow를 기본값으로 소개한다는 간접 증거는 강함. (2차 다수, 확신도 중간)
- **이탈 사례(1차)**: 당근페이 머니서비스팀은 배포 승인 병목으로 git-flow → GitHub Flow(short-lived feature branches)로 전환해 매일 배포 ([매일 배포하는 팀이 되는 여정 1](https://medium.com/daangn/매일-배포하는-팀이-되는-여정-1-브랜치-전략-개선하기-1a1df85b2cff), 1차, 스니펫만, 확신도 중간). 뱅크샐러드는 git-flow(기능 1개 배포에 브랜치 전환 5회·PR 6회)를 폐기하고 master 중심 + Commit-Train + ChatOps로 배포 빈도 약 4배 ([하루에 1000번 배포하는 조직 되기](https://blog.banksalad.com/tech/become-an-organization-that-deploys-1000-times-a-day/), 1차, 2020, 확신도 높음). 맘시터는 트렁크 기반 개발 전환 공개 (1차, 스니펫만).

### 확인 불가

- 한국 개발자 TDD 채택률 정확한 %
- 카카오의 공개 코딩 컨벤션 문서
- 주요 기업의 공식 커밋 메시지 컨벤션 문서
- 토스의 브랜치 전략 1차 자료
- 한글 vs 영어 커밋 메시지 사용 비율 통계

### 스킬 반영 후보

1. **tdd 스킬 현지화**: red-green-refactor를 유지하되, 한국 현업의 장애물(느린 통합 테스트, 격리 기준 부재)에 대응하는 지침 추가 — 협동/단독 테스트 격리 기준(우아한형제들), "커버리지 지표를 목표로 삼지 않는다"(토스) 원칙, 외부 경계만 mock하는 Classicist 기본값.
2. **코딩 컨벤션 감지 스킬**: Java 프로젝트에서 checkstyle/EditorConfig 부재 시 네이버 핵데이 컨벤션(120자, 하드탭, 명명 규칙)을 기본 제안하고, 규칙 식별자(`indentation-tab` 등)로 리뷰 코멘트를 인용하는 관행 반영.
3. **브랜치·커밋 기본값**: 스킬이 브랜치 전략을 가정할 때 develop 중심 git-flow를 한국 기본값으로 두되(release 브랜치에서 QA라는 흐름 포함), 배포 빈도가 높은 팀을 위한 GitHub-flow 분기 지원. 커밋 메시지는 "영문 type prefix + 한글 제목 30자 이내" 옵션 제공.

## 4. 검증·디버깅

### QA 조직: 대형사는 전담 QA 조직, 소규모는 셀프 QA

- **우아한형제들**: 품질개선팀(QA·QC·Testing 전담)이 존재. "어느 정도 큰 조직이 아니면 별도 QA 조직을 두고 운영하기 힘들다"고 명시 — 중소·스타트업은 개발자 셀프 QA가 일반적임을 시사. QA가 킥오프·회고에서 누락되는 업계 관행에 대한 비판도 담김. ([QA != 통합테스트](https://techblog.woowahan.com/2534/), 1차, 2017, 확신도 높음)
- **LINE**: Quality Management 조직 산하 Service QA 팀. QA가 킥오프(기획 단계)부터 스펙 리뷰·테스트 설계·배포 후 회고까지 전 단계 개입. ([LINE의 QA는 어떻게 일할까](https://engineering.linecorp.com/ko/blog/about-line-qa/), 1차, 2021, 확신도 높음) LINE 앱은 2주 릴리스 주기에 맞춰 서비스당 QA 2명이 홀수/짝수 버전을 번갈아 담당하는 "듀얼 QA 프로세스" 운영. ([1차](https://engineering.linecorp.com/ko/blog/dual-qa-process/), 2021)
- **네이버**: QA(SQA)를 자회사 NTS(엔테크서비스)에 상당 부분 위탁하는 구조. TE → TL → QA 직군 체계. ([NTS 공식](https://www.nts-corp.com/), 1차, 확신도 높음 — "네이버 QA 전부가 NTS"라는 단정은 불가)
- **토스**: QA Platform 팀이 주 1회 릴리스되는 토스 앱의 릴리스 후보 단계에서 스모크·회귀 테스트, 자체 QA 플랫폼 '토션(Tossion)' 개발. ([1차](https://toss.tech/article/50893), 2026, 확신도 높음) 토스인컴은 별도 게이트 조직이 아닌 "제품팀 속 QA"(임베디드 모델). ([1차](https://toss.tech/article/income-qa-e2e-automation), 2025)
- 카카오는 "전사 QA" 직군을 별도 채용. (공식 채용 페이지, 스니펫만, 확신도 중간)

### 환경 단계: dev/stg/prod 개념은 공유하되 사내 명명은 제각각

- 커뮤니티 통용 구분은 local/dev/qa(test)/staging/production. (2차 자료 다수, 확신도 중간 — 통계 근거 없음)
- **카카오스타일(지그재그)**: "스테이징" 대신 "알파"(프로덕션 동일 구조+별도 DB), "베타"(애플리케이션 별도+프로덕션 DB 공유)를 사용, 알파 검증 후 프로덕션 반영. ([잘못된 브랜치 배포를 방지하기](https://devblog.kakaostyle.com/ko/2022-08-28-1-prevent-deploy-invalid-branch/), 1차, 2022, 확신도 높음)
- **카카오(카카오TV)**: Dev, Sandbox, CBT, Production 4단계 — Dev·Sandbox 통합 운영, CBT·Production은 물리 분리. CI는 Jenkins, CD는 Argo(GitOps). ([실용주의 데브옵스 for MSA](https://tech.kakao.com/posts/449), 1차이나 스니펫 2건 교차 확인, 확신도 중간~높음)
- 즉 다단계 환경(개발→검증→운영)은 보편이나, "dev/qa/stg/prod"라는 명명 자체가 표준이라기보다 알파/베타/샌드박스/CBT 등 사내 용어가 흔하다.

### 테스트 자동화: "가장 도입하고 싶지만 실제 도입은 낮은" 항목

- 프로그래머스 2021: "팀에 가장 도입하고 싶은 것" 1위 테스트 자동화 34.2%. (1차, 원문 확인, 확신도 높음)
- **토스인컴**: 수동 검증("작은 문구 변경에도 35개 이상 시나리오 재검증")이 배포 속도를 못 따라가 E2E 자동화 도입, 검증 시간 4시간 → 55분. ([1차](https://toss.tech/article/income-qa-e2e-automation), 2025, 확신도 높음)
- 토스페이먼츠는 Playwright 기반 자동화 플랫폼으로 일 45만 개 테스트 처리(SLASH 24). (1차, 스니펫만, 확신도 중간)

### 배포 승인·배포 문화

- **릴리스 트레인**: 토스 앱 주 1회 정기 릴리스(버전당 수백 개 변경), LINE 앱 2주 주기 — 대형 앱은 정기 배포가 일반적. (둘 다 1차 원문 확인, 확신도 높음)
- **승인 게이트에서 자동화로**: 뱅크샐러드는 수동 QA 게이트 대신 Lint/Test 자동 검증 + Slack ChatOps(deploybot)로 개발자 1인당 하루 약 5회 배포. ([1차](https://blog.banksalad.com/tech/become-an-organization-that-deploys-1000-times-a-day/), 2020, 확신도 높음)
- 우아한형제들은 MR에 리뷰어 2명 이상 approve가 있어야 머지 가능 — 머지가 사실상 배포 전 승인 게이트. (1차 블로그 계열, 스니펫만, 확신도 중간)
- **"금요일 배포 금지"**: 업계 불문율로 널리 회자되나 근거는 개인 브런치·블로그 경험담뿐이며 기업 공식 문서로 명문화된 1차 자료는 미발견. (2차만, 확신도: 관행의 존재는 중간, 정량 근거 없음)
- CI 도구: 카카오 사례에서 Jenkins 선택 이유가 "사내 레퍼런스 재활용"으로 언급될 만큼 레거시 지배력이 있으나, 한국 한정 점유율 통계는 없음. 글로벌(JetBrains State of CI/CD 2025)은 GitHub Actions 1위, Jenkins는 중·대형 기업 강세. ([1차](https://blog.jetbrains.com/teamcity/2025/10/the-state-of-cicd/), 확신도 높음 — 한국 수치 아님)

### 확인 불가

- 한국 한정 CI/CD 도구 점유율 통계
- "금요일 배포 금지"의 기업 공식 1차 자료
- 프로그래머스 설문의 테스트 자동화/TDD/CI-CD 도입률 정확한 % (차트가 JS 렌더링)
- 네이버 본체의 QA 조직·환경 명명 공식 글
- 카카오 본체의 전사 배포 승인 절차
- 국내 기업의 단위 테스트 커버리지 목표치(예: 80% 룰) 관행

### 스킬 반영 후보

1. **환경 맵 질의 규칙**: 스킬이 dev/stg/prod를 하드코딩하지 말고, 프로젝트의 환경 명명(알파/베타/샌드박스/CBT/qa 등)과 각 환경의 DB 공유 여부를 먼저 확인하는 선행 질문 단계를 둔다.
2. **QA 산출물 연계**: to-issues/triage 계열 스킬에 "QA 시나리오 문서" 산출 후보 추가 — 당근의 문서 타임라인(테크 스펙 다음이 QA 문서)과 릴리스 후보 단계 회귀 테스트 관행을 미러.
3. **배포 게이트 인식**: "머지 = 2인 승인 게이트"와 릴리스 트레인(주 1회/2주) 개념을 배포 관련 스킬의 기본 모델로 — 브랜치 전략 스킬과 연동해 release 브랜치 QA 흐름을 지원.

## 5. 리뷰

### 코드리뷰는 한국에서 가장 널리 도입된 개발 문화

- 프로그래머스 2021 설문(5,595명): "31.7%의 개발자는 팀에 코드 리뷰가 도입되어 있다", 코드리뷰는 "도입하고 싶은 것" 3순위, SI·솔루션 분야에서는 도입 희망 1순위. (1차, 원문 확인, 확신도 높음)
- 프로그래머스 2022 설문(5,362명): 코드 리뷰가 "팀에 도입된 개발 문화" 1위. (1차, 원문 확인, 확신도 높음)

### Pn 룰: 원출처는 뱅크샐러드(2020), 이후 확산

- **원출처 원문 검증 완료**: 뱅크샐러드 "코드 리뷰 in 뱅크샐러드 개발 문화"(정진규, 2020-11-24)가 Pn 룰을 공개한 원출처. 정의(원문): **P1** "꼭 반영해주세요 (Request changes)" / **P2** "적극적으로 고려해주세요 (Request changes)" / **P3** "웬만하면 반영해 주세요 (Comment)" / **P4** "반영해도 좋고 넘어가도 좋습니다 (Approve)" / **P5** "그냥 사소한 의견입니다 (Approve)". ([1차](https://blog.banksalad.com/tech/banksalad-code-review-culture/), 확신도 높음. 단 뱅크샐러드가 "최초 발명자"인지는 이 글만으로 단정 불가 — 한국에서 가장 유명한 공개 원출처라는 것까지가 확인 범위)
- 같은 글에서: PR 1,000라인 초과 금지, 리뷰 1~2일 내 완료 목표, D-n 룰(D-0 긴급 등 완료 기한 명시), 리뷰 요청 시 기획서·테크스펙·테스트 목록 등 문맥 제공.
- **확산**: 우아한형제들 공통시스템개발팀이 Pn 룰(P1~P5)+D-n 룰 채택 ([1차](https://techblog.woowahan.com/7152/), 2021, 확신도 높음). 당근의 채택은 2차 자료에서만 언급 (확신도 낮음~중간).

### 리뷰 코멘트 컨벤션

- **이모지 리뷰 컨벤션(cremoji)**: 코멘트 성격을 5개 이모지로 구분 — 칭찬 / 필수 수정 / 질문 / 선택적 개선 / 여담. Pn 룰과 달리 반영 여부를 리뷰이 판단에 맡기는 철학. (출처: [재그지그 개인 블로그](https://wormwlrm.github.io/2024/02/04/Code-Review-with-Emoji.html), **2차 자료**, 2024 — 특정 기업의 공식 컨벤션이라는 근거는 확인 못 함)
- 부드러운 커뮤니케이션: LINE이 "이 코드는 좋지 않습니다" 대신 부드러운 표현·칭찬 코멘트를 공식 문화로 명시한 1차 사례. 우아한테크세미나 "지속가능한 SW개발을 위한 코드리뷰"(백명석, 2022)도 피드백의 조심스러운 표현 강조. ([세미나](https://techblog.woowahan.com/8159/), 1차, 스니펫만, 확신도 중간)

### 확인 불가

- 당근의 Pn 룰 채택 1차 자료 (Medium 렌더링 차단)
- 이모지 리뷰 컨벤션의 특정 기업 귀속 (컬리·당근 공식 블로그에서 미발견)
- "N시간 내 첫 리뷰" 같은 명시적 시간 SLA를 명문 규칙으로 공개한 국내 1차 자료 (D-n 룰이 가장 근접)
- 카카오 tech.kakao.com 코드리뷰 글 2건의 본문 세부

### 스킬 반영 후보

1. **code-review 스킬에 Pn 라벨링 채택**: 리뷰 코멘트를 P1~P5로 분류해 출력하고, P1·P2는 Request changes / P3는 Comment / P4·P5는 Approve에 매핑하는 뱅크샐러드 원문 규칙을 그대로 미러. 기존 2축(Standards/Spec) 리뷰 결과에 우선순위 축을 추가하는 형태.
2. **PR 크기·컨텍스트 가드**: 리뷰 대상 diff가 300줄(우아한형제들)~1,000줄(뱅크샐러드) 기준을 넘으면 분할을 먼저 제안하고, 리뷰 요청 시 기획서·테크 스펙·테스트 목록 링크 첨부를 체크리스트로 요구.
3. **코멘트 톤 가이드**: 명령형 지적 대신 질문형·제안형 표현과 칭찬 코멘트 포함을 리뷰 출력 규칙으로 — LINE·우아한테크세미나에서 공통 강조되는 한국 현업 톤.

## 6. 지식화

### 회고: KPT가 공식 1차 자료로 확인되는 대표 형식

- **우아한형제들**: 2주 스프린트 마지막 날(금요일) KPT 회고 정례 운영 — 포스트잇 작성 → 토론 → 투표로 다음 스프린트 액션 아이템 도출. 규율로 "남 탓 금지(문제 초점을 나로)"와 "구체적·실천적 Try 도출" 강조. KPT가 네이밍 규칙·짝 프로그래밍·코드리뷰 등 팀 문화를 만들어내는 핵심 도구로 소개됨. ([팀 문화의 탄생](https://techblog.woowahan.com/2677/), 1차, 2020, 확신도 높음)
- 우아한테크코스는 회고를 커리큘럼에 내장(레벨별 회고 글쓰기 미션, 미션·레벨 단위 회고). (1차 계열, 스니펫 확인, 확신도 중간~높음)
- KPT의 "업계 전반 지배력"은 2차 자료(개인 블로그 다수)로만 추정 가능하며, 카카오·토스·당근이 KPT를 공식 채택했다는 1차 자료는 미확인. 4L 등 대안 형식의 주요 기업 공식 채택 사례도 미발견.

### 장애 포스트모템: blameless 원칙이 1차 자료로 가장 탄탄한 영역

- **LINE(2019)**: 사내 위키에 장애 보고서 템플릿(요약/탐지 시간/영향 서비스/원인/타임라인/예방책)과 작성 가이드 제공, 1차 보고 이메일은 장애 당일 발송 원칙, "개발자를 꾸짖지 않고 시스템 관점에서 대응"하는 비난 없는 문화 명시. ([장애 보고와 후속 절차 문화](https://engineering.linecorp.com/ko/blog/line-failure-reporting-and-follow-up-process-culture/), 1차, 확신도 높음) LINE 플랫폼 서버 조직은 장애 회고를 "근무일 기준 5일 이내" 실시, 보고서를 Summary(비개발자용)/Detail(개발자용)/시정·예방 조치 3부로 작성. ([1차](https://engineering.linecorp.com/ko/blog/line-platform-server-outage-process-and-dev-culture), 2022, 확신도 높음)
- **우아한형제들(2021)**: 장애 대응 5단계(탐지-공지-전파-복구-후속조치), 후속조치에서 5 Whys 근본 원인 분석, 장애보고서 전사 공유, "특정 개인이나 팀을 탓하지 않는다는 것을 모두가 알고 있다"고 blameless 명시. ([우아~한 장애대응](https://techblog.woowahan.com/4886/), 1차, 확신도 높음) 모의장애훈련(카오스 훈련)도 정례 운영, 훈련 직후 30분 회고. ([1차](https://techblog.woowahan.com/6557/), 2021)
- **카카오(2022)**: 판교 데이터센터 화재 후 공식 원인 분석문 "우리가 부족했던 이유" 공개 — "시스템 전체 관점의 이중화" 부족 등 자인, 외부 전문가 원인조사 소위, if(kakao)dev2022에서 "1015 회고" 세션 5편 공개. ([1차](https://www.kakaocorp.com/page/detail/9902), 확신도 높음)
- **데브시스터즈(2025)**: 장애 종료 후 가까운 업무일에 회고 미팅, 5 Whys, "모든 조치가 각자 상황에서 최선이었음을 신뢰한다"는 blameless 명시. ([1차](https://tech.devsisters.com/posts/incident-management-principles/), 확신도 높음)
- 토스는 실패 공유 행사 'Failure Party' 등 실패 학습 문화는 공개했으나 포스트모템 프로세스 상세 공개 글은 미확인. (1차, 스니펫만, 확신도 중간)

### 사내 위키·문서화: 도구는 기업별로 갈리고, 사용률 통계는 없음

- **우아한형제들 = Confluence**: 2016년경 Confluence+JIRA 전사 도입, "개발 조직만 써서는 효과가 없고 전사적으로 문서가 모여야 한다"는 가이드 공개. ([1차](https://techblog.woowahan.com/2508/), 스니펫만, 확신도 중간)
- **당근 = Notion**: 사내 정보(인사 제외) 전사 공개 문화 하에 Notion 전사 위키 운영 — 온보딩 위키, 팀별 위키, 회의록 연동. ([Notion 공식 고객 사례](https://www.notion.com/customers/karrot), 1차 계열, 원문 확인, 확신도 높음)
- **토스 = 자체 플랫폼**: Technical Writing Chapter 운영, 사내 지식 플랫폼 '토독(Todoc)' 개발, AI 기반 문서 작성·리뷰 자동화, 문서화 길드·지식 커미티. ([Technical Writing 시리즈 1편](https://toss.tech/article/technical-writing-1), 1차, 2026, 확신도 높음)
- Confluence vs Notion 국내 사용률의 정량 설문 수치는 확보 실패 (프로그래머스 리포트 접근 한계, 오픈서베이 요약본에 미포함).

### 기술블로그·컨퍼런스 = 지식화의 최종 공개 채널

- 조사 대상 주요 기업 전부가 공식 기술블로그를 운영하며(우아한형제들, 카카오, 토스, 당근, LINE/LY, 컬리, 네이버 D2, 데브시스터즈, 하이퍼커넥트 등), 회고·장애 대응·문서화 문화 글 자체가 이 블로그에 게재되는 구조. 정례 컨퍼런스(우아콘, SLASH, if kakao, 당근 테크 밋업)도 지식화 채널. (블로그 실존·운영은 직접 확인, 확신도 높음)

### 확인 불가

- Confluence vs Notion 국내 사용률 정량 수치
- 토스·당근의 포스트모템 프로세스 단독 공식 글
- 카카오·토스·당근의 KPT 공식 채택 1차 자료
- 회고 문화 도입률 정량 데이터 (프로그래머스 설문 내 순위 미확인)
- 카카오 안정성 보고서(Kakao Reliability Report)의 발행 연도·상세

### 스킬 반영 후보

1. **KPT 회고 스킬**: Keep/Problem/Try 3열 템플릿에 우아한형제들의 두 규율 — "Problem은 남 탓이 아니라 나·시스템 초점", "Try는 다음 스프린트에 실행 검증 가능한 구체 항목" — 을 검증 규칙으로 내장. Try 항목을 이슈 트래커 티켓으로 변환하는 후속 단계 연결.
2. **blameless 포스트모템 템플릿 스킬**: LINE 3부 구성(Summary 비개발자용 / Detail 타임라인·원인 / 시정·예방 조치)+5 Whys를 기본 템플릿으로, "장애 후 5 근무일 이내" 기한과 비난성 표현 감지·재작성 규칙 포함.
3. **위키 착지 규칙**: 지식화 산출물(회고·포스트모템·테크 스펙)의 저장처를 Confluence/Notion/저장소 내 Markdown 중 프로젝트 관행에 맞게 선택하도록 질의하는 공통 절차 — 한국 현업의 도구 분화(우아한=Confluence, 당근=Notion, 토스=자체) 반영.

## 종합: 추가 확인이 필요한 항목

1. **정량 통계 전반의 공백**: 한국 한정 Jira 점유율, TDD·회고·테스트 자동화 도입률 정확한 %, CI/CD 도구 점유율, Confluence vs Notion 사용률 — 프로그래머스 리포트 차트가 JS 렌더링이라 텍스트 수치 확보 실패. 리포트 원본(PDF/다운로드) 확보 시 보강 가능.
2. **카카오 본체 관행 다수 미확인**: tech.kakao.com이 SPA라 본문 열람 실패 — 코드리뷰·애자일·배포 승인 관행은 스니펫 수준.
3. **당근의 Pn 룰 채택**: 2차 자료에서만 언급. Medium 원문 확인 필요.
4. **이모지 리뷰 컨벤션(cremoji)의 기업 귀속**: 개인 블로그 출처로, 특정 기업 공식 관행으로 인용하면 안 됨.
5. **"금요일 배포 금지"**: 관행의 존재는 개연성이 높으나 기업 공식 1차 자료 부재 — 보고서·스킬에서 "불문율(2차 근거)"로만 인용해야 함.
6. **토스의 브랜치 전략, 네이버 본체의 계획·설계·QA 관행**: 1차 자료 미발견.
7. **우아콘 2024 DDD 세션 발표자·상세, 토스 기술블로그 런칭 시점(2021년 5월설)**: 스니펫 수준 확인에 그침.
