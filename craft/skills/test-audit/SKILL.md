# Test Audit

기존 테스트 스위트를 진단하고 정리 대상을 제안한다. **분석·제안만 한다 — 테스트를 수정·삭제하지 않는다.** 정리 실행은 사용자가 리포트를 승인한 뒤의 별도 작업이다.

판정 기준의 원본은 craft:tdd 스킬이다 — 좋은 테스트의 정의, 안티패턴, 테스트 비용 규율(최저 충분 레벨·행위당 1테스트·커버리지는 지표). 이 스킬은 그 기준을 기존 스위트에 소급 적용하는 절차다.

## 절차

### 1. 인벤토리

테스트 파일 전체를 찾고(프레임워크의 명명·디렉터리 컨벤션 기준), 각 테스트 클래스/파일을 레벨로 분류한다:

- **단위** — 인프라 없는 순수 로직 테스트
- **대체물** — in-memory·임베디드 DB 등 local-substitutable 스탠드인 사용
- **실인프라** — 실제 인프라 기동 (`@SpringBootTest`, testcontainers, 실 DB 접속, 외부 API 호출 등 마커로 감지)

가능하면 실행 시간 프로파일도 수집한다 (테스트 리포트 파일, CI 로그, 또는 스위트 1회 실행 — 실행이 비싸면 사용자에게 먼저 확인).

완료 기준: 모든 테스트 파일이 레벨 분류표에 들어가 있다.

### 2. 병렬 진단

모듈·패키지 단위로 나눠 Agent 도구로 `craft:code-reviewer`를 병렬 스폰한다. 브리프에 담을 것: 대상 테스트 파일 목록, 대응 제품 코드 경로, 그리고 아래 테스트 특화 체크리스트:

- **구현 결합** — 내부 collaborator mock, 호출 횟수·순서 검증(`verify(times(N))` 단독), private 접근, 사이드 채널 검증(인터페이스 대신 DB 직접 쿼리)
- **동어반복** — 기대값을 구현과 같은 방식으로 재계산, 상수를 자기 자신과 비교
- **커버리지 시어터** — 실패해야만 잡히는 결함이 없는 테스트 (getter/setter 테스트, 프레임워크 동작 재검증, assert 없는 실행)
- **레벨 과잉** — 순수 로직 검증인데 실인프라를 기동 (단위로 하강 가능)
- **얕은 잔재** — 더 깊은 인터페이스의 테스트가 이미 같은 행위를 보호하는데 남아 있는 내부 단위 테스트

각 발견에 근거 인용(코드 hunk)을 요구한다 — code-reviewer 페르소나의 기본 규율이다.

*(폴백)* 서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 모듈별로 현재 세션에서 직접 진단한다 — 위 체크리스트와 근거 인용 의무(인용 못 하는 지적은 내지 않는다)를 동일하게 적용한다.

### 3. 중복 행위 분석

전 모듈 결과를 모아(여기는 배리어가 정당하다 — 교차 비교가 목적) 같은 행위를 여러 테스트·여러 레벨에서 반복 검증하는 군집을 식별한다. 기준 질문: "이 테스트들 중 하나만 남긴다면 어떤 결함이 안 잡히게 되는가?" — 답이 "없다"인 테스트가 병합·삭제 후보다.

### 4. 리포트 산출

두 부분으로 구성한다:

**(a) 건강도 요약**
- 레벨 분포 (단위/대체물/실인프라 개수·비율)
- 실행 시간 프로파일 (수집됐으면 — 상위 비용 테스트)
- 안티패턴 통계와 대표 사례
- 종합 판단: 스위트가 행위를 보호하는가, 비용은 적정한가

**(b) 정리 대상 목록** — 항목마다 [분류] + 위치 + 인용 근거 + 예상 효과:
- **삭제** 후보 — 커버리지 시어터, 동어반복, 얕은 잔재
- **병합** 후보 — 같은 행위의 중복 군집 (남길 대표 테스트 지정)
- **레벨 하강** 후보 — 실인프라→대체물/단위 (예상 실행 시간 절감 명시)
- **유지하되 수선** 후보 — 행위는 보호하나 구현 결합이라 리팩토링에 깨질 테스트

마지막에 제안한다: "승인하시면 항목별로 정리를 실행할 수 있습니다. 실인프라 테스트가 계약(contract) 테스트로 재편성될 후보도 표시해 두었습니다."

## 출력 언어

리포트는 한국어로 쓴다 (테스트 이름·코드·경로는 원문 유지).
