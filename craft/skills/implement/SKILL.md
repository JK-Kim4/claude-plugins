# Implement

사용자가 지정한 PRD·이슈가 기술하는 작업을 구현한다.

## 절차

### 1. Spec 파악

PRD·이슈를 읽고, 코드베이스를 탐색하지 않았다면 탐색한다. `CONTEXT.md`의 도메인 어휘와 해당 영역 ADR을 존중한다.

### 2. 게이트 — seam과 예산

구현 시작 전에 두 가지가 합의돼 있어야 한다:

- **테스트할 seam**: PRD의 Testing Decisions나 이슈 브리프에 있으면 그것을 쓴다. 없으면 craft:tdd 스킬의 규율로 seam 후보를 제시하고 사용자와 합의한다.
- **통합테스트 예산**: 실제 인프라를 쓰는 테스트의 대상·개수. 합의가 없으면 기본 0으로 제안한다.

이 게이트를 건너뛰고 구현자를 스폰하지 않는다 — 페르소나가 중단·보고하게 돼 있다.

### 3. 구현자 스폰

Agent 도구로 `craft:tdd-implementer`를 스폰한다. 브리프에 담을 것:

- spec 원문 또는 이슈 참조 (수용 기준 포함)
- 합의된 seam 목록과 통합테스트 예산
- 프로젝트 컨벤션 포인터 (코딩 컨벤션 파일, 테스트 프레임워크, 실행 명령)

독립적인 이슈 여러 개면 병렬 스폰할 수 있다 — 단 같은 파일을 건드리지 않는 경우만 (충돌 시 worktree 격리 사용).

*(폴백)* 서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 현재 세션에서 직접 구현한다 — craft:tdd 스킬의 루프·테스트 비용 규율을 그대로 적용하고, 2단계 게이트(seam·예산)는 동일하게 유효하다.

### 4. 보고 수신·검토

구현자의 보고서에서 확인할 것: 전체 스위트 통과 출력, 예산 준수, 리팩토링 기회 목록(리뷰 단계로 넘길 것), 막힌 항목(사용자 결정 필요 시 여기서 해소하고 재스폰).

### 5. 리뷰

`/code-review`로 작업을 리뷰한다 (craft에 code-review 포크가 없으므로 기존 code-review 스킬 사용). 구현자가 보고한 리팩토링 기회를 리뷰 입력에 포함한다.

### 6. 커밋

현재 브랜치에 커밋한다. 커밋 메시지는 프로젝트의 기존 컨벤션을 먼저 확인하고 따른다. 컨벤션이 없으면 "영문 type prefix + 한글 제목(30자 이내)" 형식을 제안한다 (예: `feat: 예약 취소 시 환불 정책 적용`). develop 중심 git-flow 프로젝트면 feature 브랜치 위에서 작업하고 있는지 확인한다.

## 출력 언어

사용자 대면 출력과 커밋 메시지 본문은 한국어로 쓴다 (type prefix·코드·경로는 원문 유지).
