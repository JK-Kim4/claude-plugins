# Design It Twice

첫 아이디어는 최선이 아닐 가능성이 높다(Ousterhout). 선택된 모듈의 인터페이스를 여러 방식으로 병렬 설계해 비교한다.

어휘(module/interface/seam/adapter/leverage)와 원칙의 원본은 **codebase-design 스킬**이다 — 의존성 분류가 필요하면 그 스킬의 DEEPENING.md를 참조한다.

## 절차

### 1. 문제 공간 프레이밍

스폰 전에 사용자 대면 설명을 쓴다:

- 새 인터페이스가 충족해야 할 제약
- 의존하는 것들과 각각의 분류(in-process / local-substitutable / remote-owned / true-external)
- 제약을 구체화하는 대략적 예시 코드 스케치 — 제안이 아니라 제약을 만질 수 있게 하는 도구

사용자에게 보여준 뒤 곧장 2단계로 간다. 사용자는 설계자들이 병렬로 일하는 동안 읽고 생각한다.

### 2. 설계자 병렬 스폰

Agent 도구로 `craft:interface-designer`를 **3개 이상 병렬** 스폰한다(메시지 하나에 여러 호출). 페르소나가 어휘·원칙을 이미 내장하므로, 브리프에는 기술 맥락만 담는다.

*(폴백)* 서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 아래 설계 제약을 하나씩 순차 적용해 스스로 3개 이상의 설계안을 만든다 — 각 안을 만들 때 이전 안을 참조하지 말고 해당 제약만 극단까지 밀어붙여 radically different함을 유지한다.

브리프(또는 각 설계 패스)에 담을 것:

- 파일 경로, 결합 상세, 의존성 분류, seam 뒤에 들어갈 것
- CONTEXT.md 도메인 어휘 (있으면)
- **에이전트마다 다른 설계 제약 하나**:
  - 설계자 1: "인터페이스 최소화 — 진입점 1~3개, 진입점당 leverage 최대화"
  - 설계자 2: "유연성 최대화 — 다양한 유스케이스와 확장 지원"
  - 설계자 3: "최다 호출자 최적화 — 기본 케이스를 trivial하게"
  - 설계자 4 (해당 시): "cross-seam 의존성의 ports & adapters 중심 설계"

### 3. 제시와 비교

설계안을 하나씩 순서대로 제시해 사용자가 흡수하게 한 뒤, prose로 비교한다. 비교축은 **depth**(인터페이스의 leverage), **locality**(변경이 모이는 곳), **seam 배치**.

비교 후 자신의 추천을 낸다: 어느 설계가 가장 강한지, 왜인지. 다른 설계의 요소가 잘 결합되면 하이브리드를 제안한다. **의견을 가져라** — 사용자가 원하는 건 강한 판단이지 메뉴판이 아니다.

### 4. 착지

확정된 설계를 기록할 곳을 사용자에게 확인한다:

- **기본**: 테크 스펙 문서 — 요약 / 배경 / 목표·**비목표(Non-goals)** / 계획(인터페이스·다이어그램) / 마일스톤 5섹션. Non-goals에 기각한 설계안과 이유를 담으면 스코프 고정에 효과적이다.
- ADR 형식은 옵션 (되돌리기 어려움 + 맥락 없이 놀라움 + 실제 트레이드오프, 3조건 충족 시) — domain-modeling 스킬의 ADR-FORMAT 참조.
- 사용자가 기록을 원치 않으면 생략 — 강요하지 않는다.

## 출력 언어

사용자 대면 출력과 문서 산출물은 한국어로 쓴다 (코드·식별자는 원문 유지).
