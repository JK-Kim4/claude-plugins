# Test-Driven Development

TDD는 red → green 루프다. 이 스킬은 그 루프가 간직할 가치가 있는 테스트를 만들게 하는 레퍼런스다: 좋은 테스트란 무엇인가, 테스트는 어디에 사는가, 안티패턴, 루프의 규칙. 모든 섹션이 매 사이클에 적용된다 — 루프가 끝난 뒤가 아니라 전과 도중에 참조하라.

코드베이스 탐색 시 `CONTEXT.md`가 있으면 읽어 테스트 이름과 인터페이스 어휘를 도메인 언어에 맞추고, 해당 영역 ADR을 존중한다.

## 좋은 테스트란

테스트는 public 인터페이스를 통해 행위를 검증한다 — 구현 세부가 아니라. 코드가 통째로 바뀌어도 테스트는 안 바뀌어야 한다. 좋은 테스트는 명세처럼 읽히고("user can checkout with valid cart") 내부 구조에 무관심하므로 리팩토링에서 살아남는다.

예시는 [tests.md](tests.md), mock 지침은 [mocking.md](mocking.md) 참조.

## Seam — 테스트가 사는 곳

**seam**은 테스트를 다는 public 경계다: 내부에 손대지 않고 행위를 관찰하는 인터페이스. 테스트는 seam에 산다, 내부에 달지 않는다.

**사전 합의된 seam에서만 테스트한다.** 테스트를 쓰기 전에 테스트할 seam을 적어 사용자와 확인한다. 합의 안 된 seam에는 테스트를 쓰지 않는다. 전부를 테스트할 수는 없다 — seam을 먼저 합의하는 것이 테스트 공수를 핵심 경로와 복잡한 로직에 착지시키는 방법이다.

물어라: "public 인터페이스가 무엇이고, 어느 seam을 테스트할까요?"

## 테스트 비용 규율 — 스위트가 폭발하지 않게

테스트 개수와 실행 시간은 규율 없이는 반드시 폭발한다 (특히 spec 기반 작업에서). 네 가지 규칙:

1. **최저 충분 레벨.** 각 행위는 "올바른 이유로 실패할 수 있는 가장 낮은(싼) 레벨"에서 검증한다. 순수 로직은 인프라 없는 단위 테스트로, 어댑터 경계는 local-substitutable 대체물(in-memory, 임베디드 DB)로. **실제 인프라 테스트는 어댑터가 실 인프라와 계약을 지키는지 확인하는 소수의 계약(contract) 테스트로 한정**한다. 비즈니스 로직 검증에 실제 인프라를 동원하지 않는다. (느린 `@SpringBootTest` 피드백이 TDD의 최대 장애물이라는 것은 한국 현업 1차 기록이다 — 우아한형제들은 협동/단독 테스트 격리 기준으로 실행시간 30~40%를 줄였다)
2. **행위당 테스트 1개.** 추가 전에 "이 테스트가 실패해야만 잡히는 결함이 존재하는가?"를 묻는다. 기존 테스트가 이미 보호하는 행위면 추가하지 않는다. spec 항목→테스트의 기계적 1:1 매핑 금지 — spec은 같은 행위를 여러 문장으로 서술한다.
3. **통합테스트 예산.** seam 합의 시점에 실제 인프라 테스트의 대상·개수도 함께 합의한다. 예산을 넘는 필요가 생기면 임의로 추가하지 말고 제안하라.
4. **커버리지는 진단 지표이지 목표가 아니다.** 커버리지용 테스트를 쓰지 않는다. ("가치 있는 20%의 테스트로 80% 이상의 신뢰성" — 토스 서버 팀의 공개 전략)

## 안티패턴

- **구현 결합** — 내부 collaborator mock, private 메서드 테스트, 사이드 채널 검증(인터페이스 대신 DB 직접 쿼리). 징후: 행위가 안 변했는데 리팩토링에 테스트가 깨진다.
- **동어반복** — 기대값을 코드와 같은 방식으로 재계산(`expect(add(a,b)).toBe(a+b)`), 구성상 통과라 코드와 어긋날 수 없는 테스트. 기대값은 독립적 출처에서 — known-good 리터럴, 손으로 푼 예제, spec.
- **수평 슬라이싱** — 테스트 전부 먼저, 구현 전부 나중. 대량 테스트는 *상상된* 행위를 검증한다. **수직 슬라이스**로 일하라 — 테스트 하나 → 구현 하나 → 반복, 각 테스트는 직전 사이클이 가르쳐준 것에 반응하는 **tracer bullet**.

## 루프의 규칙

- **Red before green.** 실패하는 테스트 먼저, 통과할 만큼만 구현. 미래 테스트를 앞지르거나 투기적 기능 금지.
- **한 번에 슬라이스 하나.** 사이클당 seam 하나, 테스트 하나, 최소 구현 하나.
- **리팩토링은 루프의 일부가 아니다.** 리뷰 단계 소관이다.

## 격리 실행 (선택)

seam과 통합테스트 예산이 합의됐고 구현을 격리 위임하고 싶으면, Agent 도구로 `craft:tdd-implementer`를 스폰한다. 브리프에 담을 것: spec(또는 이슈 참조), 합의된 seam 목록, 통합테스트 예산, 프로젝트 컨벤션 포인터. 페르소나는 seam이 없으면 중단·보고하도록 만들어져 있다 — seam 합의를 건너뛰는 우회로가 아니다.

서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 이 섹션은 해당 없음 — 위 본문 규율로 현재 세션에서 직접 진행한다.
