# Triage

프로젝트 이슈 트래커의 이슈를 작은 상태 머신으로 이동시킨다.

레포가 외부 PR을 요청 표면으로 취급하면(issue-tracker 설정 참조) PR도 대상이다: **PR은 코드가 첨부된 이슈다** — 같은 역할, 같은 상태, 같은 머신. `#42` 같은 참조는 트래커 설정에 따라 이슈/PR로 해석한다.

triage 중 트래커에 게시하는 모든 코멘트·이슈는 반드시 이 문구로 시작한다:

```
> *This was generated by AI during triage.*
```

## 참조 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — durable한 에이전트 브리프 작성법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 지식 베이스 운영법

## 역할(라벨)

**분류** 역할 2종: `bug`(고장) / `enhancement`(신규·개선)

**상태** 역할 5종:

- `needs-triage` — 메인테이너 평가 필요
- `needs-info` — 리포터의 추가 정보 대기
- `ready-for-agent` — 완전히 명세됨, AFK 에이전트 투입 가능
- `ready-for-human` — 사람 구현 필요
- `wontfix` — 처리하지 않음

PR에서는 같은 상태를 첨부된 코드 기준으로 읽는다: `ready-for-agent`는 브리프가 붙어 에이전트가 diff의 다음 단계를 진행할 수 있다는 뜻, `ready-for-human`은 사람이 머지할 준비가 됐다는 뜻.

모든 triage된 이슈는 분류 역할 1개 + 상태 역할 1개를 가진다. 상태 역할이 충돌하면 진행 전에 표시하고 메인테이너에게 묻는다.

이는 canonical 역할명이다 — 실제 라벨 문자열 매핑은 별도로 제공돼 있어야 한다(`/setup-matt-pocock-skills` 참조).

상태 전이: 무라벨 이슈는 보통 `needs-triage` 먼저; 거기서 `needs-info`/`ready-for-agent`/`ready-for-human`/`wontfix`로. `needs-info`는 리포터가 답하면 `needs-triage`로 복귀. 메인테이너는 언제든 오버라이드 가능 — 이상해 보이는 전이는 표시하고 물어본다.

## 호출

메인테이너가 `/craft:triage`를 호출하고 자연어로 요청한다. 해석해서 실행하라. 예: "주의가 필요한 것 보여줘" / "#42 보자" / "#42를 ready-for-agent로" / "에이전트가 집을 수 있는 것들은?"

## 주의가 필요한 것 보여주기

트래커를 조회해 세 버킷을 오래된 순으로 제시한다:

1. **무라벨** — triage된 적 없음
2. **`needs-triage`** — 평가 진행 중
3. **마지막 triage 노트 이후 리포터 활동이 있는 `needs-info`** — 재평가 필요

PR이 범위에 있으면 외부 PR을 버킷에 포함하고 각 줄에 `[PR]`/`[issue]` 태그. 발견(discovery)은 *외부* PR만 노출하지만, 명시적으로 지목된 PR은 작성자 무관하게 triage한다.

건수와 항목당 한 줄 요약을 보여주고 메인테이너가 고르게 한다.

## 특정 이슈·PR triage

1. **맥락 수집.** 이슈/PR 전체(본문·코멘트·라벨·작성자·날짜, PR이면 diff까지)를 읽는다. 이전 triage 노트를 파싱해 해결된 질문을 다시 묻지 않는다. 도메인 글로서리를 활용해 코드베이스를 탐색하고 해당 영역 ADR을 존중한다.

2. **검증 위임.** Agent 도구로 `craft:verifier`를 스폰해 주장을 검증한다. 브리프에 담을 것: 주장 원문(재현 단계·기대 동작), 대상 브랜치/커밋, 관련 도메인 개념(중복 확인용), `.out-of-scope/` 경로. verifier가 반환하는 판정 — 확인됨(증거 포함) / 재현 실패(시도 목록) / 정보 부족 / 이미 구현됨 / 과거 기각됨 — 을 다음 단계의 입력으로 쓴다. 정보 부족은 강한 `needs-info` 신호, 확인된 검증은 훨씬 강한 에이전트 브리프가 된다.

   *(폴백)* 서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 같은 검증을 현재 세션에서 직접 한다: 버그는 재현 시도, PR은 체크아웃·실행, 도메인 개념으로 중복 검색, `.out-of-scope/` 확인 — 증거(실행 명령+출력) 없는 판정 금지, 재현 실패는 시도 목록과 함께 정직하게.

3. **추천.** 분류·상태 추천과 근거, 요청과 관련된 코드베이스 요약(이미 구현됐는지 포함)을 메인테이너에게 보고하고 지시를 기다린다.

4. **Grill (필요시).** 요청을 구체화해야 하면 `/grilling`과 `/domain-modeling` 스킬을 함께 실행 — 질문 라운드 단위로 벼리고, 결정이 내려지는 대로 CONTEXT.md/ADR을 인라인 갱신한다.

5. **결과 적용:**
   - `ready-for-agent` — 에이전트 브리프 코멘트 게시 ([AGENT-BRIEF.md](AGENT-BRIEF.md))
   - `ready-for-human` — 브리프와 같은 구조 + 위임 불가 사유(판단 필요, 외부 접근, 설계 결정, 수동 테스트) 명시
   - `needs-info` — triage 노트 게시 (아래 템플릿)
   - `wontfix` — 사유별로: **이미 구현됨**(위치를 가리키고 닫기; `.out-of-scope/`에는 쓰지 않는다 — 그 KB는 기각된 요청 전용) / **기각(bug)**(정중한 설명 후 닫기) / **기각(enhancement)**(`.out-of-scope/`에 기록, 코멘트로 링크, 닫기 — [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))
   - `needs-triage` — 역할 적용, 부분 진행이 있으면 선택적 코멘트

## 빠른 상태 오버라이드

메인테이너가 "#42를 ready-for-agent로"라고 하면 신뢰하고 직접 적용한다. 할 일(역할 변경·코멘트·닫기)을 확인받고 실행. grilling 생략. grilling 없이 `ready-for-agent`로 보낼 때는 에이전트 브리프를 쓸지 물어본다.

## needs-info 템플릿

```markdown
## Triage Notes

**지금까지 확정된 것:**

- 항목 1
- 항목 2

**추가로 필요한 것 (@reporter):**

- 질문 1
- 질문 2
```

grilling에서 해결된 것은 전부 "확정된 것"에 담아 작업이 유실되지 않게 한다. 질문은 구체적이고 실행 가능해야 한다 — "정보를 더 주세요" 금지.

## 이전 세션 재개

이슈·PR에 이전 triage 노트가 있으면 읽고, 리포터가 미해결 질문에 답했는지 확인한 뒤 갱신된 그림을 제시하고 계속한다. 해결된 질문을 다시 묻지 않는다.

## 출력 언어

사용자 대면 출력과 트래커 게시물은 한국어로 쓴다 (코드·명령어·경로·라벨명은 원문 유지).
