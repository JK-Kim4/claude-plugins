# Diagnosing Bugs

어려운 버그를 위한 규율. 명시적으로 정당화될 때만 단계를 건너뛴다.

코드베이스 탐색 시 `CONTEXT.md`가 있으면 읽어 관련 모듈의 멘탈 모델을 세우고, 해당 영역의 ADR을 확인한다.

## Redact — 시크릿 마스킹

이 스킬은 명령·출력·캡처 아티팩트를 보여주게 한다. **모든 시크릿을 먼저 마스킹하라** — 해당 자리에 `<REDACTED>`를 쓴다. 루프는 환경변수 기반으로 만들어 자격증명이 보여주는 출력이 아니라 환경에 머물게 한다. 캡처 아티팩트에는 인증 헤더가 실려 있다: 신호가 되는 줄만 인용하라.

마스킹된 출력으로 진단이 안 되면 그렇다고 말하고 사용자에게 물어라.

## Phase 1 — 피드백 루프 구축

**이것이 스킬의 전부다.** 나머지는 기계적이다. 이 버그에 빨갛게 반응하는 **tight**한 pass/fail 신호가 있으면 원인은 반드시 찾는다 — bisect도, 가설 검증도, 계측도 전부 그 신호를 소비할 뿐이다. 신호가 없으면 코드를 아무리 노려봐도 소용없다.

여기에 불균형하게 공을 들여라. **공격적으로, 창의적으로, 포기하지 말 것.**

### 위임 경로 (기본 추천)

재현 시행착오는 컨텍스트를 가장 크게 오염시키는 구간이다. Agent 도구로 `craft:verifier`를 스폰해 Phase 1~2(루프 구축 → 재현 → 최소화)를 위임하라. 브리프에 담을 것: 사용자가 말한 정확한 증상, 환경·버전·의심 커밋 범위, 재현 단계(알려진 만큼), 루프 4조건(red-capable·결정적·빠름·단독 실행). verifier의 보고서(루프 명령 + 최소 재현 + 증거)를 받아 Phase 3부터 메인 세션에서 진행한다. verifier가 "재현 실패"를 보고하면 그 시도 목록을 갖고 사용자에게 (a) 재현 환경 접근, (b) 마스킹된 캡처 아티팩트(HAR, 로그 덤프, 코어 덤프, 타임스탬프 있는 화면 녹화), (c) 임시 운영 계측 허가를 요청한다. **루프 없이 Phase 3으로 가지 않는다.**

*(폴백)* 서브에이전트 스폰을 지원하지 않는 환경(Codex 등)에서는 아래 "직접 구축" 경로로 Phase 1~2를 현재 세션에서 수행한다 — 규율은 동일하다.

### 직접 구축 시 — 수단은 싼 것부터

1. 버그에 닿는 seam에서의 **실패하는 테스트** (단위/통합/e2e)
2. 실행 중인 dev 서버에 **curl/HTTP 스크립트**
3. 픽스처 입력의 **CLI 실행** + known-good 스냅샷 diff
4. **헤드리스 브라우저 스크립트** (Playwright/Puppeteer)
5. **캡처 트레이스 재생** — 실제 요청/페이로드/이벤트 로그를 저장해 격리 재생
6. **버리는 하네스** — 시스템 최소 부분집합(서비스 1개, mock 의존성)으로 버그 경로를 함수 호출 하나로 실행
7. **Property/fuzz 루프** — "가끔 틀린 출력"이면 랜덤 입력 1000개
8. **Bisect 하네스** — 두 상태(커밋·데이터셋·버전) 사이에서 생겼다면 `git bisect run` 가능하게 자동화
9. **Differential 루프** — 같은 입력을 신·구 버전에 넣고 출력 diff
10. **HITL bash 스크립트** — 최후 수단. 사람이 클릭해야 하면 [scripts/hitl-loop.template.sh](scripts/hitl-loop.template.sh)로 사람을 루프의 부품으로 구조화

루프를 얻었으면 **조인다**: 더 빠르게(셋업 캐시, 무관한 초기화 스킵), 신호를 더 날카롭게(특정 증상에 assert, "안 죽었다" 금지), 더 결정적으로(시간 고정, RNG 시드, 파일시스템 격리). 30초짜리 flaky 루프는 루프가 없는 것과 다름없고, 2초짜리 결정적 루프는 디버깅 초능력이다.

비결정적 버그는 깨끗한 재현이 아니라 **높은 재현율**이 목표다. 트리거를 100번 돌리고, 병렬화하고, 스트레스를 넣고, 타이밍 창을 좁혀라. 50% flake는 디버깅 가능하고 1%는 불가능하다.

### 완료 기준 — red로 갈 수 있는 tight한 루프

**명령 한 줄**(스크립트 경로, 테스트 호출, curl)을 댈 수 있고, **이미 최소 1회 실행했으며**(호출과 출력을 마스킹해 제시), 그 명령이: red-capable(사용자의 정확한 증상에 반응) / 결정적 / 빠름(초 단위) / 단독 실행 가능해야 한다.

이 명령이 존재하기 전에 이론을 세우려고 코드를 읽고 있다면 **멈춰라 — 가설로 직행하는 것이 정확히 이 스킬이 막는 실패다.**

## Phase 2 — 재현 + 최소화

루프를 돌려 red를 목격한다. 확인: 사용자가 말한 바로 그 실패 모드인가(근처의 다른 실패가 아니라 — 잘못된 버그 = 잘못된 수정), 여러 번 재현되는가, 정확한 증상을 캡처했는가.

red가 되면 **최소화**: 입력·호출자·설정·데이터·단계를 하나씩 잘라내며 매번 루프를 재실행, red를 유지하는 최소 시나리오까지. 남은 모든 요소가 load-bearing(하나라도 빼면 green)일 때 완료. 최소 재현은 Phase 3의 가설 공간을 줄이고 Phase 5의 회귀 테스트가 된다.

재현·최소화 전에는 진행하지 않는다.

## Phase 3 — 가설

검증 전에 **랭킹된 가설 3~5개**를 생성한다. 단일 가설은 첫 그럴듯한 아이디어에 앵커링된다.

각 가설은 **반증 가능**해야 한다 — 예측을 명시하라: "X가 원인이면, Y를 바꾸면 버그가 사라진다 / Z를 바꾸면 악화된다." 예측을 못 대면 그 가설은 vibe다 — 버리거나 벼려라.

**검증 전에 랭킹을 사용자에게 보여준다.** 도메인 지식이 순위를 즉시 바꾸거나("#3 관련 배포가 방금 있었어") 이미 배제한 가설을 알려준다. 싼 체크포인트, 큰 시간 절약. 단 사용자가 자리에 없으면 네 랭킹으로 진행하라 — 블로킹하지 않는다.

## Phase 4 — 계측

각 프로브는 Phase 3의 특정 예측에 매핑돼야 한다. **한 번에 변수 하나.**

도구 선호: 1. **디버거/REPL** (환경이 지원하면 — 브레이크포인트 하나가 로그 열 개를 이긴다) 2. 가설을 구별하는 경계에 **타깃 로그** 3. "다 찍고 grep"은 금지.

**모든 디버그 로그에 고유 접두어 태그** (예: `[DEBUG-a4f2]`) — 마지막 정리가 grep 한 번이 된다.

**성능 분기**: 성능 회귀에 로그는 대개 틀린 도구다. 베이스라인 측정(타이밍 하네스, 프로파일러, 쿼리 플랜)을 세우고 bisect하라. 측정 먼저, 수정은 나중.

## Phase 5 — 수정 + 회귀 테스트

회귀 테스트를 **수정 전에** 쓴다 — 단, **올바른 seam**이 있을 때만. 올바른 seam이란 실제 버그 패턴을 호출처에서 일어난 그대로 행사하는 곳이다. 유일한 seam이 너무 얕으면(버그는 다중 호출자가 필요한데 단일 호출자 테스트뿐) 거기 쓴 회귀 테스트는 거짓 자신감이다.

**올바른 seam이 없으면 그 부재 자체가 발견이다.** 기록하라 — 코드베이스 구조가 버그 봉인을 막고 있다는 뜻이다. Phase 6에서 표시한다.

seam이 있으면: 최소 재현을 실패하는 테스트로 전환 → 실패 목격 → 수정 적용 → 통과 목격 → 원본(비최소화) 시나리오로 Phase 1 루프 재실행.

## Phase 6 — 정리 + 사후 분석

완료 선언 전 필수:

- [ ] 원본 재현이 더 이상 재현되지 않음 (Phase 1 루프 재실행)
- [ ] 회귀 테스트 통과 (또는 seam 부재 문서화)
- [ ] 모든 `[DEBUG-...]` 계측 제거 (접두어 grep)
- [ ] 버리는 프로토타입 삭제
- [ ] 맞았던 가설을 커밋/PR 메시지에 기록 — 다음 디버거가 배우도록

**그다음 "무엇이 이 버그를 예방했을까"를 묻는다.** 근본 원인은 blameless로 판다 — 사람이 아니라 시스템 관점에서, 필요하면 5 Whys로 왜를 거듭 묻는다. 답이 아키텍처 변경(좋은 테스트 seam 부재, 얽힌 호출자, 숨은 결합)이면 `/improve-codebase-architecture` 스킬에 구체 사항과 함께 핸드오프한다. 이 권고는 수정이 들어간 **뒤에** 하라 — 시작할 때보다 지금 아는 것이 많다.

운영 장애급 버그라 장애 보고서(포스트모템)가 필요하면 document-generator 스킬에 핸드오프한다 — 타임라인·원인·시정/예방 조치가 이 진단에서 이미 나와 있다.
