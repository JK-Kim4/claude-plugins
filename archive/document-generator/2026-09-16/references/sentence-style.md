# 문장 다듬기 (Sentence Style)

**출력 형식과 무관하게 모든 문서에 적용한다.** Markdown이든 HTML이든 Notion이든, 문서의 구조가 아무리 좋아도 문장이 읽히지 않으면 독자는 정보를 얻지 못한다.

이 문서의 권고는 토스 기술 문서 작성 가이드(technical-writing.dev)와 Google developer documentation style guide에 근거한다(하단 출처 참조).

한국어 문서를 쓸 때 특히 자주 무너지는 순서대로 정리했다. 1번과 2번만 지켜도 읽기 쉬움의 대부분이 확보된다.

## 1. 번역체·한자어를 걷어낸다

한국어 기술 문서를 읽기 어렵게 만드는 1순위 원인이다. 영어는 동사를 명사로 바꿔 쓰는 게 자연스럽지만(`-tion`, `-ment`), 한국어는 동사를 동사로 쓰는 게 자연스럽다.

**'수행/진행/처리/실시/완료' + 명사** 조합이 보이면 동사 하나로 바꾼다.

| ✗ | ○ |
|---|---|
| 로그 파일 삭제 작업을 수행합니다 | 로그 파일을 삭제합니다 |
| 코드 최적화 진행 후 배포 수행이 필요합니다 | 코드를 최적화한 후 배포합니다 |
| 인덱스 추가 작업 완료 후 성능 측정을 실시했습니다 | 인덱스를 추가한 후 성능을 측정했습니다 |
| 커넥션 풀 설정 변경 처리가 이뤄졌습니다 | 커넥션 풀 설정을 바꿨습니다 |

의미가 함축된 명사를 늘어놓지 않고, 무엇을 하는지 풀어 쓴다.

- ✗ `MongoDB 연결 정보 설정 및 초기화가 필요합니다.`
- ○ `MongoDB에 연결할 호스트와 포트를 설정하고 데이터베이스를 초기화합니다.`

## 2. 능동형으로, 주체를 분명하게

수동형은 문장을 길게 만들고 누가 무엇을 하는지 지운다.

| ✗ | ○ |
|---|---|
| 애플리케이션이 실행되기 전에 설정이 완료되어야 합니다 | 애플리케이션을 실행하기 전에 설정을 완료하세요 |
| 변경 사항이 적용된 후 다시 빌드되어야 합니다 | 변경 사항을 적용한 후 다시 빌드하세요 |
| 이 값은 캐시에 저장됩니다 | 서버가 이 값을 캐시에 저장합니다 |

도구·코드·라이브러리를 문장의 주어로 세우지 않는다. 문서에 적힌 일을 실제로 하는 것은 독자다.

- ✗ `이 라이브러리는 데이터베이스 초기화를 수행해요.`
- ○ `이 명령어를 실행하면 데이터베이스를 초기화할 수 있습니다.`

예외: 도구·시스템의 *동작 자체*를 설명할 때는 도구가 주어가 되어도 된다(`Impression 로그는 화면에 나타나면 자동으로 수집됩니다`).

## 3. 한 문장에 하나의 생각

문장이 길어지면 핵심이 묻힌다. 접속으로 이어 붙인 문장은 끊는다.

- ✗ `이 API를 호출할 때 요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다.`
- ○ `이 API를 호출할 때 요청 헤더와 인증 정보를 포함하세요.`

**메타 담화('말에 대한 말')를 지운다.** 지워도 뜻이 남으면 군더더기다.

- 흐름 안내: `다음으로`, `앞서 설명했듯이`, `이제 알아보겠습니다`
- 불필요한 강조: `사실은`, `솔직히 말하면`, `결론적으로`
- 독자 반응 유도: `아시다시피`, `여러분도 아실 것입니다`

## 4. 구체적으로 쓴다

**모호한 표현 대신 수치와 기준.** `많을 때`, `빠르게`, `성능`, `개선됨`은 독자마다 다르게 읽힌다.

- ✗ `데이터가 많을 때는 성능이 저하될 수 있습니다.`
- ○ `데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다.`

**얼버무리지 않는다.** `~일 수도 있습니다`, `~할 가능성이 있습니다`, `어느 정도`는 확인하지 않았다는 뜻이다. 확인해서 단정하거나, 확인하지 못했으면 **"미확인"이라고 명시**한다. 얼버무림과 미확인 표기는 다르다.

**누가·무엇을·어디에·어떻게를 생략하지 않는다.** 독자는 작성자의 맥락을 모른다.

- ✗ 에러가 발생하면 로그를 확인하세요.
- ○ 에러가 발생하면 애플리케이션 서버의 에러 로그(`/var/log/app/error.log`)를 확인하세요.

**앞뒤에서 참조하는 값은 맥락을 붙인다.** 처음 언급할 때 어디에 쓰이는지, 다시 쓸 때 어디서 나왔는지 한 구절로 밝힌다("1단계에서 저장한 `apiKey`로 인증합니다").

## 5. 용어를 일관되게

- **한 문서 안에서 같은 대상은 같은 이름으로.** 추가/첨부/넣기, 모듈/컴포넌트/서비스, 배치/작업/잡을 섞어 쓰지 않는다.
- **문서 종류의 템플릿이 정한 용어를 그대로 쓴다.** ADR의 배경/결정/결과, 포스트모템의 근본 원인/기여 요인을 임의로 바꾸지 않는다.
- **공식 표기를 따른다.** `K8` ✗ / `쿠버네티스(Kubernetes)` ○.
- **약어는 처음 등장할 때 풀어쓰고 병기한다.** `SSR을 지원합니다` ✗ / `SSR(Server-Side Rendering)을 지원합니다` ○. 약어와 괄호 사이는 띄우지 않는다.

## 작성 후 점검

문서를 저장하기 전에 본문을 훑으며 확인한다.

- [ ] `수행/진행/처리/실시` + 명사 조합이 남아 있지 않은가
- [ ] `~됩니다`, `~되어야 합니다`를 능동형으로 바꿀 수 있는가
- [ ] 두 생각이 한 문장에 붙어 있지 않은가
- [ ] 지워도 뜻이 남는 도입부·강조 표현이 있는가
- [ ] `개선됨`, `많음`, `느림`을 수치로 바꿀 수 있는가
- [ ] 같은 대상을 다른 이름으로 부른 곳이 있는가
