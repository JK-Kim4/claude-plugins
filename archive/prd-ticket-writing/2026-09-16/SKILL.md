# prd-ticket-writing — PRD·티켓 작성 규격

원 출처: product-on-purpose/pm-skills(Apache 2.0)의 `deliver-prd`·`deliver-user-stories`·`deliver-acceptance-criteria`·`define-prioritization-framework`를 정독 후 이 저장소 이슈 관례와 결합해 증류.

## 1. PRD 구성 (부모 이슈 `[PRD]` 본문)

순서대로: 문제 요약(왜 지금인가) → 목표·성공 지표(기준선과 목표치, 가설이면 가설 표기) → 솔루션 개요(구현을 과잉 지정하지 않는 수준) → 범위 경계(**in / out / 보류 — 보류는 해제 조건 명시**) → 유저 스토리 → 의존·리스크.

- 요건은 전부 **검증 가능**해야 한다 — 누군가 충족 여부를 판정할 수 있어야 한다.
- 15분 안에 읽히는 길이. 없는 절을 비워서 넣지 않는다(필요 없는 절 생략 = 완성, 빈 절 포함 = 미완성).
- **실행자가 작성 맥락 없이 구현하는 경우**(에이전트·다른 세션): 정본이 어느 문서인지·충돌 시 어느 쪽이 이기는지·건드리면 안 되는 것·요건별 검증 방법·멈추고 물어야 하는 조건을 명시한다. 검증 없는 요건은 "완료"와 "완료라고 믿음"을 구분하지 못한다.
- 이 저장소 관례: 착수 게이트 blockquote(즉시 가능/목업 게이트/배포 게이트) + 결정 정본 링크를 본문 최상단에.

## 2. 유저 스토리 (`deliver-user-stories` 증류)

- 형식: **"[페르소나]로서 [행동]하고 싶다 — [이유] 때문이다."** 이유 절이 핵심 — 우선순위 판단 근거가 된다.
- 일반 "사용자"가 아니라 구체 페르소나(작가·방장·운영자). 기능 단위가 아니라 **사용자 목표 단위**로 쪼갠다 — 스토리가 끝나면 사용자가 실제로 뭔가를 할 수 있어야 한다.
- INVEST 검증: Independent(순서 무관 구현 가능) / Negotiable / Valuable / Estimable / Small(한 슬라이스 안) / Testable. 스토리 문장에 구현 세부를 넣지 않는다.

## 3. 수용 기준 (`deliver-acceptance-criteria` 증류)

- Given/When/Then 만 사용. 기준 하나 = 결과 하나, 해석 없이 pass/fail 판정 가능해야 한다.
- 그룹 순서: **해피 패스 먼저 → 엣지 케이스 → 오류 상태(사용자가 보는 복구 행동 포함) → 비기능(성능·보안·감사, 해당할 때만)**.
- 실패 경로를 명시적으로 — "기록 0 사용자는 빈 카드 대신 안내 상태"처럼 비싸게 놓치는 케이스를 기준에 박는다.
- 구현 세부가 기준에 새면 안 된다.
- 이 저장소 관례: 슬라이스 이슈의 `## Acceptance criteria` 체크박스 목록. `## 실측 의무`(문서 명시값 실측 §4·계측 경로 전수 §12·신규 상태의 판정 규칙 §37·알려진 죽은 소스)와 `## 주의`를 함께 넣는다.

## 4. 우선순위 산정 (`define-prioritization-framework` 증류)

**적용성 필터 — 데이터가 허락하는 프레임워크만 돌린다. 점수 날조 금지.**

| 프레임워크 | 돌리는 조건 | 비고 |
|---|---|---|
| ICE (Impact×Confidence×Ease, 각 1~10) | 항상 가능 — 최저 입력 폴백 | 개략 추정임을 명시. 큰 투자 확정용으론 부족 |
| RICE (Reach×Impact×Conf/Effort) | 정량 reach·effort 추정치가 있을 때만 | 없으면 거부하고 ICE 로 — "추정 스캐폴드 제공" 대안 제시 |
| MoSCoW | 범위 확정(넣나/빼나) 결정일 때 | 순수 순위 매기기엔 부적합 |
| Kano | 고객 리서치 입력이 있을 때만 (게이트) | 없으면 제외하고 이유 명시 |

- **거부 규약**: 후보 3개 미만이면 "그냥 직접 결정하라" / 결정 맥락(무슨 결정을 위한 순위인가) 없으면 묻는다 / RICE 를 데이터 없이 요구받으면 정직하게 대안 제시.
- 여러 프레임워크가 돌면 **순위가 갈리는 항목이 가장 값진 발견**이다 — 어느 차원이 순위를 끌고 갔는지 설명한다.
- Effort 단위는 실행 주체의 실제 주간 용량으로 환산해 명시 — 1인 개발이면 명목 40시간 주는 틀린 단위다.
- 산출: 순위표 + 추정·가정 플래그 + 재산정 조건(계측 후) + **다음 행동 권고**(순위만 내지 않는다).

## 5. GitHub 이슈 발행 관례 (이 저장소 전용)

- gh 활성 계정 = JK-Kim4 확인(`gh auth status`, 회사 계정이면 switch). private 저장소라 이슈 링크는 외부 열람 불가.
- `[PRD]` 부모 + `[n/N]` 슬라이스, 라벨 `enhancement`. 형식 정본은 최근 이슈 실측(#144~#155 계열).
- 미확정 사항은 부모 상단에 명시 + 해당 슬라이스에 착수 전 재확인 게이트. 확정되면 **본문**을 갱신한다(코멘트 아님 — 다음 사람은 본문만 읽는다).
- 범위 증감 시 `[n/N]` 전체 재번호 + 부모 솔루션 목록 갱신.
- develop 병합은 Closes 자동 종료가 안 된다 — 이슈는 gh 로 직접 닫는다 ([[pr-closes-keyword-develop]]).
