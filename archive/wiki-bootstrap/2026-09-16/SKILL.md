# wiki-bootstrap

흩어진 마크다운을 하나의 LLM wiki로 만드는 파이프라인. Karpathy의 3계층 모델
(원본은 불변, 가공물은 LLM 소유, 규약은 파일로)을 따르되 상주 서버나 특정 도구에
묶이지 않는 순수 마크다운 구조를 만든다.

**핵심 원칙: 측정하고, 복사하고, 대조한다.** 이관은 되돌리기 어렵고 문서는 사용자가
수년간 쌓은 것이다. 옮기기 전에 재고를 세고, 이동이 아니라 복사로 하고, 옮긴 뒤 숫자를
맞춰본다. 이 세 가지를 건너뛰면 손실을 조용히 만들고도 알아채지 못한다.

## 언제 무엇을 읽나

- 인터뷰 질문과 각 선택지의 트레이드오프 → `references/interview.md`
- 이관에서 실제로 터지는 함정들 → `references/pitfalls.md` (**이관 전에 반드시 읽는다**)

## 파이프라인

### 1. 재고 조사 — 무엇을 다루는지 먼저 안다

인터뷰보다 조사가 먼저다. 사용자도 자기 문서가 몇 개인지, 링크 문법이 뭔지 모르는 경우가
대부분이라 "무엇을 통합할까요?"라고 물어도 답이 안 나온다. 숫자를 보여주면 대화가 구체적으로
바뀐다.

후보 디렉터리를 찾는다. 흔한 위치 — `~/obsidian/*`, `~/Documents/*`, `~/notes`, `~/wiki`,
`~/dev/*`. 마크다운이 몰려 있는 곳, `.obsidian/`이 있는 곳, `.git`이 있는 문서 저장소를 찾는다.

```bash
python3 <skill>/scripts/survey.py ~/obsidian/vault-a ~/notes ~/dev/kb
```

이 스크립트는 저장소별로 마크다운 수, 링크 문법 분포(wikilink vs 마크다운 링크),
프론트매터 보유율, **깨진 링크 수**를 낸다. `--json out.json`으로 저장해두면 이관 후 대조에 쓴다.

깨진 링크 베이스라인이 특히 중요하다. 이걸 안 재두면 이관 후에 깨진 링크를 발견했을 때
내가 깨뜨린 건지 원래 그랬던 건지 판별할 방법이 없다.

AI 세션 기록도 조사 대상이다. `~/.claude/projects/`와 `~/.codex/sessions/`에 대화 로그가
쌓여 있고, 이게 위키의 가장 큰 원료가 되는 경우가 많다. **Claude Code는 기본 30일 보존이라
오래된 세션이 이미 사라졌을 수 있다** — 세션을 원료로 쓸 계획이면 이관 전에 확보한다.

조사 결과를 표로 보여주고 다음으로 넘어간다.

### 2. 인터뷰 — 결정을 받는다

`references/interview.md`의 질문을 순서대로 던진다. 조사에서 나온 실측값을 각 질문에
붙여서 물어야 답이 나온다 — "링크 문법 통일할까요?"가 아니라 "A는 wikilink 75파일,
B는 마크다운 링크 266파일입니다. 통일할까요?"

한 번에 하나씩 묻는다. 선택지를 묶어서 던지면 사용자가 트레이드오프를 비교하지 못한다.

**추천을 반드시 붙인다.** 사용자는 이 도구를 처음 쓰는 사람이고, 선택지만 나열하면
결정 피로만 준다. 근거와 함께 하나를 추천하되, 다른 선택지도 진짜 선택지로 남겨둔다.

### 3. 구조 생성

인터뷰에서 정해진 루트에 디렉터리를 만든다. 기본 골격:

```
<root>/
├── 00-INDEX.md          단일 진입점
├── log.md               변경 이력 (턴당 한 항목)
├── .gitignore
├── knowledge/           확정 지식 — 프로젝트를 넘어 재사용되는 것
├── projects/<name>/     프로젝트별 현재 상태 (통합 대상 아님)
├── sessions/            AI 세션 기록 가공본
├── retrospectives/      회고
├── templates/           신규 문서의 출발점
└── raw/                 세션 원본 — git 제외, 인용 대상 아님
```

**내용이 있는 폴더만 만든다.** 3계층을 미리 다 깔아두고 싶은 유혹이 있지만, 쓰지 않을
폴더는 몇 달 뒤에도 비어 있다. `sources/`(외부 원문)나 `notes/`(잠정 분석)는 실제로
넣을 게 생겼을 때 만든다. "아직 확정 아님"은 디렉터리가 아니라 `status:` 프론트매터가 나른다.

### 4. 이관 — 이동이 아니라 복사

```bash
cp -R <원본>/. <대상>/
```

**절대 `mv`를 쓰지 않는다.** 원본 저장소 중에 git 이력이 없는 것이 섞여 있을 수 있고
(실제로 흔하다), 그러면 복구 수단이 사본뿐이다. 디스크는 싸고 문서는 비싸다.
사용자가 나중에 원본을 지우면 된다 — 그건 사용자의 결정이다.

도구 설정은 콘텐츠가 아니다. `.git`, `.obsidian`, `.ok`, `.mcp.json`, 에디터별 스캐폴드는
가져가지 않는다. 다만 **`.gitignore`나 그에 준하는 제외 규칙에 담긴 의도는 옮긴다** —
예를 들어 대용량 원본을 색인에서 빼두던 규칙을 잃으면 그게 그대로 커밋된다.

**저장소 내부 상대 링크가 많은 곳은 구조를 쪼개지 않고 통째로 옮긴다.** 폴더 두어 개를
"더 어울리는 위치"로 빼내고 싶어지는데, 그러면 그 저장소의 상대 링크가 전부 어긋난다.
정리의 이득보다 손상이 크다.

### 5. 이관 검증 — 숫자를 맞춘다

옮긴 직후 원본과 대상의 파일 수를 항목별로 대조해 사용자에게 보여준다.

```
sessions        226 → 226
retrospectives   91 → 91
projects/...    546 → 546
```

숫자가 안 맞으면 원인을 찾을 때까지 다음으로 넘어가지 않는다. 대개는 도구 설정 파일이
빠진 것(정상)이거나 복사 누락(비정상)이다. **차이를 설명할 수 있어야 정상이다** —
"몇 개 줄었지만 아마 괜찮을 것"은 검증이 아니다.

### 6. 링크 통일 (인터뷰에서 "통일"을 택했을 때만)

wikilink `[[대상]]`을 마크다운 경로 링크로 바꾼다. **반드시 건식 실행부터 한다.**

```bash
python3 <skill>/scripts/wikilink_convert.py <root>            # 건식 — 아무것도 쓰지 않음
python3 <skill>/scripts/wikilink_convert.py <root> --apply    # 적용
```

건식 실행이 해석 성공 / 모호 / 미해결을 보고한다. 미해결이 나오면 **그게 이관 때문인지
원래 없던 대상인지 반드시 확인한다.** 원본 저장소에서 같은 이름의 파일을 찾아보면 된다.
원래 없었으면 손대지 않고 그대로 두는 게 맞다 — 없는 대상을 가리키는 링크를 지우면
"여기에 문서가 있어야 한다"는 정보까지 지우는 것이다.

변환기는 이름 매칭이 여럿일 때 같은 디렉터리 → 같은 최상위 트리 순으로 좁히고,
그래도 못 정하면 모호로 분류하고 원본을 유지한다. 임의로 하나를 고르지 않는다.

### 7. 링크 건전성 대조

변환 후 다시 조사해서 **깨진 링크가 늘지 않았는지** 확인한다.

```bash
python3 <skill>/scripts/survey.py <root> --json after.json
```

이관 전 원본들의 깨진 링크 합계와 이관 후 대상의 깨진 링크를 비교한다. 늘었다면 내가
만든 것이므로 원인을 찾아 고친다. `references/pitfalls.md`에 실제로 발생한 두 가지
원인(디렉터리 개명, 이동 깊이 변화)과 처리법이 있다.

해석되는 링크는 늘고 깨진 링크는 그대로여야 성공이다.

### 8. 진입점과 git

`00-INDEX.md`를 쓴다. 구조 표, 프로젝트 목록, 그리고 **규약**을 담는다 — 링크 문법,
불변 영역, `status:` 사용법, 로그 규칙, 검색 방법. 이 파일이 다음에 오는 에이전트가
읽을 유일한 계약이다.

`.gitignore`에 대용량 원본 디렉터리를 먼저 넣고 `git init` → 첫 커밋. 순서가 중요하다.
원본을 한 번 커밋하면 이력에서 빼는 데 history 재작성이 필요해진다.

커밋 메시지에 검증 수치를 남긴다. 나중에 "이 이관이 안전했나"를 되짚을 유일한 근거다.

### 9. 루트 위치 기록 — 다른 스킬이 찾을 수 있게

만든 위키의 경로를 표준 위치에 남긴다. 이걸 안 하면 이후 스킬들이 매번 "위키가
어디죠?"를 묻거나, 더 나쁘게는 경로를 자기 본문에 박아 이식 불가능해진다.

```bash
mkdir -p ~/.config/llm-wiki
cat > ~/.config/llm-wiki/config.json <<EOF
{ "root": "<절대경로>", "raw": "raw", "sessions": "sessions" }
EOF
```

경로는 인터뷰에서 정해진 값이고, 머신마다 다르므로 **여기에만** 존재한다.
스킬 본문에는 어디에도 들어가지 않는다.

## 테스트

```bash
python3 -m unittest discover -s <skill>/tests
```

외부 의존 없이 stdlib 만 쓴다. **스크립트를 고치면 여기부터 돌린다** — 이 스위트의
상당수가 실사용에서 터진 버그의 회귀 방지라, 통과하지 않으면 같은 사고가 재발한다.

## 마무리

무엇이 만들어졌고 무엇이 아직 없는지 알린다. 세션 가공이나 점검 스킬은 이 스킬의
범위가 아니다 — 지식베이스의 뼈대까지가 여기다.

원본 저장소는 지우지 않고 남겨둔다. 며칠 써보고 사용자가 판단할 일이다.
